# 28: A Controls page in play

**What to build:** The player can look up every key of the game without leaving it. Press H during play and a Controls page opens over the game and the game pauses, like the inventory, the Automap and the stat page; press H again, or Esc, and the page closes and the game goes on. The page lists every key the game answers to, each with what it does in a few plain words, and it says how to close itself. The list is made from the same tables that bind the keys, so it cannot disagree with them: a key that is changed or added there changes the page.

**Blocked by:** 27: Page keys toggle their page

**Status:** ready-for-agent

**Spec stories:** 92, 93, 108, 109

- [x] H opens the Controls page and the game waits: nothing moves and no time passes until it closes. H pressed again closes it, with the same events as a close by Esc, and the game goes on. Esc closes it too.
- [x] The Controls page is a page of the Game core like the other three, so that every page rule applies to it and is tested at the core's interface: it opens only when no other page is open, no level-up choice waits and the question whether to sail home is not asked; another page's key does nothing while it is open; a page restored from a snapshot with it open closes with H and with Esc. What the page lists is the adapter's business, because the core knows no keys.
- [x] The page lists every key the game answers to, each with what it does, in the capital letters of the pixel font: walking (W A S D or the arrow keys), attacking (Space), switching weapon (Q), interacting (E: open, pull, read, sail), the inventory (I), the Automap (M), the stat page (C or Tab), this page (H), picking a line and equipping (Enter), closing a page (Esc), putting a Stat Point into Health, Attack or Defense (1, 2, 3), turning the sound off and on (N), and the volume (- and +). The wording is the implementer's; the keys are the keys of the controls tables. The page says how to close itself in the hint of ticket 27 ("H OR ESC TO CLOSE").
- [x] Nothing on the page is cut short or off the screen: every line is whole within the 320 x 192 screen (a second column is allowed if the list is too tall for one).
- [x] The list is made by a pure function of the controls tables. A test directly on that function (ADR 0005) pins that every key that is bound in the tables shows on the list under the label the player reads, so that a key added to a table without a line on the page fails the test, and that every line of the list fits the window it is drawn in.
- [x] H is in the controls tables, so the start-up key-clash check reads it and no key of the audio may share it; the test of the check gets a case for it. H does not hold back the browser's own shortcuts, like the other page keys.
- [x] Opening and closing the page are heard like the other pages (the same events, the same sounds).
- [x] Saves: a snapshot with the Controls page open passes the saved-game checks, and a save made before this ticket still loads. `SNAPSHOT_VERSION` is raised only if the saved shape of the state changed (a page that is open is saved as its id, so a new id alone does not change the shape); the comments of the ticket say which was chosen.
- [x] The README's controls table gets the H row and its text about the pages lists the Controls page; `docs/playtest-checklist.md` gets a line for it.
- [x] The type check, the tests, and the build pass (`npm.cmd run check`).
- [ ] Reviewer play check (manual, in a browser): during play press H, the page opens, the monsters stop and every line of the list is whole; press H again, it closes and they move again; open it and press Esc, it closes. With it open press I, M, C, and Tab (nothing opens). At a level-up choice press H (nothing opens). Press each key on the list and see that it does what the page says.

## Comments

Added at the player's request during playtesting ("we should add all the keyboard shortcuts somewhere for the user"). Decided with the player: the shortcuts are shown in play and on the title screen (ticket 29 is the title). Spec story 109; the key list, the pause rule and the Testing Decisions of the spec were amended to match.

Assumed, not decided with the player: H is the key (it was free: the keys taken are W A S D, the arrows, Space, Q, E, I, M, C, Tab, Enter, Esc, the number keys, N, - and +). Not decided: whether the opening card or the HUD should say once that H shows the controls. It is left out: the Controls line on the title (ticket 29) is how a player finds the page, and the player can say if that is too little.

For the implementer: `src/adapter/controls.ts` holds the tables and the labels (`PAGE_KEYS`, `STAT_KEYS`, `AUDIO_KEYS` and the rest), and `keysOfEverythingElse` feeds the start-up check. The list wants a table of what each key does beside the keys, so that the check and the page both read it. The Controls page is a core page: `PAGE_IDS` (`src/core/state.ts`) and the view's page union get it, and the core has nothing to show for it but that it is open (`saved-game.ts` checks a saved page against `PAGE_IDS`). Ticket 29 draws the same list on the title screen, so make the list something the title can use too.

**What was built (ticket 28).**
- H toggles a Controls page over the game, and the game waits while it is open, like the stat page, the inventory and the Automap. It is a page of the Game core: `'controls'` is in `PAGE_IDS`, the view's page is `{ id: 'controls' }` (a `ControlsPageView` and a case in `pageView`), and the same `toggle-page`, page rules, events and sounds apply. The core knows no keys and nothing of what the page lists.
- `src/adapter/controls.ts`: the H entry in `PAGE_KEYS` (`capture: false`); `PAGE_WORDS`, the few words of each page's line (a `Record<PageId, string>`, so a new page without words does not compile); `controlsTable()`, the one table, which holds each line's keys and words beside what each key is for in the start-up key check (`keysOfEverythingElse` reads it); and `controlsList()`, the pure list made from it (13 lines of `{ keys, words }`).
- `src/adapter/controls-list.ts` (new, Phaser-free): `layoutControlsList(lines)` lays the list out in two columns from its own top left corner (the keys right-aligned in a column as wide as the widest of them, the words 8 pixels after it, a line every 10 pixels: 228 x 127 pixels), and `drawControlsList(layer, layout, left, top)` draws it.
- `src/adapter/overlay.ts`: the page's window is as wide as the list and its padding (252 x 181 of the 320 x 192 screen), with CONTROLS above the list and `H OR ESC TO CLOSE` (ticket 27's `pageCloseHint`) below; a new row kind `controls` and an exported `panelHeight`.

**For ticket 29 (the title screen).** Call `controlsList()` (`controls.ts`), then `layoutControlsList(list)` and `drawControlsList(layer, layout, left, top)` (`controls-list.ts`). The layout is in pixels from the list's own top left corner and is 228 wide and 127 tall; it knows nothing of the window, so the window, its heading and the way to close it are the title's own (`controlsPagePanel` in `overlay.ts` is the in-play window). The title's key for it and its hint are ticket 29's to choose; H is the key in play.

**Decisions.**
- H is the key: assumed with the player, not decided (as above). Nothing in play says that H exists, not the HUD and not the opening card; the checklist asks the player whether that is enough.
- `SNAPSHOT_VERSION` stays 4. A page that is open is saved as its id, and `saved-game.ts` checks it against `PAGE_IDS`, so a new id does not change the saved shape. Proved by two frozen literals of version 4 saves made before this ticket (one with the stat page open, one with no page open) that still load and go on (`tests/controls-page.test.ts`), and by a save with the Controls page open that passes `parseSave` and restores open; making the version 5 fails the two old-save tests.
- The wording is mine, in the order of the ticket: walk, attack, switch weapon, interact, stats, inventory, Automap, controls, Enter, Esc, 1 2 3, N, - +. The pixel font has no `&`, quotes, `_`, `;` or arrows (it draws 0-9, A-Z, `. , ! ? ' - + / : ( ) % =` and the space), so the words use only those, and a test pins that.
- The keys are right-aligned in their column, so each sits next to its words; they are drawn in the colour of a title and the words in that of text. Seen in the screenshots: legible, nothing runs into anything. A different look is a change to `layoutControlsList` and `drawControlsList` alone.
- The audio keys keep their own start-up pass (`checkAudioKeys` over `AUDIO_KEYS`), so the table's audio lines carry no `uses`; a test pins that the check asks about exactly the keys that `PlayerInput` binds.

**Expectations that changed** (none weakened or removed; each is forced by the new id or the new window):
- `tests/player-input.test.ts`: the Esc test's ordered list of commands gains `close-page` for `controls`, after the Automap's and before `cancel-departure`.
- `tests/saved-game-walks.test.ts`: the gauntlet's seeds went from `[1, 2, 3]` to `[1, 2, 3, 4]`. The walk draws pages from `PAGE_IDS`, so a fourth id shifted the draws and the three seeds no longer saved a hero's arrow in flight; the fourth does. Its assertions are unchanged.
- `tests/page-hints.test.ts`: the room of the Controls page's hint is 228 pixels (the window is as wide as the list), as worked out by hand, where the narrow window gave 136; its `SHOWN` and `BY_HAND` rows are new. New rows too in `tests/healing-potions.test.ts` (no potion is drunk with the page open) and in the H cases of `tests/controls.test.ts`.

**Tests, and that each can fail** (every break below was made, seen red and reverted; the tree was clean after each):
- Core and the H key (`tests/controls-page.test.ts`, 22 tests): before the core change, 10 red; the page not pausing (5 red); `openPage` without its pause check (9); `togglePage` always opening (4); `closePage` closing any page (3); `SNAPSHOT_VERSION` 5 (the 2 old-save tests); H with `capture: true` (the browser's shortcuts); `keysOfEverythingElse` skipping the page (the H clash case); `isForTheGame` true (the 4 Ctrl/Cmd tests); the hint reading 'H TO CLOSE' (3 in `page-hints`); `potions.ts` allowing the page (the new row).
- The list (`tests/controls-list.test.ts`, 34 tests): the E line dropped (3 red); H labelled K (3); a key K bound in `WALK_KEYS.up` without a line (the 'exactly the keys this test has a label for' test); a `&` in the words (the literal and the drawable-characters test, which names it); `uses: []` on the Enter line (the check-asks test, and the existing ENTER clash case); a stale F1 line (the literal and the 'only keys the list shows' test).
- Layout and window (`tests/controls-list-layout.test.ts`, 9 tests): keys left-aligned (the layout literal); a gap of 4 between the columns (5 red, among them 'at least 8 pixels from its words'); the controls row 0 tall (the window's height); the narrow 160 window (the window's width and the room in `page-hints`); the panel made from an empty list (5 red, the wiring test among them); five filler lines in the table (the 'no taller than the screen' test goes red on its own, with the size ones); one over-long line (the 'no wider than the screen' test, likewise). The size tests and the fit tests are separate for that reason.

**Smoke** (the production build in headless Edge on port 5128, `?debug`, screenshots outside the repo, looked at; the server is stopped and the port is free):
- H opens the page: every one of the 13 lines is whole, in the window of 252 x 181, 5 pixels from the top and 6 from the bottom of the screen, with the title and `H OR ESC TO CLOSE`. A snapshot taken 1.5 seconds later is identical, and walking right with it open leaves the hero where it was. H again closes it and the hero then walks; Esc closes it and the hero then walks.
- With it open, I, M, C and Tab (real keys) leave it open and alone on the screen. A step by step run with synthetic key events (shown to work by H opening and closing the page) gives: Ctrl+H nothing; H opens, I, M, C and Tab nothing; Esc closes; then each of I, M, C, Tab opens its own page and Esc closes it; H opens and H closes.
- At a Level 2 choice (a snapshot with 10 Experience sent with `continue`): H opens nothing and the choice is still there (its screenshot shows only the level-up window); after 1 picks a stat, H opens the page.
- Every run: 0 console errors, 0 page errors, SMOKE: PASS.

**How to run it.** `npm.cmd run check` (142 files, 3225 tests; the base before this ticket, with ticket 30 merged, was 140 files and 3182). Focused: `npx.cmd vitest run tests/controls-page.test.ts tests/controls-list.test.ts tests/controls-list-layout.test.ts tests/page-hints.test.ts`. In a browser: `npm.cmd run dev`, start a New Game, press H.

**Left for the reviewer.** The play check in the last criterion (unticked: nobody played by hand, the smoke is a headless browser), above all pressing each key on the list and seeing that it does what its words say, and whether the words and the look read well. The sound of the page opening and closing was not listened to: it is the same events as the other pages, and the adapter picks the sound by event type. Not tested, as ADR 0005 says of drawing: `drawControlsList` and the overlay's drawing of the row; the screenshots are its check.

**Glossary.** "Controls page" (the page, opened with H, that lists every key of the game), and, with ticket 27's, "page" and "toggle", are used in the code and the README but are not in `GLOSSARY.md`; "page key" (a key that toggles a page) too. Proposed, not edited.
