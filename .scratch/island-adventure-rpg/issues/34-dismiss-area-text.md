# 34: Any key puts the text of an area away

**What to build:** When the hero comes into an Adventure Area for the first time, or reads a sign, its text shows under the HUD for about four seconds. After playing the third build the player asked that it go as soon as a key is pressed, instead of waiting out its time. The Game core gets one new command, `dismiss-area-text`, that ends the text that shows. The text is the game's state (it is in the view and in the saved game), so ending it is the core's, and what counts as a key is the adapter's: the play screen sends the command, ahead of the other commands of its frame, for the first key the player presses that is new, meaning not held when the text appeared, not an auto-repeat and not a Ctrl or Meta combination. The key still does its own job (a walk key walks, I opens the inventory). The text of a sign goes the same way, since a sign shows its text as an area does. Nothing else about the text changes: it shows once for each Adventure Area and again each time a sign is read, it still goes by itself after `areaTextMs` (4 seconds), it is hidden while the game waits, and the line that says H FOR CONTROLS (ticket 33) is not put away by a key.

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

**Spec stories:** 114

It returns no event. It works whether or not the game waits (a page is open, a Stat Point waits or the question whether to sail home is open), so that the text does not come back when the page closes: it is not held back by `isPaused`, as `move`, `stop` and `cancel-departure` are not. ## Comments

Added at the player's request after playing the third build. Among three notes the player wrote "when entering a new location: the description menu should dissapear when i press any button". Spec story 114 and the Menus bullets of the spec were written for it.

Decided with the player: any new key press puts the text away; walking, Esc and the text of a sign count; a key that was already held down when the text appeared does not; and the text still goes by itself after its four seconds. (The form that asked said so, and the player accepted it.)

Assumed, not decided with the player:

- That the text of a sign goes the same way. The player spoke of entering a new place; a sign shows its text as an area does (one state, one view field, one clock), so one rule is simpler than two.
- That the key is not swallowed. The press that puts the text away also does what it always did: a walk key walks, a page key opens its page.
- That the keys of the audio (N, - and +) and keys the game does not use count, as "any button" says. A Ctrl or Meta combination never does, as it never does for the other keys of the game (`isForTheGame`), so that a browser shortcut does not touch the game.
- That E at a sign whose text shows reads the sign again and shows its text afresh, and does not put it away: the dismissal goes first so that the key that reads a sign works. Any other key puts it away.
- That the line that says H FOR CONTROLS is not put away by a key. The player spoke of the description of a place, and the line has its own end (the Controls page).
- That the command is the core's and not the adapter's alone. The text is state, held in the view and in the saved game; hiding it in the adapter would let it come back after a page closes, or with a continued game. A command that clears the state is the smallest thing that cannot come back.

Not decided: a click or a touch (the game takes only the keyboard); whether a key should be able to bring the text back (it cannot; a sign can be read again).

For the implementer (the facts are from `integration/island-adventure-rpg` at ebed88e):

- The core. `enterArea` (`src/core/areas.ts` 47 to 63) sets `state.areaText = null` for what was shown in the area the hero leaves and, the first time the hero is in an area, `{ text, stepsLeft: content.areaTextSteps }`. `ageAreaText` (65 to 72) takes one step off in every step the game runs. `readSign` (`src/core/devices.ts` 85 to 88) sets the sign's text the same way and returns `sign-read`. The view's `areaText` is the text alone (`src/core/view.ts` 41, `src/core/interface.ts` 569). `step` returns at once while the game waits (`isPaused` in `src/core/pause.ts`), which is why the text freezes behind a page; the new command is not held back by it.
- `send` is a `switch` over the `Command` union (`src/core/game.ts` 34 to 93); the union starts at `src/core/interface.ts` 28, each member with its doc comment, and the last is `confirm-departure` (98). The switch is exhaustive, so a case that is missing is a type error.
- The saved game holds the text: `areaText` is `{ text, stepsLeft } | null` in `PlayState` (`src/core/state.ts` 199 to 225), copied by `copyState` and checked by `src/adapter/saved-game.ts` (497 to 499). The command changes a value that the format already has.
- The adapter. `PlayerInput` (`src/adapter/player-input.ts`) takes keys through `Keyboard<K>.addKey` only, and `GameScene.useKeyboard` (`src/adapter/game-scene.ts` 42 to 48) builds it with Phaser's `JustDown`; nothing sees "any key" today. A `KeyState` carries `originalEvent` (`{ repeat, ctrlKey, metaKey }`, line 21); `isForTheGame` (36) is the Ctrl and Meta rule, and `pressedAgain` (182) adds `repeat`. A `Key` that Phaser makes for a scene takes the first auto-repeat of a held key for a press (the comment at 178), which is why `repeat` must not count here either. Phaser's keyboard plugin (`this.input.keyboard`, which `useKeyboard` reads) emits `keydown` for every key with the browser's event: one way to see any key is to read those into a flag once a frame. `Keyboard<K>` is what the tests give a plain object, so an addition to it needs that object extended. The way is the implementer's.
- The frame. `PlayScene.update` (`src/adapter/play-scene.ts` from 157) starts with `pollAudioKeys`. The card (`holdForOpening`, which reads `pollMenu` and `pollActions` and throws the actions away) and a fall (`showFall`, the same) return early. The frame of the game then makes `send`, reads `viewAtStart`, and sends `pollWalking`, the inventory menu, `pollActions` and `departureAnswer` in that order, so the dismissal is the first thing sent, ahead of `pollWalking`. The steps run after the commands, so a text that appears in a frame (by an exit, or by the `interact` of the frame) is never put away by a press of that frame.
- The text of the start area is in the state from `new-game`, while the card shows (README, Area text): the frames of the card run no step, so its time starts when the card ends.
- The documents (lines approximate, at ebed88e): README 98 (the pause), 106 (Area text), 149 (the sentence on signs), and the lists of tests near 271 to 285; the checklist has no line for the text yet (the New Game lines are at 34 to 36).
- Tickets 34 and 36 both touch `src/adapter/play-scene.ts` and `src/adapter/player-input.ts`, the README and the checklist (ticket 36 makes Esc pause the game): whichever merges second takes the other's lines. When both are in, one Esc press puts the text away and pauses (the dismissal goes first, so that the text is gone when the player resumes): the reviewer of the second checks that. Ticket 35 does not touch these files.
