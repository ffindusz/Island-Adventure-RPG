# Island Adventure

A short top-down action RPG for desktop browsers, built with Phaser: a castaway crosses an island to sail home. The plan is in `.scratch/island-adventure-rpg/spec.md`, the vocabulary in `GLOSSARY.md`, and the decisions in `docs/adr/`.

## Run it

You need Node.js and npm. Install once with `npm install`; the dependency versions are pinned exactly.

| Command             | What it does                                                                     |
| ------------------- | -------------------------------------------------------------------------------- |
| `npm run dev`       | Starts the Vite dev server with hot reload. Open the URL it prints.              |
| `npm run build`     | Builds plain static files into `dist/`. Any static host will do; there is no server. |
| `npm run preview`   | Serves the `dist/` build locally.                                                |
| `npm run typecheck` | Type-checks twice: the core-only config first, then the whole project.           |
| `npm test`          | Runs the tests with Vitest: the Game core's, and the adapter's pure functions and shipped files (ADR 0005). No browser is needed.                      |
| `npm run check`     | Typecheck, then test, then build. It must pass before any change is merged.      |

To host the game, run `npm run build` and put the files of `dist/` on any static file server, at the root of a site or in a sub-folder of it: `vite.config.ts` has `base: './'`, so the page asks for its script, pictures and sounds by paths relative to itself, and nothing needs a server component. Every request uses the exact name of a file, so a host that tells upper and lower case apart (a Linux one) serves the game too, and the page gives its own icon inline so that no browser asks the host for a `favicon.ico`. Ticket 26 played the build from a plain Node file server, at the root and in `/some/place/`, from the title to the credits: every request was answered and the console stayed clean. `?debug` in the address bar works in the built game as well (see Looking at the running game, under Conventions), and exposes `window.gameCore` there. Two documents come with the game: `docs/balance.md`, the numbers of the adventure (Experience, fights, Gear, supplies, the Guardian and the play time) with how they were measured, and `docs/playtest-checklist.md`, a walk through the game for a first playthrough, with the assumptions that still wait for the player's word.

On Windows PowerShell, `npm` and `npx` can be blocked by the execution policy: use `npm.cmd` and `npx.cmd`.

## Controls

| Key                    | Action                                                                          |
| ---------------------- | ------------------------------------------------------------------------------- |
| W A S D or arrow keys  | Walk. The hero faces the direction pressed last.                                |
| Space                  | Attack with the weapon in hand, in the facing direction: the sword strikes, the bow shoots one arrow. One attack per press, then a short cooldown. |
| Q                      | Take the other weapon in hand, the sword or the bow. It takes no time. It does nothing until a bow is equipped. |
| C or Tab               | Open the stat page: Level, Experience, Health, Attack and Defense. Pressed again, either closes it. Tab is held back from the browser while the game has the keyboard, so that it does not move the focus away from the game. |
| I                      | Open the inventory: the Gear the hero carries and which pieces are equipped, the Ammunition and the Healing Potions, and the keys it holds. Pressed again, it closes it. |
| M                      | Open the Automap: every Adventure Area on the route, what the hero has discovered of each, where it is, and the exits it has found. Pressed again, it closes it. |
| H                      | Open the Controls page: every key of this table, each with what it does in a few words. Pressed again, it closes it. H opens it in play only: the title screen offers the same list from its Controls line. |
| E                       | Interact with what is right in front of the hero: open a chest or a cache, open a locked door with the key the hero holds, pull a lever, or read a sign, or use the vessel: the first press prepares it and the next asks whether to sail home. A loose pickup or a key needs no press: walk onto it. |
| Up, Down (or W, S)     | At the title: choose New Game, Continue or Controls. In the inventory: move along the list, the Gear and then the Healing Potion line below it. The hero does not turn. |
| Enter                  | At the title: choose the highlighted line, or replace the saved game when New Game asks. On Controls it shows the list of the controls, and Enter closes the list again. On the card of the opening: begin. In the inventory: equip the piece on the highlighted line, or use a Healing Potion on the potion line. At the question whether to sail home: sail home. On a card of the ending or the credits: turn to the next, and from the last, go to the title. |
| Esc                    | At the title: keep the saved game when New Game asks to replace it, and close the list of the controls. At the question whether to sail home: stay. Otherwise close the open page. Each page says at its foot which keys close it: its own key or Esc. |
| 1, 2, 3 (or keypad)    | At a level-up, put the Stat Point into Health, Attack or Defense. The choice is final. |
| N                      | Turn the sound off and on, the music and the effects together. It works on every screen and in every wait. |
| - and + (or keypad)    | Make the sound quieter or louder, one step of ten. Either turns a muted sound back on. They work on every screen and in every wait. |

The game opens on the title screen (see Saving, Continue and the title below), and a New Game goes on to the card of the opening (see The opening below). It waits on that card until Enter, while a page is open, while a level-up choice waits, while the question whether to sail home is open, and while the browser tab or window is not focused. Sailing home ends the game with the ending and the credits, and then the title (see The harbor and the ending below). The keys of the sound (N, - and +) work in all of these waits and on every screen, and are left alone with Ctrl or Meta held, so that the browser's own zoom keys still work (see Audio below). The keys of the pages (C, Tab, I, M and H) are left alone with Ctrl or Meta held as well, so that Ctrl+C still copies and Ctrl+Tab still switches the browser's tab, and a page key held down, or repeated by the keyboard, toggles its page once (see Pages and the pause below).

## Project layout

```
src/
  core/      The Game core: every gameplay rule, headless. Its public face is core/index.ts.
  content/   The game's content as plain data: terrain, hero, monsters, Gear, areas.
  adapter/   The Phaser adapter: keys to commands (the tables and labels of the keys, apart from Phaser, in controls.ts, and the list of them that the Controls page shows), the fixed-step loop, drawing, the art pipeline (asset manifest, loader and
             the hero's sprite), the HUD, the overlay, the Automap page, the inventory cursor and the notice (what was found,
             a Checkpoint touched, a door that is locked or opened, a lever pulled, the Guardian's gate that opened, that the vessel is ready, or that there is no Ammunition), the title scene (with the rules of its menu and the rows of its window, apart from Phaser, in title-menu.ts and title-window.ts), the card of the opening, the ending and the credits (the pages of them, and the scene that shows them), the autosave rule and the saved game's
             parser and store, and the audio (the manifest of its sounds, the service that plays them, and the settings and the line that show them). It holds no rules.
  main.ts    The composition root: builds the Game core from the content and starts the adapter with the browser's storage.
tests/       Vitest tests of the Game core's interface, of the adapter's pure functions and of the shipped files (docs/adr/0005), and fixtures.ts, a tiny arena to test in.
public/art/  The art pack's picture files that the game shows, each one listed in docs/assets/licences.md.
public/audio/ The audio pack's music (music/, .ogg) and effects (sfx/, .wav) that the game plays, each one listed in docs/assets/licences.md.
docs/adr/    Decision records.
docs/        balance.md, the balance of the adventure and how it was measured; playtest-checklist.md, the player's walk through
             the game with the assumptions that wait for their word; assets/, the licence record, the art inventory and the
             script that composes the art.
```

Dependencies point one way: `main.ts` uses the adapter, the content and the core; the adapter uses the core; the content imports only types from the core; the core imports nothing outside itself. Import the core through `core/index.ts`, never from the files behind it.

## Walking and the corner slide

- **Walking.** The hero walks one fixed step at a time (`walkHero` in `src/core/movement.ts`) and is stopped flush against whatever is in the way: solid terrain (rock, water, wreckage, trees), a chest, a lever, a sign, a vessel, a shut door, a shut gate and a living monster. `moveBody`, in the same file, does the stopping, and the monsters and the arrows move with it too. The real hero is 0.75 tile wide and walks 5 tiles a second, a step of 1/12 tile, so a passage one tile wide leaves it an eighth of a tile of room on each side.
- **The corner slide.** When a step of the hero is stopped by the corner of something that does not move, and the middle of its body is already over the gap beside it, the rest of the step slides it sideways the little that clears the corner, and the next steps go on in the direction it was walking (`slideRoundCorner`). So the crevice in the south wall of the coast's bay, the cabin's door in the woods and the cave's gate can be walked into a little off their middle, without lining the hero up.
- **What it goes round.** What stands still and stops a walker: solid terrain, and the interactables that are solid (a chest, a lever, a sign, a vessel, a shut door, a shut gate). A monster is never a corner, because it moves. A shut door or gate is a blocker as wide as the gap, so a hero in front of one has no corner to slide round.
- **When it helps.** Only when the shift that clears the corner is at most half the hero's width (`SLIDE_LIMIT`), which is when the middle of its body is over the gap. A hero whose middle is over the wall, the chest, the lever, the sign or the shut door is not helped: it stops flush against it as before, and a hero that walks head-on into one of them stays flush in front of it, so that Interact reaches it.
- **How it goes.** The slide spends only what is left of the step, so the hero never goes faster than it walks. It stops flush against anything solid, the living monsters too: a monster that stands in the way of the slide stops it and leaves the hero where it was, and no step ends with the hero overlapping any of them. The hero's facing is not changed.
- **Only the hero.** `moveBody` is as it was, so a monster whose body clips the corner of a passage is stopped as before. The slide has no state and no event: nothing of it is in the view or the snapshot or the save (`SNAPSHOT_VERSION` stays 4), and nothing in the picture or the sound shows it.
- **The tests.** `tests/corner-slide.test.ts` is at the Game core's interface, with numbers worked out by hand: the hero a little off the middle of the crevice of the coast's bay, and in a yard with each kind of thing on one tile (rock, water, a chest, a lever, a sign, a shut door, a shut gate), where it slides when its middle is over the gap, stays flush when its middle is over the thing, with Interact still reaching the thing, and is stopped by a monster that stands in the way of the slide. It also has the slide round a rock in each of the four directions (the facing is kept and no event is told), a step that arrives at the corner part of the way through, a biter that is not helped round the corner of a wall, the walks that no corner stops (as they were: along the key, a twelfth of a tile in a step), and seeded walks about a room full of things, where the hero never ends a step inside one of them or farther on than a step. A hero that no longer sticks to the chests does not come to a shot by chance, so the walks of `tests/saved-game-walks.test.ts` over its gauntlet begin with a scripted shot (the hero takes the Ammunition and the bow, equips it and shoots), and a hero's arrow in flight is saved every time.
- **The passages.** `tests/passages.test.ts` walks the real hero into the passages one tile wide of the real content, from every offset from the middle of the gap, half a tile either way in sixteenths, and wants its middle past the gap within a second. The two the player named are walked by place (the crevice of the coast's bay, and the cabin's door in the woods: shut, where the hero stays flush, then open, and then opened with the brass key), and every passage of the five areas is found from their maps and placed obstacles alone (a tile that is open with an open tile behind it and no open tile on either side, the doors and gates open: 98 at the time of writing) and walked into flush against its mouth and from the middle of the tile behind it. A passage added to the content is covered without a line in the test.

## Monsters, damage and defeat

- **Behaviors.** A monster type in `src/content/monsters.ts` names a `behavior` and gives the numbers that behavior needs; several types can share one. The behaviors are a small registry in `src/core/behaviors.ts`: `stationary` stands still, and `chaser` notices the hero, walks up, winds up a telegraphed attack, strikes, and rests before it can wind up again. To add a behavior, follow the three steps at the top of `behaviors.ts` (a definition plus a `loadMonsterType` case in `src/core/monster-content.ts` that checks its numbers, a step function, a registry entry); the compiler refuses one that misses a place. Two more, `charger` and `ranged`, are described under Chargers and ranged attackers below, and a fifth, `guardian`, under The Guardian.
- **A chaser's numbers** are monster type fields. Distances are in tiles from the monster's body, times are in milliseconds: `damage`, `speedTilesPerSecond`, `noticingDistance`, `reach`, `windUpMs` (at least one fixed step), `recoveryMs`, with `health` and `size`. The attack zone is the square around the body that `reach` describes. It is fixed when the wind-up starts and is in the view (`action` is `winding-up`, with `zone` and `progress`); the damage lands when the wind-up ends, and only if the hero overlaps the zone then. There is no line of sight and no pathfinding: a chaser walks straight at the hero and stops at what is in the way.
- **Hero numbers.** `health` (the maximum) and `defense` in `src/content/hero.ts`; `minimumDamage` (default 1) on the content itself. A hit takes off its damage minus Defense, never less than `minimumDamage`, which loading holds to 1 or more so that Defense can never take a hit away whole. Health never comes back by itself.
- **Defeat.** At 0 Health the core emits `hero-defeated` in that same step and `recoverHero` in `src/core/checkpoints.ts` puts the hero back at the Checkpoint it touched last (the start of the adventure before it has touched any) with full Health, and resets the monsters of that Checkpoint's Adventure Area to full Health at their starting places, defeated ones included; the other areas stay as they are (a Guardian is the exception, see The Guardian). `hurtHero` in `src/core/hero-damage.ts` is the one caller. Arrows in flight are removed too. The Ammunition and the Healing Potions go back to what the hero had at the Checkpoint, and the pickups and caches taken since are back; the Gear, the weapon in hand, the Experience, the Stat Points and the opened chests of Gear are left as they are. All of it is under Checkpoints below. The adapter fades the screen in when it sees the event.
- **HUD.** `src/adapter/hud.ts` draws the hero's Health (a heart, "current/maximum" and a bar), its Level, a bar of the Experience towards the next Level, the weapon in hand, the Ammunition and the Healing Potions, from the view and nothing else, fixed to the screen. It is a panel of the pack's art with pictures and the project's own bitmap font on it (see Art below). `HUD_WIDTH` and `HUD_HEIGHT` are a deliberate pair of numbers, 88 by 46 canvas pixels, so growing the HUD is a decision; `HUD_BOTTOM` is the canvas pixel row where its panel ends, and what is drawn below the HUD (the area text) follows it. The HUD covers the top left of the screen, so every Adventure Area, whatever its size, keeps that corner solid, so that the hero can never stand where it cannot be seen: `COVERED_CORNER` (6 by 3 tiles) in `src/core/covered-corner.ts`. `createGame` checks it for content that sets `checkCoveredCorner: true` (the shipped content does; the small arenas of the tests do not), refusing an area that has a walkable tile in it. The adapter's `checkHudFootprint` refuses to start the game when the HUD is bigger than that corner. **A new area must keep its top-left 6 by 3 tiles solid.** The shipwreck coast has water there, in rows 0 to 2.

## Experience, Levels and Stat Points

- **Experience.** Each monster type has an `experience` value (`src/content/monsters.ts`) that the hero earns every time it defeats one, a monster that a defeat reset included. A milestone is ground in an Adventure Area (`milestones`, in `src/content/areas/`) that gives its `reward` once: the first time the hero's body overlaps its `zone`, a block of whole tiles. That it was reached is kept with the area, so it survives a defeat and a snapshot. The reward is separate from the zone so that later rewards can sit beside Experience.
- **Levels.** `levelThresholds` in `src/content/progression.ts` is the total Experience for Level 2, Level 3 and so on. The highest Level is one more than the number of thresholds, so the five shipped give Level 6, and Experience past the last threshold is not counted. The Level is worked out from the Experience, never stored.
- **Stat Points.** The hero has one for each Level above 1, and `statPointValue` in the same file is what one adds to Health, Attack or Defense. The points not yet assigned are worked out too (the Level less 1, less those assigned), so there can be no more and no fewer than one per Level. A Health point raises the current Health by as much as the maximum. Every stat is worked out in `src/core/stats.ts`: no rule reads a base number from the content, and Gear adds its bonus there too (see below).
- **The numbers** are picked so that the way out of the shipwreck coast (two crabs on the way and the broken mast, 15 Experience) gives Level 2, and clearing the whole coast still leaves the hero short of Level 3. Each area goes on from there in the same way: a hero who fights what it meets on the trail has the next Level by the way out (Level 3 by the woods' exit, Level 4 by the mountain's, Level 5 by the cave's), and one who clears every area up to and including it is still short of the Level after. The castle ends the climb: a hero who fights what it meets on the way to the end of its route has Level 6, four Experience to spare. The Guardian beyond the castle gives 30 more: a hero who comes to it with 70 Experience is Level 6 once it falls, while one who fought the whole route has the most that is counted already, so for that hero the 30 adds nothing. The balance pass (ticket 26) checked each of these totals against the thresholds and changed none of them: `tests/route-experience.test.ts` pins them, and `docs/balance.md` has the table, with the monsters and the Experience of the route of each area.
- **Events** `experience-gained`, `level-up` (one for each Level reached) and `milestone-reached` are for presentation. The view's `levelUp` is the truth about a choice that waits.

## Pages and the pause

- **A page** is shown over the game, one at a time: the stat page, the inventory, the Automap and the Controls page. Which page is open is core state (`page`: a page id, or none), changed by the `open-page`, `close-page` and `toggle-page` commands; the view's `page` holds what to draw. `toggle-page` is what a page key sends (`togglePage` in `src/core/pages.ts`): it closes the page when it is the one that is open, in every state in which `close-page` does, and otherwise opens it as `open-page` does. Which of the two a key does is a rule of the core, so the adapter never reads the view to choose; `open-page` on the page that is open stays ignored, and never closes it. A snapshot taken with a page open restores it open, and its own key closes it.
- **The Controls page** (H) lists every key the game answers to, each with what it does in a few words, and says how to close itself. For the core it is a page like the other three, with nothing to show for it but that it is open (the view's page is `{ id: 'controls' }`), because the core knows no keys. What it lists is the adapter's: `controlsList` in `src/adapter/controls.ts` is a pure function of one table, `controlsTable`, that holds beside each line's keys what they do and what each key is for in the start-up check of the keys (`checkAudioKeys`), so that a key changed or added in the tables changes the page and is checked. `layoutControlsList` and `drawControlsList` in `src/adapter/controls-list.ts` lay it out in two columns, the keys at the right of theirs, and draw it, and know nothing of the window it goes in: the overlay puts it in a window as wide as it is, and the title screen draws it in one of its own, from its Controls line (see Saving, Continue and the title); the title does not read H, which opens the page in play only. Its words use only what the pixel font draws. `SNAPSHOT_VERSION` stays 4: a page that is open is saved as its id, so a new id changes nothing of the saved shape, and a save made before the Controls page still loads.
- **To add a page,** add its id to `PAGE_IDS` in `src/core/state.ts`. The compiler then points at what is missing: the page's view in `src/core/interface.ts` and `src/core/view.ts`, its keys in `PAGE_KEYS` in `src/adapter/controls.ts` (a name for Phaser, a label for the player, and whether Phaser holds the key back from the browser: the first key is the one a notice names, and all of them are named in the hint at the page's foot), its words in `PAGE_WORDS` there (what its line on the Controls page says) and its drawing in `src/adapter/overlay.ts`. The Automap is the exception: it has a class of its own, `src/adapter/automap-page.ts`, so its case in the overlay draws nothing.
- **The hint at the foot of a page** says which keys close it: its own key or keys, then Esc (`C/TAB OR ESC TO CLOSE` on the stat page, `I OR ESC TO CLOSE` on the inventory, `M OR ESC TO CLOSE` on the Automap, `H OR ESC TO CLOSE` on the Controls page). `pageCloseHint` in `src/adapter/controls.ts` builds it from the same `PAGE_KEYS` table that binds the keys, so a key that is changed changes the hint, and the overlay and the Automap both use it. A line of text on the overlay is drawn as it is given, centred, and nothing cuts it, so a hint wider than the room of its window runs over the window's edges: the stat page has room for 22 letters of the pixel font, and that is why its two keys go side by side with a slash. `ESC TO STAY`, at the question whether to sail home, and `ESC TO KEEP IT`, on the title, are not hints of a page and name only Esc. The list of the controls that the title shows has a foot of its own, `ESC OR ENTER TO CLOSE`, made from the same labels of the keys: the title does not read H, so it does not name it.
- **The pause.** The game waits while a page is open, a Stat Point waits to be assigned or the question whether to sail home is open (`isPaused` in `src/core/pause.ts`): `step` advances nothing, `attack`, `interact` and `switch-weapon` do nothing, and `open-page` and `toggle-page` open nothing, so a page is closed before another opens: the key of another page does nothing while a page is open. `move` and `stop` still keep track of the keys that are down, so the hero does not walk on by itself afterwards. They also turn the hero, so the adapter holds back the walking keys while the game waits, and sends the ones that are down when it stops waiting: the arrow keys of a menu do not turn the hero, and a key held through a page walks on when the page closes. The level-up choice cannot be closed. Several at once are asked one after another, the lowest Level first.
- **An unfocused tab** is the adapter's business, not the core's. `FixedStepClock` in `src/adapter/fixed-step.ts` is told every frame whether the player is watching (`document.hasFocus()` and the tab not hidden, read in `play-scene.ts`). While nobody is, it runs no steps and forgets the time that passed, so the game does not rush to catch up. `tests/fixed-step.test.ts` pins the clock; reading the focus is the scene's and is not tested.
- **The overlay.** `src/adapter/overlay.ts` draws the level-up choice, the open page and a PAUSED notice from the view, in windows over the dimmed game: the pack's orange frame round a dark panel, with an icon on each line of Gear and each consumable, the cursor's line on the pack's orange button, and a tick behind the Gear that is equipped. The inventory has two columns, the Gear on the left and, on the right, the Ammunition, the Healing Potions, the keys the hero holds (two at a time, then a count of the rest) and the stats. Its text uses the bitmap font, which has the capital letters, the digits and a few signs: add a glyph to `pixel-font.ts` before using a new character. A name that is too long for its line is cut off at the end without a word, so the name of a piece of Gear keeps to `LONGEST_GEAR_NAME` characters (11, worked out from the layout beside a bonus of one digit), and `tests/gear-names.test.ts` checks that every piece of Gear in the content does, and has a bonus of one digit.

## Connected areas and the camera

- **Areas are joined by data.** An area in `src/content/areas/` lists its `entrances` (an `id` and the `tile` the hero stands on when it arrives) and its `exits` (an `id`, a `zone` of whole tiles inside the map, and `to: { area, entrance }`). When the hero's body overlaps an exit's zone, the core emits `area-changed` and puts the hero at the centre of the entrance tile; the way it faces and the keys held carry on. Loading refuses an area with no entrance, an exit to an area or an entrance that does not exist, an exit to an area that has no exit back, an entrance on solid ground or inside an exit zone of its own area (it would send the hero straight back), and an id used twice. To add an area, write its file in `src/content/areas/`, add it to `areas` in `src/content/index.ts`, and give it an exit each way: no rule changes. The shipwreck coast (`shipwreck-coast.ts`, 40 by 18 tiles), the woods (`woods.ts`, 48 by 28 tiles), the mountain (`mountain.ts`, 44 by 30 tiles), the cave (`cave.ts`, 48 by 34 tiles) and the castle (`castle.ts`, 92 by 30 tiles: its route, then the gateway to the Guardian, the arena and the harbor behind the gate) are joined this way, in that order on the route.
- **Every area keeps what happened in it:** monsters defeated or hurt, chests and Ammunition caches opened, milestones reached. The monsters of the area the hero leaves are calmed (idle, with their place and Health kept), and nothing in an area moves while the hero is away. The hero's arrows in the air are removed when it goes through an exit (`crossExits` in `src/core/areas.ts`); they fly their last step first, so one that reaches a monster on that step still hits, and the Ammunition spent on them is not given back. A defeat resets only the monsters of the area of the Checkpoint it returns the hero to, which can be another area than the one where the hero fell (see Checkpoints below).
- **Area text.** An area's optional `text` is shown the first time the hero comes into it, and the start area's as the game begins (after the card of the opening, if there is one: no step runs while it shows, so the text's time starts when it ends); `areaTextMs` (content, default 4000) is how long. The core times it: the view's `areaText` holds it while it shows, the `area-text` event announces it, a page or a Stat Point that waits freezes its clock, and it never comes back on a later visit. It does not pause the game. `src/adapter/area-banner.ts` draws it under the HUD, starting a few pixels below `HUD_BOTTOM` (see the HUD above), with the bitmap font, so write it with letters, digits and `/ + - : . !` only.
- **The camera** (`src/adapter/camera.ts`) follows the hero in whole pixels and stops at the area's edges, so there is no empty space beyond the map. The canvas is 20 by 12 tiles (`VIEW_TILES_*` in `src/adapter/config.ts`): the coast, the woods, the mountain and the cave are larger and scroll, and an area smaller than the canvas sits in the middle with black around it. The HUD, the area text, the notice and the overlay stay fixed to the screen. Exits are marked by chevrons painted on the ground, one to a tile and pointing to the nearest edge of the area (`src/adapter/prop-sprites.ts`), and the screen fades in briefly when the hero comes into another area. The core's interface has nothing for the camera.
- **The tests.** `tests/area-connections.test.ts` pins the rules on fixtures, the arrows in the air and the Ammunition caches among them; `tests/shipped-areas.test.ts` checks the real areas (they join both ways, the woods are larger than the canvas, the hero walks from the coast into the woods, on into the mountain, the cave and the castle, and back, every tile that is not solid can be reached, a chest being solid like rock and with room beside it, nothing lies on an entrance, the covered corner is checked, and no monster notices the hero where it arrives); `tests/camera.test.ts` and `tests/area-banner.test.ts` cover the pure parts of the adapter.

## Gear, the inventory and chests

- **Gear** is content (`src/content/gear.ts`): each piece has an id, a `name`, a `slot` and a `bonus`. A slot raises one stat (`GEAR_SLOT_STAT` in `src/core/definitions.ts`): a melee weapon or a ranged weapon adds to Attack, armor to Defense, and Gear changes nothing else. The hero begins with a basic sword and basic armor (`startingGear` in `src/content/hero.ts`), both with a bonus of 0 so that the base numbers stand. The shipped upgrades, each at least a fifth more Attack or Defense than the piece below it in its slot (or than having none) at the Level where the hero finds it, which the balance pass checked (`docs/balance.md`, "The Gear"): the Steel Sword and the Chain Mail add 1, the Plate Armor that the hero finds in the mountain adds 2, the Knight Mail that the hero finds in the armory of the castle adds 3, the Katana that the hero finds behind the gate of the cave is a sword that adds 2, and the Long Bow, the only bow of the game, adds 2: it lies in the chest of the cabin in the woods, behind a locked door whose key is in the north woods, so that the route itself gives the hero no bow.
- **Carrying and equipping.** The hero carries every piece it finds, with no limit, and has one equipped in each slot. Each piece exists once: the content is refused if two places give the same piece, whether they are two chests, or a chest and the starting Gear. No monster gives Gear. There is no unequip, only a swap for another piece of the same slot. `src/core/stats.ts` adds the bonuses of the equipped pieces to Attack and Defense after the Stat Points, so the stat page, the damage of an attack and the damage the hero takes all follow. A weapon's bonus counts only for the attacks made with it, the sword's for strikes and the bow's for arrows, so the stat page and the inventory show the Attack of the weapon in hand.
- **To add a slot** (a helmet, say), add it to `GEAR_SLOTS` and to `GEAR_SLOT_STAT` in `src/core/definitions.ts`; the compiler refuses a slot that is missing from the map. A slot that holds a weapon is a `WEAPON_SLOTS` entry too, and `heroAttacks` and `switchWeapon` in `src/core/weapons.ts` then say how it attacks and how it is taken in hand.
- **The inventory** is a page, `inventory`. Its view lists the carried Gear, by slot and then in the order found, each with whether it is equipped, the Attack and Defense totals, how many of each consumable the hero has (the Ammunition and the Healing Potions) and the keys it holds, in the order it took them (`keys`, see Light puzzles and clues). The `equip` command takes a piece's id and works only while the inventory is open; it does nothing for a piece the hero does not carry or already has equipped. Choosing the piece is the adapter's job: `src/adapter/inventory-menu.ts` keeps the cursor (Up and Down, or W and S, without wrapping; it runs over the Gear, five lines showing at a time, and then to the Healing Potion line below), Enter sends `equip` for a Gear line and `use-healing-potion` for the potion line (see below), and Esc closes the page. The page shows the hero's Health too, so that what a potion did can be seen.
- **Chests** are interactables: things in an Adventure Area that the hero acts on with E (the `interact` command), listed in the area's `interactables` (the shipwreck coast's are in `src/content/areas/shipwreck-coast.ts`). A chest has an id, a tile and its contents, a tagged union: `{ kind: 'gear', gear: <id> }`, or `{ kind: 'consumable', consumable: <id>, amount: <n> }` for a cache, a chest of a consumable (see below). Interact acts on the nearest interactable in the ground right in front of the hero, as far as `interactionReach` (`src/content/hero.ts`) and as wide as the hero's body; when two are as near, the one listed first. It does nothing while the game waits. A chest opens once: the hero picks up what is inside, and the core emits `chest-opened` and `pickup`. That a chest was opened is kept per Adventure Area in the state, so it survives a snapshot, and a defeat too when it holds Gear (a cache is closed again by a defeat that goes back to before it was opened: see Checkpoints). Chests are solid, opened or not.
- **To add a kind of interactable** (the devices of the light puzzles were added this way), follow the steps at the top of `src/core/interactables.ts`: a definition, a state, a function that says what it does, and an entry in the `INTERACTIONS` registry. The compiler refuses a kind that is missing from the registry or from the views.
- **The notice.** The adapter shows one notice at a time for a few seconds (`src/adapter/notice.ts`), the latest of these: a `pickup` (what was found, what it adds, and a hint to press I; for a key, that it opens a door), `out-of-ammunition` (see below), `checkpoint` (see Checkpoints), `door-locked`, `door-opened` and `lever-toggled` (see Light puzzles and clues), `gate-opened` (see The Guardian) and `save-failed` (see Saving, Continue and the title). A page or a Stat Point that opens covers the notice that was showing and ends it, and so does a defeat. What the very frame that opens the wait told is kept: when a defeat leaves a Healing Potion and raises the Level in the same step, `Feedback.setWaiting` holds the notice, off the screen and with its time stopped, and it shows for its whole time once the point is assigned (`tests/feedback.test.ts`). A new kind of find needs its lines in `pickupLines` there, and its picture in `iconFor`. A `pickup` also lifts its picture over the hero for half a second, apart from the notice (see Healing Potions and pickups). Chests, caches, pickups, keys, doors, gates, levers, signs and Checkpoints are drawn by `src/adapter/prop-sprites.ts` (see Art).

## The bow, Ammunition and drops

- **Two weapons, one in hand.** The sword is in the melee weapon slot and a bow, once found and equipped, in the ranged weapon slot. The weapon in hand (`activeWeapon`, one of those two slots, in the hero's view) starts as the sword. Q sends `switch-weapon`: the sword to the bow and back. The bow can be taken in hand only while one is equipped, and the sword is always there to go back to. Switching takes no time, leaves the cooldown alone and does nothing while the game waits; equipping a bow does not take it in hand. `attack` goes through `heroAttacks` in `src/core/weapons.ts`: a strike with the sword, a shot with the bow. Both wait for the same attack cooldown and start it, and nothing is spent but the Ammunition.
- **A shot** costs one Ammunition and sends an arrow from the hero's centre in the direction it faces (`hero-shot`). With none left nothing is shot and the cooldown does not start: the core emits `out-of-ammunition` (once the cooldown is over), and the adapter's notice says so and hints at Q. The numbers are `rangedWeapon` in `src/content/hero.ts`: `arrowSpeedTilesPerSecond`, `range` (the tiles an arrow flies before it is gone) and `arrowSize`, at most the hero's size.
- **Arrows** are state: each has its Adventure Area, position, direction and the range it has left, and the view's `arrows` gives the position, direction and size to draw. `flyArrows` in `src/core/arrows.ts` moves them each fixed step, after the hero walks and before the monsters act. An arrow hurts the first living monster it reaches (a monster that walks into one is hit too) and is gone; solid terrain and chests stop it, and so does a spent range. The damage is the Attack of the bow (base, Stat Points and the bow's bonus), worked out when the arrow arrives. Arrows wait while the game waits and fly only in the Adventure Area they were shot in; a defeat removes them, and so does the hero going through an exit.
- **Ammunition is a consumable.** The hero's `consumables` count each kind (`CONSUMABLE_IDS` in `src/core/definitions.ts`: there are two, `ammunition` and `healing-potion`, and the hero starts with none of either), and `grantConsumable` in `src/core/consumables.ts` is the one way to give some. To add a kind, add its id there and follow the compiler to its starting count (`src/core/state.ts`), its name (`src/adapter/labels.ts`) and its look as a cache and as a pickup (a frame of `prop-chest` and of `prop-pickup`, chosen in `src/adapter/prop-sprites.ts`; the sheets are made by `docs/assets/compose-art.py`).
- **Caches.** A cache is a chest whose contents are a consumable, `{ kind: 'consumable', consumable: 'ammunition', amount: 6 }`. It opens once like any chest, and the hero takes the amount (`pickup`). The chest in the view says what it holds (`holds`: `'gear'` or the consumable's id), which is how the adapter draws a crate of arrows. The two caches of six stand along the sand trail of the woods (`arrow-cache-1` and `arrow-cache-2` in `src/content/areas/woods.ts`): the coast has none, because the bow belongs in the woods, and a hero who finds arrows and has no bow has a reason to look for the Long Bow of the cabin (see Gear, the inventory and chests). The mountain has two more of six a few steps off its trail (`mountain-arrow-cache-1` and `mountain-arrow-cache-2` in `src/content/areas/mountain.ts`) and a cache of eight at the end of its side path. The cave has three of six a few steps off its trail (`cave-arrow-cache-1` to `cave-arrow-cache-3` in `src/content/areas/cave.ts`) and a cache of eight in the grotto at the end of its side path. The castle has three of six a few steps off its route (`castle-arrow-cache-1` to `castle-arrow-cache-3` in `src/content/areas/castle.ts`), the last of them past the knight, and a cache of eight at the end of each of its two side paths.
- **Drops.** A monster type can have a `drops` table (`src/content/monsters.ts`), a list of `{ consumable, chance, amount }` with `chance` from 0 to 1. When the hero defeats a monster, with a strike or an arrow alike, `rollDrops` in `src/core/drops.ts` rolls each entry once, in order, with the game's `random` option, which the rules use for nothing else. An entry drops when its roll is below its `chance` (so 0 never drops and 1 always does), and the roll is made whatever the chance is, so retuning one does not shift the rolls after it. What drops goes straight into the hero's count, with a `pickup` event: nothing lies on the ground. A type without a table asks for no roll. The crab leaves a Healing Potion about one time in seven (15 in 100) and no arrows: it meets a hero who has no bow yet. The spitter, which shoots them, leaves 2 arrows one time in four. The balance pass does not count on any drop to keep a hero supplied, and changed none of them (`docs/balance.md`, "The supplies").

## Chargers and ranged attackers

- **Two more behaviors,** `charger` and `ranged`, sit in the registry beside `chaser` and are data in the same way: a monster type names the behavior and gives its numbers, so a tougher or faster variant is another type in `src/content/monsters.ts` and no rule changes. The shipped ones are `boar` (a charger) and `spitter` (a ranged attacker); the woods have one of each beside their wolves and slimes, and the coast, which teaches the controls, has crabs only. The raiders of the mountain are four more types of those behaviors, tougher than the beasts of the woods: `raider` and `raider-veteran` (chasers), `raider-charger` (a charger) and `raider-archer` (a ranged attacker). The veteran is the tougher variant, 12 Health against 5 or less, with a heavier hand and a Healing Potion that it sometimes drops; it holds the shaft below the summit, and five raiders watch the sand trail while a sixth guards the side path. The creatures of the cave are four more types, the cave's own: `cave-bat` (a chaser, frail and quicker than any other), `cave-lizard` (a charger), `cave-eye` (a ranged attacker that does not move and carries the arrows it shoots) and `cave-bear`, the tougher variant, 14 Health against 6 or less, with a hit of 9 and a Healing Potion that it sometimes drops. The bear holds the chamber before the way on, and the second lizard guards the grotto at the end of the side path. The undead of the castle are four more types: `castle-skeleton` (a chaser), `castle-ghoul` (a charger), `castle-wraith` (a ranged attacker that keeps its distance and sometimes drops arrows) and `castle-knight`, the tougher variant, 20 Health against 8 or less, with a hit of 10 and a Healing Potion that it sometimes drops. The knight holds the great hall, before the way on, and a wraith and a ghoul guard the two side paths. The wolf and the slime are variants of the chaser in the same file and need no rule: the wolf is frail and quick (quicker than a crab, slower than the hero) and the slime is slow and sturdy, with a lighter bite. The balance pass changed three numbers, all damage, so that a hero who never dodges loses less than half its Health to a charger on the way: the raider-charger's and the cave-lizard's went from 7 to 6, and the castle-ghoul's from 9 to 7 (`docs/balance.md`, "What was tuned"). Loading refuses a type whose numbers cannot work and names the type and the field, for example a Health or a size that is not more than 0 (whatever the behavior), a damage, reach, dash speed or dash range that is not more than 0, a wind-up shorter than one fixed step, a speed, noticing distance, recovery or Experience below 0, and a projectile bigger than its shooter. It holds every number of the hero to the same: a size, a speed, a Health, an interaction reach, a Melee Weapon reach or width, and an arrow's speed, range or size that is not more than 0 (an arrow no bigger than the hero), and an Attack, a Defense or an attack cooldown below 0 (a cooldown of 0 is allowed: the hero then strikes at every step). The `minimumDamage` of the content is held to 1 or more, whatever the hero's Defense.
- **A charger** (`src/core/charger.ts`) notices the hero as a chaser does, then works out its lane (`src/core/lanes.ts`): the strip in front of its body, toward the hero along the axis they are farther apart on, as wide as the body and `dashRange` long, cut short by solid terrain and chests. If the hero's body overlaps the lane it winds up with the lane fixed in the view as the telegraph (`winding-up`, whose `zone` is the lane); if not it walks sideways at `speedTilesPerSecond` until the lane takes the hero in, then toward it (a speed of 0 makes it wait for the hero to step in). When the wind-up ends it dashes down that lane at `dashSpeedTilesPerSecond` (`dashing` in the view) whether or not the hero is still in it, and `monster-attacked` gives the lane as its zone. The dash hurts the hero once, for `damage`, only if the hero is in its way, and is stopped by the hero, solid terrain, a chest, another monster or the end of the lane. Then it recovers for `recoveryMs`, standing still, and can be hit freely: no hit interrupts a wind-up or a dash. Its numbers are `noticingDistance`, `speedTilesPerSecond`, `windUpMs`, `dashSpeedTilesPerSecond`, `dashRange`, `recoveryMs` and `damage`, with `health` and `size`.
- **A ranged attacker** (`src/core/ranged.ts`) notices the hero and, if its type has `keepsDistance: { preferredDistance, speedTilesPerSecond }`, walks to `preferredDistance` tiles from it (the gap between their bodies, along the axis they are farther apart on), backing away when it is nearer and winding up where it stands once a wall leaves it nowhere to go; without `keepsDistance` it stands still. It winds up for `windUpMs`, then fires one projectile from its centre along the row or column toward where the hero stands at that moment (the axis the hero is farther along, a tie going horizontal), emits `monster-fired` and recovers for `recoveryMs`. It aims when it fires, so its `winding-up` has no lane to show: its `zone` is its own body, and the adapter flashes it. A hero that has left that row and column by then is missed. Its numbers are `noticingDistance`, `windUpMs`, `recoveryMs`, `projectile: { damage, speedTilesPerSecond, range, size }` and the optional `keepsDistance`, with `health` and `size`.
- **A monster's projectile is an arrow.** It is an arrow in the state with a `shotBy` (the monster and its type, so that it flies on when its shooter is defeated), moved by the same `flyArrows` as the hero's, in the same place in the step. It flies `range` tiles at `speedTilesPerSecond`, is stopped by solid terrain and chests, passes through monsters, and hurts the hero through `hurtHero`, so Defense, `hero-hit` and defeat work as for any hit. The view's `arrows` say who shot each one (`shooter`: `'hero'` or `'monster'`), and the adapter draws a monster's as an orb with a trail (`ProjectileSprites` in `src/adapter/projectile-sprites.ts`), apart from the hero's arrows. A hero defeated by a projectile ends the step there and loses every arrow in flight, as a defeat always does (see the guard after `flyArrows` in `src/core/game.ts`). A Checkpoint the hero came onto in that step was activated before the hit, so the guard reports its `checkpoint-activated` too, and the hero is back on it: a defeat ends the same way whether a bite, a dash or a projectile caused it.
- **No attack is unavoidable.** The charger's lane shows for the whole wind-up and the dash begins only after it, so stepping out of the lane in that time avoids it. The ranged attacker's projectile goes along one row or column and is slower than the hero's walk, so leaving that row and column before the shot, or sidestepping the projectile, avoids it. `tests/shipped-enemies.test.ts` keeps the shipped types that way and keeps both out of the notice of every entrance, the start and every Checkpoint, so the hero never arrives into an attack.
- **The tests.** `tests/enemy-fixtures.ts` is the arena for these suites: `CHARGER`, `SHOOTER`, `KEEPER`, `HEAVY` and `SNIPER` are types to place with `chargerAt`, `shooterAt` and `keeperAt`. `charger.test.ts`, `charger-lining-up.test.ts` and `charger-avoidance.test.ts` cover the wind-up, the lane, the dash, the stop at terrain, the hit and the recovery; `ranged-attacker.test.ts`, `ranged-keeping-distance.test.ts`, `projectile.test.ts` and `ranged-avoidance.test.ts` the same for the ranged attacker and its projectile; `enemy-content.test.ts` that bad numbers are refused and that a variant is data only; `shipped-enemies.test.ts` the real areas; `checkpoint-enemies.test.ts` the two tickets together: a hero defeated by a bite, a dash or a projectile is put back alike, in the area of the Checkpoint or in another, with no wind-up, lane, dash, recovery or projectile of the life before left to hit it, and a lane or a shot over a Checkpoint activates nothing.

## Healing Potions and pickups

- **Healing Potions** are a consumable (`healing-potion`, see above) and the only way the hero gets Health back between Checkpoints: Health never comes back by itself, and a potion is never used on the hero's behalf. The hero finds them three ways: in a chest or cache (`{ kind: 'consumable', consumable: 'healing-potion', amount: 2 }`), lying on the ground as a pickup, and in a monster's `drops` table. The shipwreck coast has a chest of two (`potion-chest`) under the hull of the wreck and a single potion (`beach-potion`) on the beach below it, both a short walk from the start; the woods have a single potion lying on the trail (`woods-potion`) and a chest of two (`woods-potion-chest`) a short walk off it, in the north; the mountain has two on the ground a step off its trail (`mountain-potion-1` and `mountain-potion-2`) and a chest of three at the end of its side path (`mountain-overlook-potions`); the cave has two on the ground a few steps off its trail (`cave-potion-1` and `cave-potion-2`) and a chest of three in the grotto at the end of its side path (`cave-grotto-potions`); the castle has three on the ground a step or two off its route (`castle-potion-1` to `castle-potion-3`, the last past the knight) and a chest of two and a chest of three at the ends of its side paths (`tower-potion-chest` and `crypt-potion-chest`); the crab drops one 15 times in 100, the veteran of the mountain one time in two, the bear of the cave one time in two, and the knight of the castle one time in two. The balance pass counted the potions near the route against what the fights take: a hero that puts its points on Attack or on a split is never short, and one that puts them all on Health is short in the castle unless it goes for the potions that lie further off. It changed none of them (`docs/balance.md`, "The supplies").
- **Pickups** are interactables of the kind `pickup`, `{ kind: 'pickup', id, tile, consumable, amount }`: some of a consumable lying on a tile. The hero takes it by walking onto it, with no key to press: `collectPickups` in `src/core/pickups.ts` runs in every fixed step right after the hero has walked, takes each pickup its body overlaps that it has not taken, and emits `pickup`. It is taken once, until a defeat that goes back to before it was taken (see Checkpoints); that is kept per Adventure Area in the state, so it survives a snapshot. A pickup is not solid, so the hero, the monsters and the arrows pass over it, and the view's `interactables` list it only while it lies there. The content is refused for a pickup of an unknown consumable, with an amount that is not a whole number of 1 or more, on a tile that is not walkable, or where something else is placed or starts.
- **Using a potion** is the `use-healing-potion` command, which works only while the inventory page is open (`useHealingPotion` in `src/core/potions.ts`). It gives back `healingPotion.restores` (`src/content/healing-potion.ts`: 5 for now, half of the starting Health), never above the hero's maximum Health as it is then, Stat Points counted. The potion is used up even when less than that fits. With none, or at full Health where it would be wasted, nothing happens and there is no event. A use emits `healing-potion-used` with the Health `restored` and the `health` now. `createGame` refuses content whose `restores` is not more than 0.
- **In the adapter.** The HUD shows the potion count beside the Ammunition count, grey at 0. The inventory page gives the potions a line of their own below the Gear, with the Health under it. Down moves the cursor onto that line, Enter there sends `use-healing-potion`, and the page stays open, so Enter again uses the next potion until the Health is full or the potions are gone. A refused use is not explained: the count and the Health line show why. Pickups and potion chests are drawn by `src/adapter/prop-sprites.ts`: the pack's bottle lying on the ground, and a crate with two bottles in it that is empty once opened.
- **What a find does in the picture.** A `pickup` also lifts the picture of what was found, its own icon (`pickupIcon` in `src/adapter/notice.ts`), over the hero's head for half a second (`PICKUP_RISE_MS` in `src/adapter/feedback.ts`), whether it came from a chest, a cache, a key, a pickup walked onto or a monster's drop. It rises 12 pixels, slowing as it goes, stays whole for the first two fifths of the time, fades out for the rest, and follows the hero. It is drawn at `DEPTH.pickupRise`, above the strikes and under the HUD and the notice, and the notice is as it was. Two finds within half a second stand side by side in lanes 18 pixels apart, so that neither hides the other, and a defeat ends them with the notice. `Feedback.pickupRises` works out how far through each is and which lane it takes, `placementOf` in `src/adapter/pickup-rise-sprites.ts` the pixels, and `PickupRiseSprites` there is only the part that talks to Phaser. `tests/feedback.test.ts` and `tests/pickup-rise-sprites.test.ts` pin the time and the pixels with numbers worked out by hand. Not tested automatically: how it looks. Look at it in a browser with `npm run dev` and `?debug`: stand the hero below a chest or an Ammunition cache with `gameCore` and press E, and walk onto a potion.
- **Defeat** gives the potions back as they were at the Checkpoint it returns to, and puts the pickups, caches and chests of potions that were taken since back where they were (see Checkpoints below).

## Light puzzles and clues

- **Six kinds of interactable, all data.** Keys that open doors, levers that move gates and signs that give a clue are optional: the way along the route never needs one. The sixth, the vessel, is where the game ends (see The harbor and the ending). They are listed in an area's `interactables` beside the chests, and their rules are in `src/core/devices.ts` (a key here is the item the hero carries, not a key of the keyboard). A `key` (`{ kind: 'key', id, tile, name }`) lies on its tile and the hero takes it by walking onto it: `collectKeys` runs in the step right after `collectPickups`, puts its id in the hero's `keys` and emits `pickup` with an item of the kind `key`. A `door` (`{ kind: 'door', id, tile, key }`) is solid while shut. Interact on it with its key in hand opens it for good, the door takes the key and the core emits `door-opened`; without the key nothing changes and the core emits `door-locked`, with the name of the key to look for. A `gate` (`{ kind: 'gate', id, tile }`) is solid while shut, begins shut and does nothing for Interact: only a lever moves it, except a gate with `opensWhenDefeated` (the id of a Guardian of its own area), which no lever may name and which opens for good in the step that Guardian falls (see The Guardian). A `lever` (`{ kind: 'lever', id, tile, targets }`) is always solid. Interact flips its `pulled` and moves every door and gate it names the other way, so a shut one opens and an open one shuts (`lever-toggled`); a door that a lever opens takes no key. A `sign` (`{ kind: 'sign', id, tile, text }`) is always solid. Interact shows its text as the text of an area is shown (the view's `areaText`, for `areaTextMs`, in place of any text showing) and emits `sign-read`: the game does not pause, and a sign has no state. A `vessel` (`{ kind: 'vessel', id, tile }`) is always solid, and Interact on it prepares it and then asks the question whether to sail home (see The harbor and the ending).
- **One-time loot, not a consumable.** A key taken, a door opened, a gate opened and a lever pulled stay as the hero left them when it is defeated (`consumable-rollback.ts` leaves them alone), when it goes through an exit and comes back, and in a saved game: the flags (`collected`, `open`, `pulled`) are in each area's state and the keys held are the hero's `keys`, so all of it is in the snapshot, which is why `SNAPSHOT_VERSION` was raised to 2 (it is 4 now: the Guardian's rotation made it 3, and the question whether to sail home made it 4). A key that a door has taken stays taken, so it never lies on the ground again. `parseSave` refuses a snapshot whose hero holds a key that its area still has lying there (`damaged`). It refuses too, as `damaged`, a snapshot in which a vessel is prepared while a Guardian whose gate is in its area has not fallen (the harbor is out of reach until then), and one in which the question whether to sail home is open about a vessel that is not prepared or that is not in the area the hero is in; a prepared vessel with no question open, even with the hero in another area, is an ordinary save. A New Game builds it all fresh: no key held, every door and gate shut, every lever not pulled.
- **What loading refuses.** The message names the area and the device (`src/core/device-content.ts`): a key with no name, a sign with no text, a lever that moves nothing, names a target twice or names one that is not a door or a gate of its own area, a door whose key no area places, a key that no door needs and a key that two doors need. As for any interactable, a device on solid ground, or on the tile of a monster, a Checkpoint, the start or another interactable, is refused too, but one on an entrance or in an exit's zone is not: keep it off them (`tests/shipped-puzzles.test.ts` does for the shipped rooms).
- **The route never needs one.** The hero finds every door and gate shut and may never find the key or the lever, so the way along the route has to be there with all of them shut. `checkRoutesStayOpen` (`src/core/device-routes.ts`) takes each area and each place the hero can be put in it (every entrance, and the start of the game in the area where it begins), and refuses the content when an exit or a Checkpoint can be reached from there with every door and gate open but not with every one shut: a key or a lever is never a way through. Only doors and gates make that difference, since a chest, a lever and a sign are solid either way. What cannot be reached even with everything open (a wall) is the map's business, and content with no door or gate is never refused. The exits and the Checkpoints are the destinations of the route as the core knows it: a ticket that adds another destination adds it to `destinationsOf`.
- **The shipped room** is in `src/content/areas/woods.ts`, in the woods' `interactables` beside the chests, and is not on the way out: a locked cabin in the south-west, with a chest inside that holds the Long Bow (the weapon upgrade of the woods). A sign by its door says that the key is in the north woods, and the brass key lies there, a good walk from the trail. The cabin is the first side path of the game. The first lever and the first gate are in the cave, off the way on: a lever in a niche of the east wall of the middle chamber opens a gate that shuts a pocket of grass in its north wall, with the Katana in a chest (`cave-lever`, `cave-gate` and `cave-weapon-chest` in `src/content/areas/cave.ts`), and a sign by the gate says where to look (`cave-sign`). The pocket is a dead end, so the way on never needs the lever. The covered corner stays solid.
- **In the adapter.** The inventory lists the keys under the consumables, each with the pack's key picture and its name, two at a time and then `+N MORE` (`VISIBLE_KEYS` in `src/adapter/overlay.ts`). The notice tells of a key found (IT OPENS A DOOR), a door that is locked (NEEDS the key's name), a door opened and a lever pulled or put back (`src/adapter/notice.ts`). A sign needs no notice: its text shows in the banner of the area text, so it follows the banner's font rules, and `tests/shipped-puzzles.test.ts` draws every character of the shipped sign. The key, the door, the gate, the lever and the sign are drawn by `src/adapter/prop-sprites.ts` from the pack's pictures (see Art): the gate is the pack's iron arch, with bars between its legs while it is shut, and the lever is a stick and a ball set on a slab of the pack's stone in a niche of the rock, with a red ball on the left at rest and a blue one on the right when pulled.
- **To add a puzzle,** put its devices in an area's `interactables`: no rule changes, and the route rule says if one stands in the way. To add another kind of device, follow the steps at the top of `src/core/interactables.ts`.
- **The tests.** `tests/keys.test.ts`, `doors.test.ts`, `levers.test.ts` and `signs.test.ts` are at the Game core's interface on fixtures (`keyAt`, `doorAt`, `gateAt`, `leverAt` and `signAt` in `tests/fixtures.ts`). `device-blocking.test.ts` pins what a shut device does to the hero's arrow, a walking monster, a charger's dash and a projectile; `device-content.test.ts` and `device-routes.test.ts` the refusals, the second on small halls drawn in the file; `device-persistence.test.ts` a defeat, leaving an area and a saved game. The saved adventure in `tests/saved-adventure.ts` takes the devices through the round trip and the sweeps. `tests/shipped-puzzles.test.ts` plays the shipped room, the cabin, with the core's own walking and Interact, keeps the way out free of it, and checks the two tickets together: a New Game after the puzzles were played starts clean with the opening, and a Continue brings them back with none. A door and a gate count as solid in `tests/routes.ts`, as the hero finds them, and as open in the check of `tests/shipped-areas.test.ts` that every tile that is not solid can be reached, so that the rooms behind them count; no route that `shipped-enemies.test.ts` or `shipped-content.test.ts` walks goes through one. `tests/routes.test.ts` pins both, and where a monster takes the hero in (`awarenessOf` and `isWithinAwareness`, which `shipped-enemies.test.ts` and `the-guardian.test.ts` use to keep the layout clear of every monster). Not tested automatically: how the devices, the notices and the key rows of the inventory look. Look at them in a browser with `npm run dev`: start a New Game (see Looking at the running game), walk east along the coast and through its exit into the woods, and follow the sand trail east and then north-east to the brass key, which lies off it in the north. Take the key, go back to the cabin in the south-west, read the sign, and press E at the door and at the chest. No shipped area has a lever or a gate on the way to the cabin, so pulling a lever is for the play check of the cave (see the tests of the cave below). Walk onto the Checkpoint at the way in of the woods to save, reload and choose Continue: the door and the key are as they were left, and a defeat leaves them alone too.

## Checkpoints and defeat recovery

- **Checkpoints are data.** An area in `src/content/areas/` lists its `checkpoints`, `{ id, tile }`: one tile each, which is not solid. Every area needs at least one, so that a defeat in it can send the hero somewhere safe. The coast has `coast-checkpoint` on the tile where the hero starts, the woods `woods-checkpoint` at the way in from the coast, the mountain `mountain-checkpoint` at the way in from the woods, the cave `cave-checkpoint` at the way in from the mountain, and the castle `castle-checkpoint` at the way in from the cave. Loading refuses an area with none, an id used twice anywhere in the content, and a tile that is solid or where a monster starts (`loadCheckpoints` in `src/core/checkpoint-content.ts`), inside an exit of its own area (`checkConnections` in `src/core/connections.ts`), or where an interactable starts (`loadInteractables` in `src/core/content.ts`), because after a defeat the hero stands at the centre of the tile. To add one, add it to the area's list: no rule changes.
- **Touching one activates it.** In every fixed step `activateCheckpoints` (`src/core/checkpoints.ts`) activates each Checkpoint of the hero's area that its body overlaps now and did not at the start of the step: the hero comes onto it. Standing on it, or being hit on it, does nothing more; a hero who leaves it and comes back activates it again. Activating emits `checkpoint-activated`, restores the hero's Health to full and records what defeat will give back (below). It refills no Ammunition. It comes after the hero has walked and taken the pickups it touched, so a pickup on the way onto a Checkpoint is recorded with it, and before the arrows fly and the monsters act. A Checkpoint at an entrance is activated as the hero comes in: its event follows `area-changed` and `area-text`. The start of the adventure counts as the first Checkpoint without being touched, so a new game, or a game continued from a snapshot, emits no `checkpoint-activated`.
- **Defeat goes back to the last one.** `recoverHero` puts the hero at the centre of the tile of the Checkpoint it activated last, at full Health, and the monsters of that Checkpoint's area are back at full Health at their starting places, defeated ones included. The Checkpoint can be in another area than the one where the hero fell: then `hero-defeated` is followed by `area-changed`, the living monsters of the area where the hero fell are calmed (idle, with their Health kept) as when it leaves by an exit, and the monsters of every other area keep what happened to them, so a monster defeated there stays defeated. The one exception is the Guardian: one that has not fallen is put back as it was placed (full Health, on its start tile, idle, its first pattern next) in every area, not only in the Checkpoint's, and one that has fallen stays fallen, with its gate open (see The Guardian).
- **What is given back and what is kept.** The Ammunition and the Healing Potions are as many as the hero had at the Checkpoint: what it spent is back, what it found since is gone. Every pickup, cache and chest of potions, in every area, is taken or not as it was then (`src/core/consumable-rollback.ts`), so a cache opened after the Checkpoint can be opened again, its arrows included. What stays is everything permanent: the Level and Experience, the Stat Points already assigned, all the Gear and what is equipped, the weapon in hand, the opened chests of Gear, the milestones reached and the world of the light puzzles: the keys taken and held, the doors opened, the levers pulled and the gates they opened (see Light puzzles and clues).
- **One known edge.** A consumable that a monster dropped is not given back when that monster is in another area than the Checkpoint's: it stays defeated and drops nothing more, so the drop is lost. The monsters of the Checkpoint's own area come back, so their drops can be earned again. This is left as it is on purpose, and `tests/checkpoints.test.ts` pins it.
- **In the adapter.** `src/adapter/prop-sprites.ts` draws a Checkpoint as a pole with a flag (`prop-checkpoint`, 16 by 26 pixels, standing on the bottom of its tile). The pole stands 10 pixels above its tile, so that the flag of the one defeat returns to now (`active` in the view: red, waving at the top of the pole) shows over the hero, who stands on it at the start and after a defeat; the others hang a grey flag half way down, still. The notice says CHECKPOINT and HEALTH FULL for a few seconds when one is touched, and a defeat ends the notice that is on the screen, whatever it is, because it told of what happened before the fall (what was found since the Checkpoint is back where it was).
- **The tests.** `tests/checkpoints.test.ts` builds two-area worlds with numbers worked out by hand: the content rules, touching, arriving on a Checkpoint, defeat in the same area and in another, the monsters, each kind of consumable that is given back, what stays, and a snapshot taken before a defeat. `tests/shipped-areas.test.ts` checks the Checkpoints of the real areas. `tests/checkpoint-enemies.test.ts` takes a charger and a ranged attacker through the same defeat (see Chargers and ranged attackers).

## The Guardian

- **What it is.** The Guardian is the one monster of the `guardian` behavior (`src/core/guardian.ts`), the last thing between the hero and the sea. Its type has `patterns` where a chaser or a charger has one attack: an ordered list of telegraphed attacks, each with a `kind` (`sweep`, `charge` or `smite`), the `damage` it does, `windUpMs`, the time the player has to get out of the way, and `recoveryMs`, the time the Guardian rests afterwards and the hero can hit it freely. Like every monster it has `health`, `size`, `experience`, `speedTilesPerSecond` and `noticingDistance`, and it drops nothing. A new kind of pattern is a member of `GuardianPatternDefinition`, a case in `guardian.ts` and one in `monster-content.ts`.
- **The three patterns.** The sweep lands on the zone within `reach` tiles of the Guardian's body, all round it. The charge is the charger's: the Guardian dashes along the lane in front of it, as wide as its body and `dashRange` tiles long, at `dashSpeedTilesPerSecond`; it hurts the hero once if it reaches it, and it is stopped by solid terrain, a chest, another monster or the end of the lane. The smite lands on a square `size` tiles wide, centred on where the hero stood when the wind-up began, so a hero who walks on is out of it.
- **How it chooses.** `stepGuardian` leaves the Guardian idle while the hero is beyond `noticingDistance` of its body. Otherwise, whenever it is free (not winding up, dashing or recovering), it takes the first pattern that reaches the hero, trying them from the one after the last it made: the sweep when the hero is within `reach` of its body, the charge when the hero is in the lane toward it, the smite when the hero is within `range` of its body. When none reaches, it walks toward the hero (`chasing`) and tries again in the next step. Which pattern it tries first is `nextPattern` in its state, the one thing a Guardian keeps that no other monster does, and it is saved (that raised `SNAPSHOT_VERSION` to 3). Nothing is random.
- **Telegraphed and fair.** The zone of a wind-up is fixed in the step it begins and shows in the view as a charger's does: `winding-up` has the `zone` and the `progress` towards the blow. A charge's direction is pinned then too, so the dash goes down the lane whether or not the hero still stands in it, and a smite's square stays where it was. A hit on the Guardian never interrupts a wind-up, so every blow lands as it was shown. `tests/shipped-enemies.test.ts` wants the hero able to step out of each pattern's zone within half of its wind-up, and to strike freely twice at least in each recovery.
- **The gate.** A gate with `opensWhenDefeated` (see Light puzzles and clues) opens for good in the very step that its Guardian falls, and nothing else moves it. The events of that step come in this order: `monster-hit`, `monster-defeated`, `guardian-defeated` (with the `monsterId`; the gate is open already when it is told), the Experience the Guardian gives, and its drops, of which it has none.
- **Fought once.** The ordinary monsters of the area of a Checkpoint come back after a defeat, but the Guardian begins again (`src/core/guardian-reset.ts`). One that has not fallen is put back as the content placed it (full Health, on its start tile, idle, its first pattern next) whenever the hero is defeated or leaves its area, in every area, so each try starts from the beginning. One that has fallen stays fallen, and its gate stays open, whatever happens to the hero. That is why the victory is saved at once (see Saving, Continue and the title): no Checkpoint follows it.
- **What loading refuses.** `src/core/guardian-content.ts` runs when the game is created, from `loadContent`. Whatever the content: a second Guardian; a gate with `opensWhenDefeated` that names no monster, a monster of another area or a monster that is no Guardian; a lever that names such a gate; and a way to the Guardian's start tile that needs a door or a gate opened (that tile is one more place for the route check of `src/core/device-routes.ts` to lead to, like an exit). With `requireGuardian: true` in the `ContentDefinition`, which the game's own content says and the small maps of the tests do not: no Guardian at all; no Checkpoint immediately before it, that is one that lies on every way to the Guardian from the entrances and the start of its area, with no ordinary monster on the Guardian's side of it (a hero would meet it on every try before the Guardian); no gate that opens when it is defeated; a harbor that is empty; and no vessel in the harbor (see The harbor and the ending). The harbor is the set of walkable tiles that the hero cannot reach while the gates that wait for the Guardian are shut and can reach with them open (`tilesBehindGuardianGates`, which is not on the core's interface).
- **The castle's Guardian.** East of the last hall, the castle (92 by 30 tiles now) goes on with a gateway one tile wide and five long (row 11, columns 63 to 67) that has the Guardian's own Checkpoint in it (`guardian-checkpoint`, at column 65, which every way to the arena goes over) and nothing else. The arena is sand, 16 by 9 tiles (columns 68 to 83, rows 7 to 15), with four pillars, so that every pattern can be avoided by positioning, and the Guardian (`arena-guardian`, of the type `castle-guardian`) stands alone in the middle of its east half, at (76, 11), so that all it notices lies within the arena. In the far wall of the arena (column 84, row 11) is `harbor-gate`, shut, with no key and no lever. Behind it is the forgotten harbor: sand (columns 85 to 88, rows 10 to 12) and water (columns 89 and 90) enclosed by rock, with the vessel at the water's edge (see The harbor and the ending). `src/content/index.ts` sets `requireGuardian: true`, so that a castle without any of this is refused.
- **Its numbers.** `castle-guardian` has 100 Health, size 1.6, 30 Experience, a speed of 2.2 tiles per second (the hero's is 5), a noticing distance of 7 and no drops. Its patterns, in this order: the sweep (8 damage, 900 ms of wind-up, 1,100 ms of recovery, a reach of 1.4), the charge (11, 1,000 ms, 2,200 ms, a dash of 14 tiles per second over 7 tiles) and the smite (7, 1,100 ms, 1,400 ms, a square 3 tiles wide, within 5 tiles). The balance pass (ticket 26) kept them. `docs/balance.md` ("The Guardian") has the fight played by a dodging bot over the shipped content: a hero of Level 6 built five ways with the Gear of the main route, the same with the Katana and the Long Bow, and one of Level 3, each answering at different speeds. It says what such a bot can and cannot tell, and `tests/guardian-balance.test.ts` pins the relations. `tests/the-guardian.test.ts` pins ranges and not the values: the biggest, toughest and hardest-hitting monster of the game, slower than the hero, noticing from as far as an arrow flies, making its patterns in order, and a fight of between twelve and forty strikes for each of the three heroes.
- **In the adapter.** The Guardian is drawn from pictures like every monster of final art (see Art): `monster-castle-guardian.png`, in cells of 96 by 96 pixels, is the pack's Giant Blue Samurai made an empty suit of pale teal armour by `compose-art.py`, four ways of facing with a walk, a white frame when it is hit and, while it winds up, the pack's lunge with a blade raised high in red, with a shake. The pack draws its boss from the front only, so up is the mirror of down. The zone of a wind-up is drawn under the picture, as every telegraph is: the Guardian hides the middle of the square of a sweep, and the red of its pose and the outline of the zone say that the blow is coming. The view has no pose for a strike, so the pack's idle, hit and sweeping frames are not used. The flat gold of `castle-guardian` in `MONSTER_COLOURS` is only for a castle drawn without its art. When it falls the notice says GUARDIAN DEFEATED and THE GATE OPENED for the usual few seconds (the kind `gate-opened`, without an icon), and `guardian-defeated` is one of the events that save the game (`SAVING_EVENTS` in `src/adapter/autosave.ts`).
- **The tests.** `tests/guardian-patterns.test.ts` (each pattern's wind-up, blow and recovery, how it chooses, and the turns), `tests/guardian-gate.test.ts` (the gate while the Guardian lives, the events of its defeat, a lever and the gate), `tests/guardian-retry.test.ts` (a defeat while it lives, leaving the area and coming back, a Guardian that has fallen) and `tests/guardian-content.test.ts` (a Guardian the rules cannot work with is refused) are at the Game core's interface on content built for them, in `tests/guardian-fixtures.ts`, with numbers worked out by hand. `tests/guardian-validation.test.ts` gives what loading refuses of a Guardian's place one case each, by content that breaks that rule alone. `tests/saved-adventure.ts` has a Guardian and its gate, so that `tests/saved-game.test.ts`, `tests/save-round-trip.test.ts` and `tests/saved-game-walks.test.ts` check `nextPattern` and a gate that is open only once its Guardian has fallen. `tests/the-guardian.test.ts` says what the shipped Guardian and the castle's extension have to be (see above). Content that asks for a Guardian is refused when it has none, so the tests that walk the areas with every monster taken out use `withoutOrdinaryMonsters` in `tests/routes.ts`, which keeps the Guardian.
- **Looking at it.** How the Guardian looks and how the fight feels are not tested (a bot plays the fight in `tests/guardian-balance.test.ts`, and a bot is not a person: `docs/playtest-checklist.md` asks the player). Open the page with `?debug`, start a New Game, and set the scene up in the console (see Looking at the running game): take `gameCore.snapshot()`, set `state.areaId` to `'castle'`, `state.hero.position` to `{ x: 75, y: 11.5 }` with `state.hero.facing` `'right'`, and the `health` of the monster `arena-guardian` in `state.areas.castle.monsters` to a few points, then `send({ type: 'continue', snapshot })`. Watch the telegraphs in turn (the sweep's square round the Guardian, the lane of the charge, the smite's square), strike it until it falls, and see the notice, the gate open and the way to the harbor. Reload the page and choose Continue: the gate is still open and the Guardian is gone.

## The harbor and the ending

- **The vessel.** The vessel (`src/core/vessel-content.ts`, `src/core/departure.ts`) is the old ship that sails the hero home: an interactable of the kind `vessel` that fills one tile and is always solid, which the hero uses from any tile beside it. Interact on a vessel that is not prepared prepares it, for good: the core emits `vessel-prepared`, the view's vessel shows `prepared`, and nothing else changes. Interact on one that is prepared opens the question whether to sail home. Both are in the snapshot (the vessel's `prepared` and `PlayState.departure`), which is why `SNAPSHOT_VERSION` is 4.
- **The question.** Sailing home is the game's only point of no return, so the game asks first. While the question is open (`departure` in the view, `{ vesselId }` or `null`) the game is paused, as it is for a page (see Pages and the pause). `confirm-departure` answers yes and `cancel-departure` answers no; both are ignored when no question is open, and at the title. No closes the question and changes nothing else: the vessel stays prepared, and the hero may walk away and come back. Yes ends the game. The one event is `ending-reached`, with the `ending` and the `credits` lines of the content, and the view is `{ phase: 'title' }` afterwards: there is no postgame, only `new-game` and `continue` are heard, and the core writes nothing, so the saved game is the last one that was saved, as it was.
- **The ending and the credits.** `ContentDefinition.ending` is from one to four lines, none blank, for the card the hero sails home to, and `credits` is as many lines as are needed, none blank, for the pages after it. They come together or not at all, and content that places a vessel must have them. The game's own are in `src/content/ending.ts`: an ending in four short lines, and credits in four: the title, the tools (Phaser, TypeScript and Vite), the credits text of the art pack from `docs/assets/licences.md`, and thanks. No person is named: a comment in that file says where a line for the author goes. The pixel font draws letters (all as capitals), digits, spaces and `. , ! ? ' - + / : ( ) % =` and nothing else, so a line may have no quotation mark, ampersand, semicolon or accent. **To credit a new asset,** add its credits text from the record to `credits` in the commit that copies the asset in: `tests/the-credits.test.ts` reads `docs/assets/licences.md` and goes red for an entry whose status says it is in use when the credits do not give its credits text, or when the entry has none.
- **What loading refuses.** Whatever the content: a second vessel; a vessel with no ending and credits to sail home to; and a way to a vessel that needs a key, a lever or a door (the route check of `src/core/device-routes.ts` leads to the vessel as it does to an exit, and counts the gate of a Guardian as open, since defeating the Guardian is the way). With `requireGuardian: true`: no vessel at all; a vessel that is not in the Guardian's area; one that the hero can walk up to before the Guardian is defeated; and one that it cannot walk up to even after.
- **The game's harbor.** `old-vessel` stands at (88, 11) in the castle, in the middle row of the quay at the water's edge, and the hero stands at (87, 11) to use it. The way there is the Guardian's (the gateway, the arena and `harbor-gate`) and nothing else: no key, no lever and no other door or gate is on it.
- **What the player sees.** The first Interact on the vessel tells the player that it is ready and which key sails it (`vessel-prepared` in `notice.ts` and `feedback.ts`). The second opens the question as a panel of the overlay (`departurePanel` in `overlay.ts`): SAIL HOME? THE ADVENTURE ENDS. ENTER TO SAIL, ESC TO STAY. Enter answers yes (`departureAnswer` in `departure-menu.ts`, decided from the view before the frame's commands, so that the Interact that opens the question and an Enter pressed with it do not answer it at once), and Esc answers no: `PlayerInput.pollActions` sends `cancel-departure` along with the `close-page`s. The question is a wait of the game, as a page and a Stat Point are (`gameIsWaiting` in `waiting.ts`): the walk keys are left alone, the area's text is hidden and the notice goes. The vessel lies in the water at the end of the quay with its bow to the north, moored to a post, its sail furled on the mast; once it is prepared its sail is hoisted, which is how the picture shows that it is ready (see Art).
- **The ending scene.** When the frame's commands send the core back to the title and `ending-reached` is among the events, `PlayScene` starts `EndingScene` (`ending-scene.ts`) with the lines instead of the title screen, before it would save: the core is at the title, where there is nothing to save, so the saved game stays as it was. The scene shows the cards of `layoutEnding` (`ending-pages.ts`) over a picture of the evening the hero sails home (`backdrop-ending`, see The backdrops), drawn as the opening's card is (`drawCard` in `opening-card.ts`): the ending first and then the credits, never on one card, each card as many whole lines as fit, and a word too wide for a row, such as the link, broken after a slash, a hyphen or a dot. Enter turns one card (`turnPage`), and from the last goes to the title, which reads the saved game afresh: Continue is there. The play screen is started again for the next game, and makes what it keeps of the last one (its clock and the flashes and notice of its feedback) anew in `init`. At start-up `requireDrawableEnding` refuses an ending or credits with a character the pixel font cannot draw, naming each. Enter held down to sail home turns no card, and held down on the last one does not choose on the title: `pressedAgain` in `player-input.ts` does not take the first repeat of a key that was held from the screen before for a press (Phaser makes new keys for each screen, and a new key counts that repeat as a press), which also keeps the card of the opening from going when New Game is chosen with a held Enter.
- **The tests.** `tests/vessel.test.ts` (the vessel is solid and is prepared with Interact), `tests/departure.test.ts` (the question, the pause while it is open, declining), `tests/ending-route.test.ts` (the way to the ending runs through the Guardian) and `tests/ending.test.ts` (sailing home, the title afterwards, the ending in the content) are at the Game core's interface on the content of `tests/harbor-fixtures.ts`. `tests/vessel-validation.test.ts` gives what loading refuses of a vessel one case each, on content that breaks that rule alone. `tests/the-harbor.test.ts` and `tests/the-credits.test.ts` are on the shipped content (see How the tests work). What the saved game checks about a vessel and the question are in `tests/saved-game.test.ts` and `tests/save-round-trip.test.ts`. The adapter's pure parts are tested directly, with numbers and views worked out by hand: `tests/ending-pages.test.ts` (the pages and what Enter does among them), `tests/departure-panel.test.ts` (the panel), `tests/departure-menu.test.ts` (which key answers), `tests/game-waiting.test.ts` (what counts as a wait), `tests/feedback.test.ts` and `tests/notice-lines.test.ts` (the notice of the vessel, and in the first of them that COULD NOT SAVE THE GAME is told once in a play, and that a notice told in the very frame a wait begins waits for it, as the bow does when the defeat that gives it raises the Level), `tests/vessel-art.test.ts` (the picture of the vessel against the harbor's water, the quay and the placement), `tests/pixel-font.test.ts` (what the font cannot draw), `tests/play-start.test.ts` (what the play screen is started with and what it hands the ending) and `tests/player-input.test.ts` (a key held from the screen before is not a press, on plain fake keys and a copy of Phaser's rule of when a key went down, which `PlayerInput` is given: the browser is where the real ones are looked at).
- **Looking at it.** How the vessel, the question, the ending and the credits look and feel is not tested automatically. Open the page with `?debug`, start a New Game, and set the scene up in the console (see Looking at the running game): take `gameCore.snapshot()`, set `state.areaId` to `'castle'`, `state.hero.position` to `{ x: 75, y: 11.5 }` with `state.hero.facing` `'right'`, `state.hero.experience` to 100 and `state.hero.statPoints` to `{ health: 2, attack: 2, defense: 1 }` (a hero as it is at the end of the route: Level 6, its five Stat Points assigned) and the `health` of the monster `arena-guardian` in `state.areas.castle.monsters` to 1, then `send({ type: 'continue', snapshot })` and `send({ type: 'attack' })`: the Guardian falls. Take `gameCore.snapshot()` again, set `state.hero.position` to `{ x: 87.5, y: 11.5 }` with `state.hero.facing` `'right'`, and `send({ type: 'continue', snapshot })`: the hero stands on the quay before the vessel. Press E: the notice says that the vessel is ready. Press E again: the question. Esc stays (walk away and come back: the vessel is still ready, and E asks again); Enter sails home: the ending, then the credits, each turned with Enter, then the title, where Continue brings back the last automatic save (here the start of the game), not the vessel. Hold Enter down at the question to see that a held key turns no card.

## The Automap

- **What is recorded.** Each Adventure Area keeps `revealed` in the state: a grid of booleans, one per tile (`revealed[row][col]`), all false at the start of the adventure. A tile only ever goes from false to true, so what the hero has explored is never taken back: not by a defeat and the roll-back that comes with it, not by leaving the area. It is part of the plain-data state, so a snapshot carries it. `SNAPSHOT_VERSION` was not raised for it: nothing was saved to disk before the save store (see Saving, Continue and the title), so no save lacks it.
- **When tiles are revealed.** `revealAroundHero` (`src/core/automap.ts`) reveals every tile of the hero's area within `automapRevealDistance` tiles of the hero's tile: a disc, the tile `(c, r)` when `(c - hc)² + (r - hr)² <= d²` with `hc` and `hr` the hero's column and row. There is no line of sight, so a wall or water beside the hero is revealed like ground. It runs at a new game, after the hero has walked in each fixed step, as the hero comes in through an exit, and after a defeat once the hero is back at its Checkpoint, never while the game waits. It sends no event: the view is the truth. `automapRevealDistance` is a number on the content (tiles, 0 or more; 4 if left out, and the shipped content says 4); a value that is not a number of 0 or more is refused.
- **The page.** While the Automap is open, `view().page` is `{ id: 'automap', areas }`, built only then. `areas` has every Adventure Area of the content in the order of `areas` in `src/content/index.ts`, which is the order of the route, and each one has `id`, `name`, `width` and `height`, `current`, `discovered`, `connections` (the ids its exits lead to, shown from the start so the route is known), `hero` (where the hero is, in tiles, only in the current area), `exits` (only the ones found) and `terrain` (the kind of each revealed tile, `null` for a tile not revealed). An area the hero has not been in has no name, no terrain and no hero. A found exit is one with a revealed tile in its `zone`, worked out when the view is built, so a farther distance finds exits sooner. A reveal distance below 1 can let the hero cross an exit before it has found it. There are no quest markers.
- **Adding an area.** Write it and add it to `areas`: it comes on the page in that place with no rule changes. Content that links areas both ways is already required (see Connected areas).
- **In the adapter.** `src/adapter/automap-layout.ts` places the route with plain numbers and no Phaser (`layoutRoute`, `routeLinks`, `linkEnds`, `exitSide`, `tileRects`, `exitRect`, `markerRect`, `fitLabel`), and `src/adapter/automap-page.ts` draws it from the view and from the exits of the content's areas (`startAdapter` gives them to the play scene), over the dimmed game, with the bitmap font (area names must use letters, digits and the signs the font has). Its window is drawn with the same `UiLayer` frames as the other pages (see Art below), under the map and the hero's mark, which are shapes drawn on top of it (the window at depth 199, the map at 200, the mark at 201, the same place as the overlay). Each Adventure Area is a card: its name above its map, the revealed terrain in the colours of the area's palette (`src/adapter/automap-palette.ts`, see Art below), undiscovered tiles dark, found exits pale (as in the game), the current area ringed in the title colour of the window, and the hero a mark that blinks gold and white. The cards run along a row in route order and the next row runs back (a serpentine), at the largest scale from 8 pixels a tile down to 1/16 at which the whole route fits; a name too wide is cut and ends in `..`. A link joins two areas next to each other on the route when an exit of one leads to the other, and it meets each map at the side where that exit is: `linkEnds` takes, from the areas of the content, the side of the first exit of an area that leads to the next one and of the first exit of the next one that leads back (`exitSide`: an exit in the first column of its map is at its left, one that ends at its last column at its right; an exit anywhere else, or an area with none to the other, leaves the side to the layout). Where the sides face one another it is a straight strip in a row and a C round the end of the rows between rows; where they do not, it leaves the map by an arm to a post clear of the card, runs along the gap between the rows (below the row, for two maps in one) and comes in by the arm of the other map. The shipped route has two of those, the mountain's east edge to the cave's west edge and the cave's east edge to the castle's west edge, because the second row runs back. Two links that ran along the same gap between rows could run over one another; the shipped route has no such pair. Links between areas that are not neighbours on the route are not drawn. An area the hero has not been in is a dark box of its true size with the name UNKNOWN.
- **The tests.** `tests/automap.test.ts` is at the Game core's interface on fixtures: nothing revealed before the hero has explored, the disc and its edge, the reveal distance, the hero's position, the route in order, exits found only once, arriving in another area, the page and the pause, a snapshot, and a defeat that takes nothing back, with a three-area route (so a route of more than two areas is covered). `tests/shipped-content.test.ts` checks the real route. `tests/automap-layout.test.ts` pins the pure layout in numbers worked out by hand: the scale ladder, the rows, the pixels of a map, the links, the side of its map that each exit is at (and that every link of the shipped route leaves an area by its east edge and comes into the next by its west edge), the links drawn at those sides and the cut names. `tests/automap-palette.test.ts` checks the colours of the maps: one for every kind of terrain in every area, each from the pack's own palette, a solid kind told from one that is walked on, every kind clear of the unexplored ground and of the exits, and no two kinds alike. Not tested automatically: that the colours look right, the size of the mark, and how it looks. Look at it in a browser with `npm run dev`: start a New Game (see Looking at the running game), then M, and walk.

## Saving, Continue and the title

- **The game opens on the title screen.** `TitleScene` (`src/adapter/title-scene.ts`) is the first scene. It shows a picture behind everything (`backdrop-title`, composed by `docs/assets/compose-art.py` from the sea, the sand and the wreck of the coast: a morning with the Hunter on the sand, a crab, and a low island with a castle on the horizon; it is the size of the canvas, so it is shown as it is, at `DEPTH.backdrop`, 290), the name of the game in big letters across the top (the project's own bitmap font drawn at three times its size, with an outline and a shade: `logoLayout` and `paintedBounds` in `src/adapter/title-layout.ts` choose the largest whole scale that fits, and `UiLayer.scaledText` draws it), and offers New Game, Continue and Controls in a `UiLayer` window of its own (depth 300 in `depths.ts`), centred in the room under the logo (`windowTop`), the tallest of its states (the message about a saved game that cannot be used) included. `tests/the-title-logo.test.ts` pins the lettering and the layout. Up and Down (or W and S) move the cursor and Enter chooses. Continue is greyed, and the cursor cannot rest on it, when there is no saved game to continue from; when there is one the cursor starts on it, so that Enter goes on with it, and otherwise it starts on New Game. Controls is never greyed, with a saved game or without. New Game over a saved game asks first (REPLACE THE SAVED GAME?): Enter replaces it, Esc keeps it, and nothing is written until Enter. Enter on Controls shows the list of the controls: the same lines as the Controls page in play (see Pages and the pause), laid out and drawn from the same tables by the same `layoutControlsList` and `drawControlsList`, so that the title and the play screen cannot disagree. The list takes the middle of the whole screen, the name of the game being left out, headed CONTROLS and with ESC OR ENTER TO CLOSE at its foot; Esc closes it and so does Enter, and the menu is back with the cursor on Controls. While it shows nothing else of the menu answers (the cursor keys do nothing, no game starts and the question to replace cannot open), but the keys of the sound (N, - and +) do. The title does not read H. The list is a state of the menu, `showingControls`, beside the question's `confirming`, and not a choice: it starts no game, and showing it and closing it are heard as a page opening and closing, as the question is. No save is written. The rules of the menu are `openMenu`, `selectableEntries`, `pressMenu` and `soundOfPress` in `src/adapter/title-menu.ts`, with no Phaser, and `tests/title-menu.test.ts` pins them. What the window says in each of its states, how high it is and where each of its rows goes are `layoutTitleWindow` in `src/adapter/title-window.ts`, with no Phaser either, and `tests/title-window.test.ts` pins them: the scene draws what it says. The window is 106 high in the two states of the menu with nothing to tell (with a saved game and without), 57 for the question, 132 in the three states that tell of the saved game (saving not available, a damaged save, a save from another version) and 181 for the list. The line of the audio is at the bottom right and the rows of the window end above it, so the window may be 139 high at most; the third line of the menu made the tallest states 15 higher than that, and to stay within it the hints are three rows, the keys of the sound sharing the last (N TO MUTE and - OR + FOR VOLUME), and a save from another version is told in two rows of message (SAVE IS FROM ANOTHER VERSION. and A NEW GAME WILL REPLACE IT.), like the damaged one. New Game sends `new-game` and Continue sends `continue` with the saved snapshot, and then `PlayScene` starts; for a New Game it starts with the card of the opening (see The opening). `gameCore.view()` is `{ phase: 'title' }` until one of them is chosen, so press Enter before using `gameCore` in the console. When the core's view says `title` while the play scene is up, the hero has sailed home: the play scene hands over to the ending scene (see The harbor and the ending), which goes on to the title screen, and the title reads the saved game afresh, so Continue is offered from the last autosave.
- **When it saves.** There is one slot and no manual saving. The rule is `callsForSave` (`src/adapter/autosave.ts`, pinned by `tests/autosave.test.ts` for every kind of event the core tells): a frame whose events hold `checkpoint-activated`, `area-changed` or `guardian-defeated` saves, once, as the game stands at the end of the frame. That includes a defeat that returns the hero to a Checkpoint in another area. The Guardian's fall is there because no Checkpoint follows it: without that save, a tab closed after the victory would bring back the last Checkpoint with the Guardian alive and its gate shut. A New Game saves at once as well: the start counts as the first Checkpoint without an event, and without that save a tab closed right after a confirmed New Game would bring the old save back. Continue and the title never save. The slot holds the game as it was at the last Checkpoint, area change or victory over the Guardian, not as it is now: reload, choose Continue, and the hero is back there.
- **The slot.** It holds the JSON text of one `Snapshot` under the localStorage key `island-adventure-rpg:saved-game` (`SAVE_KEY` in `src/adapter/save-store.ts`). `createSaveStore(storage, content)` is a thin adapter and holds no rules: `read()` says `none`, `usable`, `unusable` (`damaged` or `incompatible`) or `unavailable` (the browser gives no storage, or refuses to read it), and `write(snapshot)` says whether the browser took the save. It never removes a save: one the game cannot continue from stays until the next autosave overwrites it. `main.ts` hands it `window.localStorage`, or null when the browser blocks it. Held keys are input, not state, so a Snapshot has none and `continue` clears them: a restored game stands still until a key goes down. Whatever the player is pressing right now is never saved, and the tickets that follow keep to that.
- **The sound settings are not in the slot.** Whether the sound is off and how loud it is are kept under a key of their own, `island-adventure-rpg:audio-settings`, so that a New Game, Continue and a damaged save leave them as they were, and changing them never writes the saved game (see Audio).
- **A save the game cannot take is never fatal.** `parseSave` (`src/adapter/saved-game.ts`) is the one gate between the text in the slot and the Game core. It is a pure function of the text and the content: it parses the JSON, checks the saved shape field by field (a snapshot must have exactly the fields the state has, with ids the content has and values that make sense, such as a position inside the area), and then tries the snapshot on a game of its own (`continue`, `view`, one step), so a save that passes the checks but cannot be played is refused too. A save that is not a snapshot is `damaged`; one made for other content or by another version of the game (the `version` marker, `SNAPSHOT_VERSION`) is `incompatible`. The title treats either as no save: Continue is greyed, a short message in the window says why (THE SAVED GAME IS DAMAGED. or SAVE IS FROM ANOTHER VERSION.) and that a New Game will replace it (nothing is asked, because there is nothing to keep), and the console gets a warning with the detail. With no storage the title says SAVING IS NOT AVAILABLE and the game can still be played. A write that fails shows the notice COULD NOT SAVE THE GAME for a few seconds, over whatever the notice told, and the game goes on; the earlier save stays as it was. Only the first write that fails in a play is told (`Feedback.saveFailed` in `src/adapter/feedback.ts`, a `Feedback` being made afresh for each play): with no storage at all every write fails, and the title has said so, so telling again would cover the notice of every Checkpoint.
- **Changing what is saved.** A ticket that adds to or changes the saved state bumps `SNAPSHOT_VERSION` (`src/core/state.ts`), with the literal of `Snapshot.version` in `src/core/interface.ts` (both are 4 now: ticket 13 added the devices and made them 2, ticket 19 gave the Guardian a turn of its patterns to save and made them 3, and ticket 20 added the question whether to sail home, `PlayState.departure`, and made them 4), so that older saves are named incompatible, and it extends two things in the same commit: the checks in `saved-game.ts` (they refuse a snapshot with fields the state does not have, so the tests go red until the checks are extended) and the fixture `tests/saved-adventure.ts` (a thing in its content and a chapter of its script that changes it). For a new kind of interactable, such as the devices of ticket 13, that means `FLAG_OF` and `checkInteractables` in `saved-game.ts`, as well as the fixture's content and a chapter. State that is only input stays out of the snapshot.
- **Content that a save names.** A save holds the state of every interactable of every Adventure Area, and `checkInteractables` in `saved-game.ts` refuses a save that has one its area no longer places and a save that lacks one its area places (`incompatible`). That is how a change to the content makes old saves unusable without a new `SNAPSHOT_VERSION`: ticket 30 took the bow chest out of the woods, so every save made before it is refused for the chest it names, the title says it is from another version, and a New Game replaces it. The Gear of the hero is checked in the same way: `checkHero` refuses a save whose hero carries a piece that is not Gear of the content (`incompatible`, the detail naming the place and the id), so a save of ticket 30 or 31 whose hero holds the lesser of the two bows, which ticket 32 took out of the game, is refused as well, while one whose hero holds no bow, or the Long Bow, is usable. The shape of the state did not change, so the version is still 4. Adding, removing or renaming an interactable, or taking a piece of Gear out of the content, does the same, so a ticket that does it makes a New Game necessary.
- **The tests.** The parser and the store are the first of the three exceptions of ADR 0002, tested directly because a save outlives the build that wrote it. `tests/saved-game.test.ts` pins the faults that matter, with saves written by hand. `tests/saved-game-sweeps.test.ts` damages a full saved adventure at every place of it in turn (the wrong kind of value, taken away, an extra field) and expects a refusal that names the place; the few places that would not be a fault are named in the file, and a ticket that adds state has its places swept without writing a line. `tests/saved-game-walks.test.ts` plays a hero that does anything at all, among every kind of monster and in the shipped content, and requires every state it saves to be usable and to come back as it was. `tests/save-store.test.ts` tests the store over a storage in memory that can fail (`tests/memory-storage.ts`, which `tests/audio-settings.test.ts` and `tests/continue-after-checkpoint.test.ts` use too). `tests/save-round-trip.test.ts` is at the Game core's interface: a game restored from its snapshot, after a trip through JSON text, is the same game after every chapter of `tests/saved-adventure.ts`, and a defeat after Continue goes as it would have. The saved adventure places no chaser, so the rows about one are judged in `saved-game.test.ts` with the content's rat made one.
- **Not tested automatically:** the title scene and the play screen, which call the rules of the menu, the window of the title and the autosave rule (the rules themselves are in `tests/title-menu.test.ts`, `tests/title-window.test.ts` and `tests/autosave.test.ts`). Look at them in a browser with `npm run dev`: start a New Game (see Looking at the running game), walk to a Checkpoint or through an exit, reload the page and choose Continue. At the title, move down to Controls and press Enter for the list of the controls, then Esc or Enter to close it; N, - and + answer while it shows. For a bad save, put text that is not a snapshot into the key in the console (`localStorage.setItem('island-adventure-rpg:saved-game', '{')`) and reload.

## The opening

- **What it is.** A New Game begins with a short card of text before the player takes control: a few lines that say what happened and what to do about it. The shipped card has four lines: the storm, the island, the wake on the sand, and the goal, a way home that the hero is to find (first-draft words, for the author to rewrite). It is content (`opening` in `ContentDefinition`, the lines are in `src/content/opening.ts`): one to four lines, none of them blank, and a content with none (leave `opening` out) has no card. `createGame` refuses an opening with no line, a blank line or more than four (`MAX_CARD_LINES` in `src/core/content.ts`), naming the line. The pixel font draws letters (as capitals), digits and `. , ! ? ' - + / : ( ) % =`, and anything else is left blank, so write the lines with those: `tests/opening-card.test.ts` draws every character of the shipped opening to be sure.
- **Where the Game core stands.** The core sends the opening as an event and holds nothing for it. `new-game` returns `opening` (with the `lines`) first, then what entering the first area gives (its `area-changed`, `area-text` and so on); `continue` and a defeat never return it. The game is not paused and nothing is saved for it: if the caller steps, the hero walks. That is why the saved game needed no new field and `SNAPSHOT_VERSION` was not raised.
- **Where the adapter holds the game.** `startOfNewGame` (`src/adapter/scene-keys.ts`) turns the events of `new-game` into what `PlayScene` starts with: `saveAtOnce` as before, and the `opening` lines when the core gave them. While `PlayScene` has a card up (`OpeningCard` in `src/adapter/opening-card.ts`, at `DEPTH.openingCard`, over everything of the play screen but the audio line) it does not step the core, forwards no key and discards what the menu and action keys pressed; Enter takes the card away and the screen fades in from black. The keys that are held are read again from the next frame. The area text counts its time from there, because no step has run. A New Game is still saved at once while the card shows, so a tab closed on the card brings back the new game on Continue, which skips the card.
- **The layout** is `layoutCard` in `src/adapter/opening-card.ts`, with no Phaser: each line is wrapped to fit the screen with the bitmap font (the same `wrapText` as the area text), lines are set apart more than the rows of one broken line, the rows are centred, the hint ENTER TO BEGIN sits under them, and the window is sized round them and centred on the screen.
- **The tests.** `tests/opening.test.ts` is at the Game core's interface on fixtures (`opening` in the arena options of `tests/fixtures.ts`): the event, its place before the area text, every new game, none for Continue, no pause and nothing saved, and the refusals. `tests/play-start.test.ts` pins what `PlayScene` starts with. `tests/opening-card.test.ts` pins the layout in numbers and the glyphs of the shipped lines. `tests/shipped-content.test.ts` pins that the shipped opening gives a goal (a line about the way home that the hero is to find) and that the goal names no Guardian, castle, harbor or ship. Not tested automatically: the drawing of the card, that it holds the game, and the fade.

## Art

The art is the Ninja Adventure pack (CC0), and the one record of every file copied from it is `docs/assets/licences.md`. Art is presentation only: no rule, number, map or collision depends on it, and the Game core knows nothing of it.

- **The asset manifest** (`src/adapter/asset-manifest.ts`) registers every picture by name, as one of three kinds: `image(file)`, `sheet(file, frameWidth)` for equal frames in one file, and `drawn(rows, palette)` for a small picture drawn in code where the pack has nothing (the armor icons, `src/adapter/drawn-icons.ts`). `ARTWORK` in `src/adapter/artwork.ts` is the one list, a line per picture, and the files are under `public/art/`. **To add a picture,** copy the file into `public/art/` unchanged, add its line to `ARTWORK`, and list the file in `docs/assets/licences.md` in the same commit.
- **Content asks for art by name, never by file.** For Gear and consumables the name follows one rule: `gear-<id>` and `consumable-<id>` (`gearIcon`, `consumableIcon` and `neededArt` in `artwork.ts`). A new piece of Gear or a new consumable needs its line in `ARTWORK` under that name. The flat colours, which every area without final art is still drawn in (see below), are named the same way: a terrain kind needs its colour in `TERRAIN_COLOURS` and a monster type its colour in `MONSTER_COLOURS` (`src/adapter/art.ts`), and one that has none is drawn in magenta. `tests/shipped-art.test.ts` fails for any picture or colour that the shipped content asks for and the adapter lacks.
- **A missing picture fails loudly, and says which.** `requireArt` throws an Error that names every picture that is missing. It runs when the game starts, on the names the content needs against the manifest, and again once the scene has loaded, on every picture of the manifest against Phaser's textures, so a file that is not there (a 404) is named too, and nothing is drawn as a blank. The check is a pure function of an `ArtLookup`, and `tests/asset-manifest.test.ts` tests it through its public functions with in-memory fakes. The loading itself is `src/adapter/asset-loader.ts`: `queueArt` in `preload`, then `buildDrawnArt` and `requireLoadedArt` in `create`, which the title, the play screen and the ending get from their base class, `GameScene` (`src/adapter/game-scene.ts`, which also takes their keyboard and makes their audio line). Files are fetched from `art/` under the site's base, so the game works from any path. `vite.config.ts` sets `appType: 'mpa'`: with the default single-page fallback the dev server answers a missing picture with `index.html` and a 200, which hides the missing file, and with `mpa` it is a real 404.
- **Final art, area by area.** `FINAL_ART_AREAS` in `artwork.ts` lists the Adventure Areas that are drawn from pictures: all five now, the shipwreck coast, the woods, the mountain, the cave and the castle. `hasFinalArt` is the one question the scene asks, and an area that is added without its art keeps its flat colours (`TERRAIN_COLOURS` and `MONSTER_COLOURS`) until its own art pass, so an area can be playable before it is drawn. For a listed area `neededArt` asks for `terrain-<kind>` for every kind of terrain on its map and `monster-<type>` for every type placed in it, and the game refuses to start without them; for any other area it asks for nothing. **To give another area its art,** compose the pictures its kinds and types need, add their lines to `ARTWORK`, and then add the area to the list. `tests/final-art.test.ts` pins all of it, `tests/mountain-cave-final-art.test.ts` that the mountain and the cave are on the list and that every picture they ask for is in the manifest, and `tests/castle-final-art.test.ts` the same of the castle, its undead and its Guardian.
- **Composed pictures.** Most of the pictures of the coast, the woods, the mountain, the cave and the castle are not copies of one pack file. `docs/assets/compose-art.py` cuts named pieces out of the pack, puts them together, and writes the PNGs of `public/art/`: it needs Python 3 with Pillow and the pack (not in the repository), and `python docs/assets/compose-art.py --pack "<the folder Ninja Adventure - Asset Pack>"` makes every picture again, or only the ones named after it; `--out <folder>` writes somewhere else. Some of what is in them is not from the pack but drawn by the script itself: small touches (the glint of a pickup, the pole of a Checkpoint, the padlock of a door), pieces of pictures (the stick and the ball of the lever, the edges, the hole and the mast of the wreck, the mast and the furled sail of the vessel) and whole pictures (the mark of an exit, the pillars and the fountain of the castle, and the greater part of the two backdrops: the skies, clouds, gulls and island of both, and the sun, the sea and the far vessel of the ending's). `docs/assets/licences.md` names, for each picture, the pack files and the pieces it was made from and what the recipe draws, and the same commit keeps it in step. The icon of the Long Bow, the only bow of the game, is a bow of the pack turned upright (the bow that the hero holds, `bow-held.png`, is the pack's own, lying down, which read as a bowl in the HUD and the inventory).
- **The ground.** `planTerrain` (`src/adapter/terrain-plan.ts`) is pure planning, with no Phaser: it turns the kinds of terrain of a map into a list of stamps, each a frame of a terrain sheet on a tile or on a quarter of one, so that a shore, the edge of the sand and the face of a cliff join up at bends, corners and inlets with thirteen pieces each. `bakeGround` (`src/adapter/terrain-baker.ts`) paints the stamps once onto one canvas texture for the area (`ground-<area id>`), in whole pixels with nearest-neighbour sampling, and the scene shows it as one image that scrolls with the camera, because terrain never changes. The wreck is a picture of its own (`terrain-wreckage`). Sand, grass and rock are dressed in the look of the area (`TerrainLook`, chosen by `lookOf`): the coast and the woods have the standard sheets, the mountain has cliffs of slate, and boulders where a rock stands alone, and the cave has a darker stone and a floor of sand and grass that is darkened in the sheets themselves, so that its dim look is in the ground and nothing is laid over what stands on it. The castle has walls of masonry, flagstones in its halls, moss in its courtyards, a pillar where a rock stands alone, a fountain where a block of rock three tiles by three stands free and, at the harbor, water of grey-green and weathered planks on the sand within four tiles of it (the look of the castle is the only one that switches on water, planks and a fountain of its own). A look changes the picture of a frame and never which frame goes where, so the maps and their collision are as authored (`tests/mountain-cave-ground.test.ts` pins the looks of the mountain and the cave, and `tests/castle-ground.test.ts` the castle's, on small maps worked out by hand and with generic checks of the shipped map, and that the four earlier areas keep their own sheets). `tests/terrain-plan.test.ts` pins the plan on small maps worked out by hand, and `tests/final-art.test.ts` that the pictures on disk hold the frames the plan asks for.
- **The monsters.** In an area of final art each monster is a sprite (`MonsterSprites`, `src/adapter/monster-sprites.ts`): four ways of facing, a walk, a white frame when it is hit, a red one with a shake while it winds up, faded copies of a dash, a puff of smoke where it fell, and its Health bar (`healthBarBox`: just above the picture and as wide as the body, held on the top row of the screen while the picture reaches above it, as the Guardian's does against the north wall of its arena, and none once the whole picture is above the screen). What a flat monster shares with a pictured one, the red of a wind-up and the faded copies of a dash, is in `src/adapter/monster-look.ts`, and the hero's sheet has the same four columns (`FACING_COLUMN` in `config.ts`). `MonsterView` has no facing, so it is worked out from the last step, from the direction of a dash and, while it winds up, towards the hero. What a monster shoots (the spitter, the raider archer and the cave eye) is an orb (`src/adapter/projectile-sprites.ts`). The pack has no crab and no wolf, so the crab is its red mollusc and the wolf its black dog, and the spitter's mushroom has a purple cap, so that the red of a wind-up shows on it (all in `licences.md`). It has no raiders either: the dark ninja is the raider, the yellow one the charger, the blue one the archer and the knight, in navy, the veteran; the bat, the lizard, the eye and the bear of the cave are the pack's own, the bear in brown for the same reason as the mushroom's cap (`tests/mountain-cave-monsters.test.ts` pins their sheets). The pack has no ghoul, wraith or armoured dead for the castle either: its skeleton is the pack's own, the ghoul is its beast in a sickly yellow-green, the wraith its spirit in violet and the knight its gold knight tarnished, and the Guardian is its Giant Blue Samurai in the pale teal of an empty suit of armour, in cells of 96 pixels (`tests/castle-undead.test.ts` and `tests/castle-guardian-art.test.ts` pin their sheets, and that the pose of a wind-up differs from the walk in colour; see The Guardian). The telegraph and the strike of an attack stay shapes drawn in `src/adapter/art.ts`: they say where a blow will land and must read on every ground.
- **The props** every area shares (`PropSprites`, `src/adapter/prop-sprites.ts`): chests and caches shut and open (a Gear chest, a cache of Ammunition and a cache of Healing Potions look different from one another), what lies on the ground (a potion, arrows, a key, each with a glint now and then), Checkpoints (a grey flag hung low while untouched, a red one waving once it is the one the hero returns to), the chevrons that mark an exit, doors shut (with a padlock) and open, gates shut (iron bars under an arch that stands over the way and on the rock beside it) and open (the arch alone), levers at rest and pulled, signs, and the old vessel of the harbor (`prop-vessel`: the pack's boat and sail in weathered brown, moored to a post at the end of the quay with its sail furled on the mast, and with the sail hoisted once the hero has prepared it). Each stands with its foot on the bottom of the tile the core says it is on, and none of it knows which area it is in; the vessel alone is stood two tiles lower (`vesselFoot`), because its picture is three tiles wide and seven tall: the vessel lies in the water beside its own tile, and its mast and sail stand over the rock; a gate is stood four pixels to the left of its tile (`gateFoot`), because its arch reaches that far past the tile on each side, and both numbers are worked out from the size of the frame in the manifest (`frameSize`). `tests/vessel-art.test.ts` ties that picture to the harbor's water, to the quay and to the placement, so that moving the vessel or the water cannot leave it drawn on the wrong tiles. `tests/gate-lever-art.test.ts` pins the frames of the gate and the lever: two each, the same arch for a gate shut or open with the bars in every column and row of the way only while it is shut, the way of a gate standing on its own tile, and a lever that fills its tile with its knob on the left at rest and on the right once it is pulled. A new kind of interactable gets its picture here, and a new area needs nothing.
- **The backdrops.** The title has a picture behind its logo and its window, `backdrop-title`, and the ending and the credits have one behind their cards, `backdrop-ending` (`compose-art.py` makes them, as it makes the others, and `licences.md` lists what they are made of). Each is 320 by 192 pixels, the size of the canvas, so that it is shown at whole pixels and never scaled; the window and the cards cover the middle, so the things that are meant to be seen stand at the sides, the top and the foot (on the title the sky, the island with its castle, the wreck, the Hunter and the crab; on the ending a sunset with the old vessel sailing across the sun, the island with its castle dark on the horizon and the quay of the harbor along the foot, the horizon high enough that the credits, the tallest card, leave the vessel clear), and `backdrop` is its own depth (`DEPTH.backdrop`, 290, under the 300 of the screens' windows). A screen that gets a backdrop adds one `image` at depth `DEPTH.backdrop` under its `UiLayer`, and nothing else of the screen changes; the card of the opening stays on black.
- **The colours of the Automap.** The maps on the Automap page are small flat pictures of the ground, and their colours are the pack's own, one for each kind of terrain, in the table of the area (`automapPalette` in `src/adapter/automap-palette.ts`): the coast and the woods share one (sand, lime grass, dark sea), the mountain, the cave and the castle have a table each (slate rock; a dark, violet cave; the castle in wall brown, flagstone and grey-green harbor water), and an area that is added later gets the coast's until it has its own. The flat colours of `art.ts` (`terrainColour`) are unchanged: they are still the ground of an area with no art, and what the Automap shows for a kind its table lacks. The page knows the kinds of terrain and nothing finer, so the harbor's dock planks are flagstone on the castle's map.
- **What draws above what** is in `src/adapter/depths.ts`: the ground, the marks of an exit, the props, the telegraphs, the flat shapes of what has no picture yet, the monsters, their shots, the hero, the strikes and the picture of a find rising over the hero. The telegraphs are above the props on purpose: a wind-up must never be hidden by a chest or a flag. Over the world come the parts of the play screen that are fixed to the screen, each over the one before: the HUD, the text of an area, the notice, the pages of the overlay (the Automap's too, which draws where the overlay does) and the card of the opening. The title, the ending and their backdrop are scenes of their own, and the audio line is over everything on every screen. `tests/depths.test.ts` pins that order, not the numbers.
- **The hero** is `HeroSprite` in `src/adapter/hero-sprite.ts`: standing, walking in four directions, the sword, the bow, a red flash when hit and lying defeated, and the hero's arrows, which point along their flight. The Hunter's sheet has one attack pose per direction and nothing for being hit, so the sword in the hand, the slash and the flash are added there. It runs on frame time from the view and the events, and the weapon in hand is shown by its slot, because the view does not say which piece of Gear is equipped. Only the arrows the view says the hero shot are the hero's (`byShooter` in `src/adapter/projectiles.ts`); a monster's projectile is an orb and no arrow sprite is ever drawn on it.
- **The fall.** The Game core puts a defeated hero back at its Checkpoint, in another Adventure Area if that is where it is, in the very step that defeats it, so the view of that step already shows the place it returned to. `Fall` (`src/adapter/fall.ts`) keeps the last frame the player saw, with the hero lying in it at 0 Health (the HUD too: the counts it had), for `FALL_LIE_MS`, then the camera fades to black for `FALL_FADE_OUT_MS`, and only then does the scene show the place the hero returned to, fading in, with the Health, the Ammunition and the potions that the roll-back gave it. No step of the Game core runs during the fall, and its timeline always ends, so it can never hold the game.
- **The interface** is built from `UiLayer` in `src/adapter/ui-layer.ts`: nine-patch frames (`panel`, `window` and `button`, from the pack's wooden theme; `UiLayer.window` draws a window, the `window` frame with a `panel` flush inside it, and `WINDOW_PADDING` is the space from its edge to what it holds), pictures at whole pixels, text and bars, all in the `INK` colours. The HUD, the overlay, the Automap's window, the notice and the area text all use it, so the look is in one place. Text is the project's own 5 by 7 bitmap font, `src/adapter/pixel-font.ts`, whose letters are rectangles: Phaser's `Text` blurs at this size, and no font file is shipped (see A2 in the licence record). Lettering larger than the font's own size is the same rectangles scaled by a whole number (`textBitmap` and `scaledRects` in `pixel-font.ts`, which merge the runs that repeat on the next row, and `UiLayer.scaledText`), which the title's logo uses; `INK.logoOutline` and `INK.logoShade` are its two extra colours. A rectangle of canvas pixels is a `Rect` (`left`, `top`, `width` and `height`, declared in `pixel-font.ts`) wherever the adapter makes one: the rectangles of the letters, the box of a Health bar and of the line of the audio, the cards, maps and links of the Automap, the window of a card and the box of the title's name.
- **Looking at it.** The drawing is not tested automatically. Open the dev server with `?debug`, start a New Game (see Looking at the running game), and use `gameCore` in the console to set a scene up (a `snapshot()` with more Gear or Health, then `send({ type: 'continue', snapshot })`), then look at the page: the HUD, the pages, the level-up choice, a pickup and the out-of-ammunition notice.

## Audio

- **What plays.** Music: one track each for the title, the five Adventure Areas, the fight with the Guardian and the ending. A track plays over and over until another is wanted, changes with a cut and no fade, and is the only one playing. Effects: sixteen short sounds for what happens (the swing of the sword, the shot of the bow, a monster or the hero hit, a monster defeated, a pickup, a new level, a Checkpoint lit or the vessel prepared, the hero defeated, a page opened or closed, a choice made, a Healing Potion used, a refusal, the weapon switched, the Guardian defeated). Both come from the Ninja Adventure pack (CC0, entry A1 of `docs/assets/licences.md`), copied in unchanged under `public/audio/music/` (`.ogg`) and `public/audio/sfx/` (`.wav`): 24 files, 12.6 MiB. The game has no voice acting.
- **The audio manifest** (`src/adapter/audio-manifest.ts`) is where sounds are named and chosen, with no Phaser in it. `AUDIO` registers each sound by name (`music-title`, `music-area-<area id>`, `music-fight`, `music-ending`, `sfx-<effect>`) with its file and its base volume, how loud it is before the player's volume; the tracks of the pack differ in loudness by as much as 15 decibels, so each track has the volume that brings its average level to about the same, and all the volumes are guesses to be checked by ear (`docs/playtest-checklist.md` has the tables to check them against). `trackFor` says which track a place wants, and `sfxFor` says which effect an event of the Game core is heard as, or `null` for an event that is silent on purpose. Its switch names every event, so an event added to the core without a decision there does not compile. `neededAudio` names every sound the content needs, so an area added without music is refused at start-up, by name. **To change a sound,** copy the new file in unchanged, change its entry, and say so in the licence record in the same commit: `tests/shipped-audio.test.ts` goes red when the files, the manifest and the record disagree.
- **Events make the effects, and the place makes the music.** `GameAudio` (`src/adapter/audio.ts`) is the one class that holds Phaser's sound manager. Each frame the play scene hands it the events of the frame, and each distinct effect plays once, however many events call for it (two `level-up` events in one step are one fanfare). The question whether to sail home has no event of its own, so opening it is heard as a page opening, and turning it down as a page closing, from the views before and after the frame (`effectsOfFrame`). The music is a state, not an event: the scenes tell `GameAudio` the place (the title, an area with the fight on or off, the ending) and it plays that place's track, ending the one before. The fight begins with the new event `guardian-engaged` (the Guardian leaves idle: the core works it out from its action, nothing new is saved, and `SNAPSHOT_VERSION` stays 4), and it ends when the Guardian or the hero falls, the hero comes into another area, or the game ends (`fightAfter`). The core gained four events for the audio: `page-opened`, `page-closed`, `stat-point-assigned` and `guardian-engaged`.
- **When it starts.** A browser keeps sound locked until the player has done something. No music is asked for until the player's first input (a key or a click, seen by a listener on the window) and Phaser has unlocked the sound, and an effect asked for while it is locked is dropped, not kept for later: the very first Enter on the title may be silent. Nothing waits for the sound: if it never unlocks, the game plays on in silence.
- **The player's settings.** N turns the sound off and on, and - and + (the keypad's too) make it quieter and louder, in ten steps; either turns a muted sound back on. The sound starts on, at 6 of 10. A line at the top right of the screen, over the pages and the cards (at the bottom right on the title, whose name runs across the top: `TITLE_LINE_CORNER` in `src/adapter/title-layout.ts`), says what the last key did (SOUND OFF, SOUND ON or VOLUME 6/10) for one and a half seconds (`AudioLine`, `src/adapter/audio-line.ts`), and the title says which keys. A key held down changes the settings once, and one pressed with Ctrl or Meta is the browser's own. `checkAudioKeys` (in `src/adapter/controls.ts`, given Phaser's table of key codes, and tested in `tests/controls.test.ts`) runs at start-up and throws, naming the key, when a key of the sound is also bound to anything else. The main row's - and = of Firefox, and of keyboards whose - and + are elsewhere, are not mapped: N and the keypad work everywhere.
- **The settings are not the save.** They are the JSON text `{"muted":false,"volume":6}` under the localStorage key `island-adventure-rpg:audio-settings` (`AUDIO_SETTINGS_KEY` in `src/adapter/audio-settings.ts`), in a slot of their own, so that a New Game, Continue and a damaged save leave them alone and a change of them never writes the saved game. Nothing is written until a key of the sound is pressed. `parseAudioSettings` is the one gate between the text and the game: it mends the text field by field (a volume is rounded to a whole step and held between 0 and 10, a field of the wrong kind has its default, and text that is not an object, or not JSON, gives both defaults) and it never throws. `createAudioSettingsStore(storage)` never throws either: with no storage, which a browser may block, it gives the defaults and `write` says false, and the keys still work for as long as the page is open. `changeSettings` is the rule of the three keys, pure.
- **What the browser cannot play.** The music is `.ogg` only. A browser that cannot play it, such as an older Safari, gets one console warning, "This browser cannot play the game's music (ogg), so the game runs without them.", and plays on without music: there is no MP3 to fall back on. The effects are `.wav`, which every browser plays.
- **Loading.** The first scene (the title) loads all 24 files before it shows, from `audio/` under the site's base like the art, so the game works from any path, and the other scenes find them in Phaser's cache. There is no loading bar. A sound that did not load is named when the scene is created, as a picture is (`requireLoaded`).
- **The tests.** `tests/audio-events.test.ts` is at the Game core's interface: the events that the audio listens for and when the core gives them. `tests/audio-settings.test.ts` is the exception of ADR 0002 for the settings: the parse of every kind of stored text, the three changes, and the store over a storage in memory that can fail (`tests/memory-storage.ts`). `tests/shipped-audio.test.ts` reads `public/audio/` and the licence record from disk, like `tests/final-art.test.ts` does for the pictures: the shipped content gets every sound it needs, every file is there in its format (an Ogg or a WAV), nothing else is shipped, every file is named in the record, and none is from the pack's voice folder. Not tested automatically: what it sounds like, the unlocking, and the playing, since Phaser cannot run in Node.
- **Looking at it.** Open the page with `?debug` to read the sound manager as `window.gamePhaser.sound` in the console: `getAllPlaying()` is what plays, and `mute`, `volume` and `locked` are its state. Press a key on the title (the title's track plays once the sound is unlocked), start a game and walk east through the areas for their music, fight to hear the effects, and press N, - and +. Reload the page: the settings are as they were. For the fight and the ending, set the scene up as The Guardian and The harbor and the ending say.

## How the tests work
The Game core's interface is the test seam for every rule (see `docs/adr/0002-game-core-interface-is-the-test-seam.md`). Commands go in with `send`, time goes in with `step` (one fixed step is 1/60 s), and everything comes out as the return values of those calls, `view()` and `snapshot()`. Tests never look inside the core, never need Phaser, and are deterministic: time moves only when a test steps the game, and the random source is passed in. Beside the seam, `docs/adr/0005-adapter-and-disk-tests-beside-the-seam.md` allows three more kinds of test, each named below: the adapter's pure functions, called directly (they are in modules that import Phaser only as a type); the files the game ships, read from disk where the code depends on a property of them; and the parts of Phaser that code needs (its keys, the rectangles it draws with), behind a small interface that a test fills with plain objects. No test replaces the Phaser module, and nothing tests what only a browser can show.

- `tests/fixtures.ts` builds a small arena whose numbers can be worked out by hand. Expected values in tests are such hand-worked examples, never the rule run again, and test names use the glossary's words. For the bow it has `WITH_BOW` (starting Gear with a bow) and `cacheAt`; for pickups `pickupAt`; for drops `newGame` takes the random source, and `scriptedRandom` (fails if the game asks for a value nobody scripted) and `seededRandom` make one, while the default `fixedRandom` always says 0.5. `tests/cellar-fixtures.ts` adds a cellar with an exit each way (`world`, the arena and the cellar, and `CELLAR` for the wide field of `tests/enemy-fixtures.ts`) to the tests that move the hero between Adventure Areas.
- A new rule starts as a failing test that creates a game with `createGame`, sends commands, steps, and asserts on the view, the events or the snapshot. Rules are tested against fixtures, so retuning the real content does not break them. `tests/drops.test.ts` is an example for what a defeat leaves behind: a drop that comes when the roll is below its chance, not before the monster is defeated, once only, by a strike or an arrow, and the loader's refusals of a table that makes no sense.
- `tests/shipped-content.test.ts` checks the real content with generic validity checks only (it loads, the hero can start and walk, there are six Levels, no monster can hurt a hero who stays at the start, the hero starts with a sword and armor and no bow, the game holds better Gear for each slot in a chest, a cache of Ammunition, and Healing Potions in a chest and on the ground, while some monster type can drop each, and the Automap of the real route: only what is around the start is known, the way out of the first area is marked before the hero reaches it, and the next area shows when the hero crosses into it).

## Keeping the core independent

`tsconfig.core.json` type-checks only `src/core` and `src/content`, with no DOM or Node typings and no way to resolve other modules. A file there that imports Phaser or the adapter, or touches `window`, `document`, `localStorage`, timers, `performance`, `console` or `AudioContext`, fails `npm run typecheck`. Two things the compiler cannot see stay review rules: `Date` and `Math.random` are part of the language, so the core must read no clock and take randomness only from the `random` option; and the content may import only types from the core.

## Conventions

- **Content is data.** Maps, hero numbers, monsters and Gear live in `src/content` and are handed to `createGame`, which checks them and refuses anything invalid. The core holds no numbers of its own.
- **Units.** Positions and sizes are in tiles; a body's position is its centre. The adapter's tile size is one constant, `TILE_SIZE` in `src/adapter/config.ts`, and `px` there turns a number of tiles into whole canvas pixels for everything that is drawn.
- **State is plain data** that survives `JSON.stringify` and `JSON.parse`. World state is kept per Adventure Area. `snapshot()` and the `continue` command save and restore a game, and the adapter keeps the snapshot in the browser (see Saving, Continue and the title).
- **Events are for presentation** (a swing, a hit, a defeat). The view is the truth; no rule depends on an event being seen.
- **Part of the world is still drawn as shapes**: the telegraphs and strikes of the monsters' attacks (`src/adapter/art.ts`); the flat colours of the ground and the monsters are for an area that is added without its art. The hero, its weapons and arrows, the HUD, the pages and the notices, the five areas with their monsters, and the chests, pickups, Checkpoints, exits, doors, gates, levers and signs of every area, and the old vessel of the harbor, already use pictures (see Art).
- **Looking at the running game.** Open the page with `?debug` in the URL to expose the Game core as `window.gameCore`, for example `gameCore.view()` in the browser console. Nothing in the game uses it. The running Phaser game is exposed the same way as `window.gamePhaser`, to read what sound is playing (see Audio). The game opens on the title: `gameCore.view()` is `{ phase: 'title' }` until a game is started with Enter; a New Game then holds on the card of the opening until Enter again (the core is already in play by then, and nothing steps).
