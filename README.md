# Island Adventure

A short top-down action RPG for desktop browsers, built with Phaser: a castaway crosses an island to sail home. The plan is in `.scratch/island-adventure-rpg/spec.md`, the vocabulary in `GLOSSARY.md`, and the decisions in `docs/adr/`.

## Run it

You need Node.js and npm. Install once with `npm install`; the dependency versions are pinned exactly.

| Command             | What it does                                                                     |
| ------------------- | -------------------------------------------------------------------------------- |
| `npm run dev`       | Starts the Vite dev server with hot reload. Open the URL it prints.              |
| `npm run build`     | Builds plain static files into `dist/`. Any static host will do; there is no server. |
| `npm run preview`   | Serves the `dist/` build locally.                                                |
| `npm run typecheck` | Type-checks twice: the core-only config first, then the whole project.           |
| `npm test`          | Runs the Game core tests with Vitest. No browser is needed.                      |
| `npm run check`     | Typecheck, then test, then build. It must pass before any change is merged.      |

On Windows PowerShell, `npm` and `npx` can be blocked by the execution policy: use `npm.cmd` and `npx.cmd`.

## Controls

| Key                    | Action                                                                          |
| ---------------------- | ------------------------------------------------------------------------------- |
| W A S D or arrow keys  | Walk. The hero faces the direction pressed last.                                |
| Space                  | Attack with the weapon in hand, in the facing direction: the sword strikes, the bow shoots one arrow. One attack per press, then a short cooldown. |
| Q                      | Take the other weapon in hand, the sword or the bow. It takes no time. It does nothing until a bow is equipped. |
| C                      | Open the stat page: Level, Experience, Health, Attack and Defense.              |
| I                      | Open the inventory: the Gear the hero carries and which pieces are equipped, the Ammunition and the Healing Potions, and the keys it holds. |
| M                      | Open the Automap: every Adventure Area on the route, what the hero has discovered of each, where it is, and the exits it has found. |
| E                       | Interact with what is right in front of the hero: open a chest or a cache, open a locked door with the key the hero holds, pull a lever, or read a sign. A loose pickup or a key needs no press: walk onto it. |
| Up, Down (or W, S)     | At the title: choose New Game or Continue. In the inventory: move along the list, the Gear and then the Healing Potion line below it. The hero does not turn. |
| Enter                  | At the title: choose the highlighted line, or replace the saved game when New Game asks. On the card of the opening: begin. In the inventory: equip the piece on the highlighted line, or use a Healing Potion on the potion line. |
| Esc                    | At the title: keep the saved game when New Game asks to replace it. Otherwise close the open page. |
| 1, 2, 3 (or keypad)    | At a level-up, put the Stat Point into Health, Attack or Defense. The choice is final. |

The game opens on the title screen (see Saving, Continue and the title below), and a New Game goes on to the card of the opening (see The opening below). It waits on that card until Enter, while a page is open, while a level-up choice waits, and while the browser tab or window is not focused.

## Project layout

```
src/
  core/      The Game core: every gameplay rule, headless. Its public face is core/index.ts.
  content/   The game's content as plain data: terrain, hero, monsters, Gear, areas.
  adapter/   The Phaser adapter: keys to commands, the fixed-step loop, drawing, the art pipeline (asset manifest, loader and
             the hero's sprite), the HUD, the overlay, the Automap page, the inventory cursor and the notice (what was found,
             a Checkpoint touched, a door that is locked or opened, a lever pulled, or that there is no Ammunition), the title scene, the card of the opening, the autosave rule and the saved game's
             parser and store. It holds no rules.
  main.ts    The composition root: builds the Game core from the content and starts the adapter with the browser's storage.
tests/       Vitest tests of the Game core's interface, and fixtures.ts, a tiny arena to test in.
public/art/  The art pack's picture files that the game shows, each one listed in docs/assets/licences.md.
docs/adr/    Decision records.
```

Dependencies point one way: `main.ts` uses the adapter, the content and the core; the adapter uses the core; the content imports only types from the core; the core imports nothing outside itself. Import the core through `core/index.ts`, never from the files behind it.

## Monsters, damage and defeat

- **Behaviors.** A monster type in `src/content/monsters.ts` names a `behavior` and gives the numbers that behavior needs; several types can share one. The behaviors are a small registry in `src/core/behaviors.ts`: `stationary` stands still, and `chaser` notices the hero, walks up, winds up a telegraphed attack, strikes, and rests before it can wind up again. To add a behavior, follow the three steps at the top of `behaviors.ts` (a definition plus a `loadMonsterType` case in `src/core/content.ts` that checks its numbers, a step function, a registry entry); the compiler refuses one that misses a place. Two more, `charger` and `ranged`, are described under Chargers and ranged attackers below.
- **A chaser's numbers** are monster type fields. Distances are in tiles from the monster's body, times are in milliseconds: `damage`, `speedTilesPerSecond`, `noticingDistance`, `reach`, `windUpMs` (at least one fixed step), `recoveryMs`, with `health` and `size`. The attack zone is the square around the body that `reach` describes. It is fixed when the wind-up starts and is in the view (`action` is `winding-up`, with `zone` and `progress`); the damage lands when the wind-up ends, and only if the hero overlaps the zone then. There is no line of sight and no pathfinding: a chaser walks straight at the hero and stops at what is in the way.
- **Hero numbers.** `health` (the maximum) and `defense` in `src/content/hero.ts`; `minimumDamage` (default 1) on the content itself. A hit takes off its damage minus Defense, never less than `minimumDamage`. Health never comes back by itself.
- **Defeat.** At 0 Health the core emits `hero-defeated` in that same step and `recoverHero` in `src/core/checkpoints.ts` puts the hero back at the Checkpoint it touched last (the start of the adventure before it has touched any) with full Health, and resets the monsters of that Checkpoint's Adventure Area to full Health at their starting places, defeated ones included; the other areas stay as they are. `hurtHero` in `src/core/hero-damage.ts` is the one caller. Arrows in flight are removed too. The Ammunition and the Healing Potions go back to what the hero had at the Checkpoint, and the pickups and caches taken since are back; the Gear, the weapon in hand, the Experience, the Stat Points and the opened chests of Gear are left as they are. All of it is under Checkpoints below. The adapter fades the screen in when it sees the event.
- **HUD.** `src/adapter/hud.ts` draws the hero's Health (a heart, "current/maximum" and a bar), its Level, a bar of the Experience towards the next Level, the weapon in hand, the Ammunition and the Healing Potions, from the view and nothing else, fixed to the screen. It is a panel of the pack's art with pictures and the project's own bitmap font on it (see Art below). `HUD_WIDTH` and `HUD_HEIGHT` are a deliberate pair of numbers, 88 by 46 canvas pixels, so growing the HUD is a decision; `HUD_BOTTOM` is the canvas pixel row where its panel ends, and what is drawn below the HUD (the area text) follows it. The HUD covers the top left of the screen, so every Adventure Area, whatever its size, keeps that corner solid, so that the hero can never stand where it cannot be seen: `COVERED_CORNER` (6 by 3 tiles) in `src/core/covered-corner.ts`. `createGame` checks it for content that sets `checkCoveredCorner: true` (the shipped content does; the small arenas of the tests do not), refusing an area that has a walkable tile in it. The adapter's `checkHudFootprint` refuses to start the game when the HUD is bigger than that corner. **A new area must keep its top-left 6 by 3 tiles solid.** The shipwreck coast has water there, in rows 0 to 2.

## Experience, Levels and Stat Points

- **Experience.** Each monster type has an `experience` value (`src/content/monsters.ts`) that the hero earns every time it defeats one, a monster that a defeat reset included. A milestone is ground in an Adventure Area (`milestones`, in `src/content/areas/`) that gives its `reward` once: the first time the hero's body overlaps its `zone`, a block of whole tiles. That it was reached is kept with the area, so it survives a defeat and a snapshot. The reward is separate from the zone so that later rewards can sit beside Experience.
- **Levels.** `levelThresholds` in `src/content/progression.ts` is the total Experience for Level 2, Level 3 and so on. The highest Level is one more than the number of thresholds, so the five shipped give Level 6, and Experience past the last threshold is not counted. The Level is worked out from the Experience, never stored.
- **Stat Points.** The hero has one for each Level above 1, and `statPointValue` in the same file is what one adds to Health, Attack or Defense. The points not yet assigned are worked out too (the Level less 1, less those assigned), so there can be no more and no fewer than one per Level. A Health point raises the current Health by as much as the maximum. Every stat is worked out in `src/core/stats.ts`: no rule reads a base number from the content, and Gear adds its bonus there too (see below).
- **The numbers are placeholders**, picked so that the way out of the shipwreck coast (two crabs on the way and the broken mast, 15 Experience) gives Level 2, and clearing the whole coast still leaves the hero short of Level 3. The woods go on from there: a hero who fights what it meets on the sand trail (a wolf, a slime, a spitter and a boar, and the old oak that gives 5) has Level 3 by the exit forward, and one who clears the coast and all the woods is still short of Level 4. The mountain goes on from there: a hero who fights what it meets on the sand trail (two raiders, a charger, an archer, the veteran and the high gap, 22 Experience) has Level 4 by the exit forward, and one who clears the coast, the woods and the whole mountain is still short of Level 5. The cave goes on from there: a hero who fights what it meets on the sand trail (two bats, a lizard, an eye, the bear and the deep shaft, 20 Experience) has Level 5 by the exit forward, and one who clears the coast, the woods, the mountain and the whole cave is still short of Level 6. Tuning them is for a later pass.
- **Events** `experience-gained`, `level-up` (one for each Level reached) and `milestone-reached` are for presentation. The view's `levelUp` is the truth about a choice that waits.

## Pages and the pause

- **A page** is shown over the game, one at a time: the stat page, the inventory and the Automap. Which page is open is core state (`page`: a page id, or none), changed by the `open-page` and `close-page` commands; the view's `page` holds what to draw. A snapshot taken with a page open restores it open.
- **To add a page,** add its id to `PAGE_IDS` in `src/core/state.ts`. The compiler then points at what is missing: the page's view in `src/core/interface.ts` and `src/core/view.ts`, its key in `src/adapter/player-input.ts` and its drawing in `src/adapter/overlay.ts`. The Automap is the exception: it has a class of its own, `src/adapter/automap-page.ts`, so its case in the overlay draws nothing.
- **The pause.** The game waits while a page is open or a Stat Point waits to be assigned (`isPaused` in `src/core/pause.ts`): `step` advances nothing, `attack`, `interact` and `switch-weapon` do nothing, and `open-page` is ignored, so a page is closed before another opens. `move` and `stop` still keep track of the keys that are down, so the hero does not walk on by itself afterwards. They also turn the hero, so the adapter holds back the walking keys while the game waits, and sends the ones that are down when it stops waiting: the arrow keys of a menu do not turn the hero, and a key held through a page walks on when the page closes. The level-up choice cannot be closed. Several at once are asked one after another, the lowest Level first.
- **An unfocused tab** is the adapter's business, not the core's. `FixedStepClock` in `src/adapter/fixed-step.ts` is told every frame whether the player is watching (`document.hasFocus()` and the tab not hidden, read in `play-scene.ts`). While nobody is, it runs no steps and forgets the time that passed, so the game does not rush to catch up.
- **The overlay.** `src/adapter/overlay.ts` draws the level-up choice, the open page and a PAUSED notice from the view, in windows over the dimmed game: the pack's orange frame round a dark panel, with an icon on each line of Gear and each consumable, the cursor's line on the pack's orange button, and a tick behind the Gear that is equipped. The inventory has two columns, the Gear on the left and, on the right, the Ammunition, the Healing Potions, the keys the hero holds (two at a time, then a count of the rest) and the stats. Its text uses the bitmap font, which has the capital letters, the digits and a few signs: add a glyph to `pixel-font.ts` before using a new character.

## Connected areas and the camera

- **Areas are joined by data.** An area in `src/content/areas/` lists its `entrances` (an `id` and the `tile` the hero stands on when it arrives) and its `exits` (an `id`, a `zone` of whole tiles inside the map, and `to: { area, entrance }`). When the hero's body overlaps an exit's zone, the core emits `area-changed` and puts the hero at the centre of the entrance tile; the way it faces and the keys held carry on. Loading refuses an area with no entrance, an exit to an area or an entrance that does not exist, an exit to an area that has no exit back, an entrance on solid ground or inside an exit zone of its own area (it would send the hero straight back), and an id used twice. To add an area, write its file in `src/content/areas/`, add it to `areas` in `src/content/index.ts`, and give it an exit each way: no rule changes. The shipwreck coast (`shipwreck-coast.ts`, 40 by 18 tiles), the woods (`woods.ts`, 48 by 28 tiles), the mountain (`mountain.ts`, 44 by 30 tiles), the cave (`cave.ts`, 48 by 34 tiles) and the castle (`castle.ts`, a small stub that holds the way in, its Checkpoint and the way back until the castle ticket fills it) are joined this way, in that order on the route.
- **Every area keeps what happened in it:** monsters defeated or hurt, chests and Ammunition caches opened, milestones reached. The monsters of the area the hero leaves are calmed (idle, with their place and Health kept), and nothing in an area moves while the hero is away. The hero's arrows in the air are removed when it goes through an exit (`crossExits` in `src/core/areas.ts`); they fly their last step first, so one that reaches a monster on that step still hits, and the Ammunition spent on them is not given back. A defeat resets only the monsters of the area of the Checkpoint it returns the hero to, which can be another area than the one where the hero fell (see Checkpoints below).
- **Area text.** An area's optional `text` is shown the first time the hero comes into it, and the start area's as the game begins (after the card of the opening, if there is one: no step runs while it shows, so the text's time starts when it ends); `areaTextMs` (content, default 4000) is how long. The core times it: the view's `areaText` holds it while it shows, the `area-text` event announces it, a page or a Stat Point that waits freezes its clock, and it never comes back on a later visit. It does not pause the game. `src/adapter/area-banner.ts` draws it under the HUD, starting a few pixels below `HUD_BOTTOM` (see the HUD above), with the bitmap font, so write it with letters, digits and `/ + - : . !` only.
- **The camera** (`src/adapter/camera.ts`) follows the hero in whole pixels and stops at the area's edges, so there is no empty space beyond the map. The canvas is 20 by 12 tiles (`VIEW_TILES_*` in `src/adapter/config.ts`): the coast, the woods, the mountain and the cave are larger and scroll, and an area smaller than the canvas sits in the middle with black around it. The HUD, the area text, the notice and the overlay stay fixed to the screen. Exits are marked by chevrons painted on the ground, one to a tile and pointing to the nearest edge of the area (`src/adapter/prop-sprites.ts`), and the screen fades in briefly when the hero comes into another area. The core's interface has nothing for the camera.
- **The tests.** `tests/area-connections.test.ts` pins the rules on fixtures, the arrows in the air and the Ammunition caches among them; `tests/shipped-areas.test.ts` checks the real areas (they join both ways, the woods are larger than the canvas, the hero walks from the coast into the woods, on into the mountain, the cave and the castle, and back, every tile that is not solid can be reached, a chest being solid like rock and with room beside it, nothing lies on an entrance, the covered corner is checked, and no monster notices the hero where it arrives); `tests/camera.test.ts` and `tests/area-banner.test.ts` cover the pure parts of the adapter.

## Gear, the inventory and chests

- **Gear** is content (`src/content/gear.ts`): each piece has an id, a `name`, a `slot` and a `bonus`. A slot raises one stat (`GEAR_SLOT_STAT` in `src/core/definitions.ts`): a melee weapon or a ranged weapon adds to Attack, armor to Defense, and Gear changes nothing else. The hero begins with a basic sword and basic armor (`startingGear` in `src/content/hero.ts`), both with a bonus of 0 so that the base numbers stand. The shipped upgrades are placeholders for the tuning pass: the Steel Sword and the Chain Mail add 1, the Plate Armor that the hero finds in the mountain adds 2, the Katana that the hero finds behind the gate of the cave is a sword that adds 2, and the Short Bow and the Long Bow add 1 and 2.
- **Carrying and equipping.** The hero carries every piece it finds, with no limit, and has one equipped in each slot. Each piece exists once: the content is refused if two chests, or a chest and the starting Gear, hold the same piece. There is no unequip, only a swap for another piece of the same slot. `src/core/stats.ts` adds the bonuses of the equipped pieces to Attack and Defense after the Stat Points, so the stat page, the damage of an attack and the damage the hero takes all follow. A weapon's bonus counts only for the attacks made with it, the sword's for strikes and the bow's for arrows, so the stat page and the inventory show the Attack of the weapon in hand.
- **To add a slot** (a helmet, say), add it to `GEAR_SLOTS` and to `GEAR_SLOT_STAT` in `src/core/definitions.ts`; the compiler refuses a slot that is missing from the map. A slot that holds a weapon is a `WEAPON_SLOTS` entry too, and `heroAttacks` and `switchWeapon` in `src/core/weapons.ts` then say how it attacks and how it is taken in hand.
- **The inventory** is a page, `inventory`. Its view lists the carried Gear, by slot and then in the order found, each with whether it is equipped, the Attack and Defense totals, how many of each consumable the hero has (the Ammunition and the Healing Potions) and the keys it holds, in the order it took them (`keys`, see Light puzzles and clues). The `equip` command takes a piece's id and works only while the inventory is open; it does nothing for a piece the hero does not carry or already has equipped. Choosing the piece is the adapter's job: `src/adapter/inventory-menu.ts` keeps the cursor (Up and Down, or W and S, without wrapping; it runs over the Gear, five lines showing at a time, and then to the Healing Potion line below), Enter sends `equip` for a Gear line and `use-healing-potion` for the potion line (see below), and Esc closes the page. The page shows the hero's Health too, so that what a potion did can be seen.
- **Chests** are interactables: things in an Adventure Area that the hero acts on with E (the `interact` command), listed in the area's `interactables` (the shipwreck coast's are in `src/content/areas/shipwreck-coast.ts`). A chest has an id, a tile and its contents, a tagged union: `{ kind: 'gear', gear: <id> }`, or `{ kind: 'consumable', consumable: <id>, amount: <n> }` for a cache, a chest of a consumable (see below). Interact acts on the nearest interactable in the ground right in front of the hero, as far as `interactionReach` (`src/content/hero.ts`) and as wide as the hero's body; when two are as near, the one listed first. It does nothing while the game waits. A chest opens once: the hero picks up what is inside, and the core emits `chest-opened` and `pickup`. That a chest was opened is kept per Adventure Area in the state, so it survives a snapshot, and a defeat too when it holds Gear (a cache is closed again by a defeat that goes back to before it was opened: see Checkpoints). Chests are solid, opened or not.
- **To add a kind of interactable** (the devices of the light puzzles were added this way), follow the steps at the top of `src/core/interactables.ts`: a definition, a state, a function that says what it does, and an entry in the `INTERACTIONS` registry. The compiler refuses a kind that is missing from the registry or from the views.
- **The notice.** The adapter shows one notice at a time for a few seconds (`src/adapter/notice.ts`), the latest of these: a `pickup` (what was found, what it adds, and a hint to press I; for a key, that it opens a door), `out-of-ammunition` (see below), `checkpoint` (see Checkpoints), `door-locked`, `door-opened` and `lever-toggled` (see Light puzzles and clues) and `save-failed` (see Saving, Continue and the title). A page or a Stat Point that opens covers it and ends it, and so does a defeat. A new kind of find needs its lines in `pickupLines` there, and its picture in `iconFor`. Chests, caches, pickups, keys, doors, gates, levers, signs and Checkpoints are drawn by `src/adapter/prop-sprites.ts` (see Art).

## The bow, Ammunition and drops

- **Two weapons, one in hand.** The sword is in the melee weapon slot and a bow, once found and equipped, in the ranged weapon slot. The weapon in hand (`activeWeapon`, one of those two slots, in the hero's view) starts as the sword. Q sends `switch-weapon`: the sword to the bow and back. The bow can be taken in hand only while one is equipped, and the sword is always there to go back to. Switching takes no time, leaves the cooldown alone and does nothing while the game waits; equipping a bow does not take it in hand. `attack` goes through `heroAttacks` in `src/core/weapons.ts`: a strike with the sword, a shot with the bow. Both wait for the same attack cooldown and start it, and nothing is spent but the Ammunition.
- **A shot** costs one Ammunition and sends an arrow from the hero's centre in the direction it faces (`hero-shot`). With none left nothing is shot and the cooldown does not start: the core emits `out-of-ammunition` (once the cooldown is over), and the adapter's notice says so and hints at Q. The numbers are `rangedWeapon` in `src/content/hero.ts`: `arrowSpeedTilesPerSecond`, `range` (the tiles an arrow flies before it is gone) and `arrowSize`, at most the hero's size.
- **Arrows** are state: each has its Adventure Area, position, direction and the range it has left, and the view's `arrows` gives the position, direction and size to draw. `flyArrows` in `src/core/arrows.ts` moves them each fixed step, after the hero walks and before the monsters act. An arrow hurts the first living monster it reaches (a monster that walks into one is hit too) and is gone; solid terrain and chests stop it, and so does a spent range. The damage is the Attack of the bow (base, Stat Points and the bow's bonus), worked out when the arrow arrives. Arrows wait while the game waits and fly only in the Adventure Area they were shot in; a defeat removes them, and so does the hero going through an exit.
- **Ammunition is a consumable.** The hero's `consumables` count each kind (`CONSUMABLE_IDS` in `src/core/definitions.ts`: there are two, `ammunition` and `healing-potion`, and the hero starts with none of either), and `grantConsumable` in `src/core/consumables.ts` is the one way to give some. To add a kind, add its id there and follow the compiler to its starting count (`src/core/state.ts`), its name (`src/adapter/labels.ts`) and its look as a cache and as a pickup (a frame of `prop-chest` and of `prop-pickup`, chosen in `src/adapter/prop-sprites.ts`; the sheets are made by `docs/assets/compose-art.py`).
- **Caches.** A cache is a chest whose contents are a consumable, `{ kind: 'consumable', consumable: 'ammunition', amount: 6 }`. It opens once like any chest, and the hero takes the amount (`pickup`). The chest in the view says what it holds (`holds`: `'gear'` or the consumable's id), which is how the adapter draws a crate of arrows. The two caches of six stand along the sand trail of the woods, soon after the bow chest (`arrow-cache-1` and `arrow-cache-2` in `src/content/areas/woods.ts`): the coast has neither, because the first bow belongs in the woods. The mountain has two more of six a few steps off its trail (`mountain-arrow-cache-1` and `mountain-arrow-cache-2` in `src/content/areas/mountain.ts`) and a cache of eight at the end of its side path. The cave has three of six a few steps off its trail (`cave-arrow-cache-1` to `cave-arrow-cache-3` in `src/content/areas/cave.ts`) and a cache of eight in the grotto at the end of its side path.
- **Drops.** A monster type can have a `drops` table (`src/content/monsters.ts`), a list of `{ consumable, chance, amount }` with `chance` from 0 to 1. When the hero defeats a monster, with a strike or an arrow alike, `rollDrops` in `src/core/drops.ts` rolls each entry once, in order, with the game's `random` option, which the rules use for nothing else. An entry drops when its roll is below its `chance` (so 0 never drops and 1 always does), and the roll is made whatever the chance is, so retuning one does not shift the rolls after it. What drops goes straight into the hero's count, with a `pickup` event: nothing lies on the ground. A type without a table asks for no roll. The crab leaves a Healing Potion about one time in seven (15 in 100) and no arrows: it meets a hero who has no bow yet. The spitter, which shoots them, leaves 2 arrows one time in four. These are placeholders for the tuning pass.

## Chargers and ranged attackers

- **Two more behaviors,** `charger` and `ranged`, sit in the registry beside `chaser` and are data in the same way: a monster type names the behavior and gives its numbers, so a tougher or faster variant is another type in `src/content/monsters.ts` and no rule changes. The shipped ones are `boar` (a charger) and `spitter` (a ranged attacker); the woods have one of each beside their wolves and slimes, and the coast, which teaches the controls, has crabs only. The raiders of the mountain are four more types of those behaviors, tougher than the beasts of the woods: `raider` and `raider-veteran` (chasers), `raider-charger` (a charger) and `raider-archer` (a ranged attacker). The veteran is the tougher variant, 12 Health against 5 or less, with a heavier hand and a Healing Potion that it sometimes drops; it holds the shaft below the summit, and five raiders watch the sand trail while a sixth guards the side path. The creatures of the cave are four more types, the cave's own: `cave-bat` (a chaser, frail and quicker than any other), `cave-lizard` (a charger), `cave-eye` (a ranged attacker that does not move and carries the arrows it shoots) and `cave-bear`, the tougher variant, 14 Health against 6 or less, with a hit of 9 and a Healing Potion that it sometimes drops. The bear holds the chamber before the way on, and the second lizard guards the grotto at the end of the side path. The wolf and the slime are variants of the chaser in the same file and need no rule: the wolf is frail and quick (quicker than a crab, slower than the hero) and the slime is slow and sturdy, with a lighter bite. Every number is a placeholder for the tuning pass. Loading refuses a type whose numbers cannot work (a speed, range or size that is not more than 0, a wind-up shorter than one fixed step, a projectile bigger than its shooter) and names the type and the field.
- **A charger** (`src/core/charger.ts`) notices the hero as a chaser does, then works out its lane (`src/core/lanes.ts`): the strip in front of its body, toward the hero along the axis they are farther apart on, as wide as the body and `dashRange` long, cut short by solid terrain and chests. If the hero's body overlaps the lane it winds up with the lane fixed in the view as the telegraph (`winding-up`, whose `zone` is the lane); if not it walks sideways at `speedTilesPerSecond` until the lane takes the hero in, then toward it (a speed of 0 makes it wait for the hero to step in). When the wind-up ends it dashes down that lane at `dashSpeedTilesPerSecond` (`dashing` in the view) whether or not the hero is still in it, and `monster-attacked` gives the lane as its zone. The dash hurts the hero once, for `damage`, only if the hero is in its way, and is stopped by the hero, solid terrain, a chest, another monster or the end of the lane. Then it recovers for `recoveryMs`, standing still, and can be hit freely: no hit interrupts a wind-up or a dash. Its numbers are `noticingDistance`, `speedTilesPerSecond`, `windUpMs`, `dashSpeedTilesPerSecond`, `dashRange`, `recoveryMs` and `damage`, with `health` and `size`.
- **A ranged attacker** (`src/core/ranged.ts`) notices the hero and, if its type has `keepsDistance: { preferredDistance, speedTilesPerSecond }`, walks to `preferredDistance` tiles from it (the gap between their bodies, along the axis they are farther apart on), backing away when it is nearer and winding up where it stands once a wall leaves it nowhere to go; without `keepsDistance` it stands still. It winds up for `windUpMs`, then fires one projectile from its centre along the row or column toward where the hero stands at that moment (the axis the hero is farther along, a tie going horizontal), emits `monster-fired` and recovers for `recoveryMs`. It aims when it fires, so its `winding-up` has no lane to show: its `zone` is its own body, and the adapter flashes it. A hero that has left that row and column by then is missed. Its numbers are `noticingDistance`, `windUpMs`, `recoveryMs`, `projectile: { damage, speedTilesPerSecond, range, size }` and the optional `keepsDistance`, with `health` and `size`.
- **A monster's projectile is an arrow.** It is an arrow in the state with a `shotBy` (the monster and its type, so that it flies on when its shooter is defeated), moved by the same `flyArrows` as the hero's, in the same place in the step. It flies `range` tiles at `speedTilesPerSecond`, is stopped by solid terrain and chests, passes through monsters, and hurts the hero through `hurtHero`, so Defense, `hero-hit` and defeat work as for any hit. The view's `arrows` say who shot each one (`shooter`: `'hero'` or `'monster'`), and the adapter draws a monster's as an orb with a trail (`ProjectileSprites` in `src/adapter/projectile-sprites.ts`), apart from the hero's arrows. A hero defeated by a projectile ends the step there and loses every arrow in flight, as a defeat always does (see the guard after `flyArrows` in `src/core/game.ts`). A Checkpoint the hero came onto in that step was activated before the hit, so the guard reports its `checkpoint-activated` too, and the hero is back on it: a defeat ends the same way whether a bite, a dash or a projectile caused it.
- **No attack is unavoidable.** The charger's lane shows for the whole wind-up and the dash begins only after it, so stepping out of the lane in that time avoids it. The ranged attacker's projectile goes along one row or column and is slower than the hero's walk, so leaving that row and column before the shot, or sidestepping the projectile, avoids it. `tests/shipped-enemies.test.ts` keeps the shipped types that way and keeps both out of the notice of every entrance, the start and every Checkpoint, so the hero never arrives into an attack.
- **The tests.** `tests/enemy-fixtures.ts` is the arena for these suites: `CHARGER`, `SHOOTER`, `KEEPER`, `HEAVY` and `SNIPER` are types to place with `chargerAt`, `shooterAt` and `keeperAt`. `charger.test.ts`, `charger-lining-up.test.ts` and `charger-avoidance.test.ts` cover the wind-up, the lane, the dash, the stop at terrain, the hit and the recovery; `ranged-attacker.test.ts`, `ranged-keeping-distance.test.ts`, `projectile.test.ts` and `ranged-avoidance.test.ts` the same for the ranged attacker and its projectile; `enemy-content.test.ts` that bad numbers are refused and that a variant is data only; `shipped-enemies.test.ts` the real areas; `checkpoint-enemies.test.ts` the two tickets together: a hero defeated by a bite, a dash or a projectile is put back alike, in the area of the Checkpoint or in another, with no wind-up, lane, dash, recovery or projectile of the life before left to hit it, and a lane or a shot over a Checkpoint activates nothing.

## Healing Potions and pickups

- **Healing Potions** are a consumable (`healing-potion`, see above) and the only way the hero gets Health back between Checkpoints: Health never comes back by itself, and a potion is never used on the hero's behalf. The hero finds them three ways: in a chest or cache (`{ kind: 'consumable', consumable: 'healing-potion', amount: 2 }`), lying on the ground as a pickup, and in a monster's `drops` table. The shipwreck coast has a chest of two (`potion-chest`) under the hull of the wreck and a single potion (`beach-potion`) on the beach below it, both a short walk from the start; the woods have a single potion lying on the trail (`woods-potion`) and a chest of two (`woods-potion-chest`) a short walk off it, in the north; the mountain has two on the ground a step off its trail (`mountain-potion-1` and `mountain-potion-2`) and a chest of three at the end of its side path (`mountain-overlook-potions`); the cave has two on the ground a few steps off its trail (`cave-potion-1` and `cave-potion-2`) and a chest of three in the grotto at the end of its side path (`cave-grotto-potions`); the crab drops one 15 times in 100, the veteran of the mountain one time in two, and the bear of the cave one time in two. All of these numbers are placeholders for the tuning pass.
- **Pickups** are interactables of the kind `pickup`, `{ kind: 'pickup', id, tile, consumable, amount }`: some of a consumable lying on a tile. The hero takes it by walking onto it, with no key to press: `collectPickups` in `src/core/pickups.ts` runs in every fixed step right after the hero has walked, takes each pickup its body overlaps that it has not taken, and emits `pickup`. It is taken once, until a defeat that goes back to before it was taken (see Checkpoints); that is kept per Adventure Area in the state, so it survives a snapshot. A pickup is not solid, so the hero, the monsters and the arrows pass over it, and the view's `interactables` list it only while it lies there. The content is refused for a pickup of an unknown consumable, with an amount that is not a whole number of 1 or more, on a tile that is not walkable, or where something else is placed or starts.
- **Using a potion** is the `use-healing-potion` command, which works only while the inventory page is open (`useHealingPotion` in `src/core/potions.ts`). It gives back `healingPotion.restores` (`src/content/healing-potion.ts`: 5 for now, half of the starting Health), never above the hero's maximum Health as it is then, Stat Points counted. The potion is used up even when less than that fits. With none, or at full Health where it would be wasted, nothing happens and there is no event. A use emits `healing-potion-used` with the Health `restored` and the `health` now. `createGame` refuses content whose `restores` is not more than 0.
- **In the adapter.** The HUD shows the potion count beside the Ammunition count, grey at 0. The inventory page gives the potions a line of their own below the Gear, with the Health under it. Down moves the cursor onto that line, Enter there sends `use-healing-potion`, and the page stays open, so Enter again uses the next potion until the Health is full or the potions are gone. A refused use is not explained: the count and the Health line show why. Pickups and potion chests are drawn by `src/adapter/prop-sprites.ts`: the pack's bottle lying on the ground, and a crate with two bottles in it that is empty once opened.
- **Defeat** gives the potions back as they were at the Checkpoint it returns to, and puts the pickups, caches and chests of potions that were taken since back where they were (see Checkpoints below).

## Light puzzles and clues

- **Five kinds of interactable, all data.** Keys that open doors, levers that move gates and signs that give a clue are optional: the way along the route never needs one. They are listed in an area's `interactables` beside the chests, and their rules are in `src/core/devices.ts` (a key here is the item the hero carries, not a key of the keyboard). A `key` (`{ kind: 'key', id, tile, name }`) lies on its tile and the hero takes it by walking onto it: `collectKeys` runs in the step right after `collectPickups`, puts its id in the hero's `keys` and emits `pickup` with an item of the kind `key`. A `door` (`{ kind: 'door', id, tile, key }`) is solid while shut. Interact on it with its key in hand opens it for good, the door takes the key and the core emits `door-opened`; without the key nothing changes and the core emits `door-locked`, with the name of the key to look for. A `gate` (`{ kind: 'gate', id, tile }`) is solid while shut, begins shut and does nothing for Interact: only a lever moves it. A `lever` (`{ kind: 'lever', id, tile, targets }`) is always solid. Interact flips its `pulled` and moves every door and gate it names the other way, so a shut one opens and an open one shuts (`lever-toggled`); a door that a lever opens takes no key. A `sign` (`{ kind: 'sign', id, tile, text }`) is always solid. Interact shows its text as the text of an area is shown (the view's `areaText`, for `areaTextMs`, in place of any text showing) and emits `sign-read`: the game does not pause, and a sign has no state.
- **One-time loot, not a consumable.** A key taken, a door opened, a gate opened and a lever pulled stay as the hero left them when it is defeated (`consumable-rollback.ts` leaves them alone), when it goes through an exit and comes back, and in a saved game: the flags (`collected`, `open`, `pulled`) are in each area's state and the keys held are the hero's `keys`, so all of it is in the snapshot, which is why `SNAPSHOT_VERSION` is 2. A key that a door has taken stays taken, so it never lies on the ground again. `parseSave` refuses a snapshot whose hero holds a key that its area still has lying there (`damaged`). A New Game builds it all fresh: no key held, every door and gate shut, every lever not pulled.
- **What loading refuses.** The message names the area and the device (`src/core/device-content.ts`): a key with no name, a sign with no text, a lever that moves nothing, names a target twice or names one that is not a door or a gate of its own area, a door whose key no area places, a key that no door needs and a key that two doors need. As for any interactable, a device on solid ground, or on the tile of a monster, a Checkpoint, the start or another interactable, is refused too, but one on an entrance or in an exit's zone is not: keep it off them (`tests/shipped-puzzles.test.ts` does for the shipped rooms).
- **The route never needs one.** The hero finds every door and gate shut and may never find the key or the lever, so the way along the route has to be there with all of them shut. `checkRoutesStayOpen` (`src/core/device-routes.ts`) takes each area and each place the hero can be put in it (every entrance, and the start of the game in the area where it begins), and refuses the content when an exit or a Checkpoint can be reached from there with every door and gate open but not with every one shut: a key or a lever is never a way through. Only doors and gates make that difference, since a chest, a lever and a sign are solid either way. What cannot be reached even with everything open (a wall) is the map's business, and content with no door or gate is never refused. The exits and the Checkpoints are the destinations of the route as the core knows it: a ticket that adds another destination adds it to `destinationsOf`.
- **The shipped room** is in `src/content/areas/woods.ts`, in the woods' `interactables` beside the chests, and is not on the way out: a locked cabin in the south-west, with a chest inside that holds the Long Bow (the weapon upgrade of the woods). A sign by its door says that the key is in the north woods, and the brass key lies there, a good walk from the trail. The cabin is the first side path of the game. The first lever and the first gate are in the cave, off the way on: a lever in a niche of the east wall of the middle chamber opens a gate that shuts a pocket of grass in its north wall, with the Katana in a chest (`cave-lever`, `cave-gate` and `cave-weapon-chest` in `src/content/areas/cave.ts`), and a sign by the gate says where to look (`cave-sign`). The pocket is a dead end, so the way on never needs the lever. The covered corner stays solid.
- **In the adapter.** The inventory lists the keys under the consumables, each with the pack's key picture and its name, two at a time and then `+N MORE` (`VISIBLE_KEYS` in `src/adapter/overlay.ts`). The notice tells of a key found (IT OPENS A DOOR), a door that is locked (NEEDS the key's name), a door opened and a lever pulled or put back (`src/adapter/notice.ts`). A sign needs no notice: its text shows in the banner of the area text, so it follows the banner's font rules, and `tests/shipped-puzzles.test.ts` draws every character of the shipped sign. The key, the door, the gate, the lever and the sign are drawn by `src/adapter/prop-sprites.ts` from the pack's pictures (see Art): the gate is the pack's iron arch, with bars between its legs while it is shut, and the lever is a stick and a ball set on a slab of the pack's stone in a niche of the rock, with a red ball on the left at rest and a blue one on the right when pulled.
- **To add a puzzle,** put its devices in an area's `interactables`: no rule changes, and the route rule says if one stands in the way. To add another kind of device, follow the steps at the top of `src/core/interactables.ts`.
- **The tests.** `tests/keys.test.ts`, `doors.test.ts`, `levers.test.ts` and `signs.test.ts` are at the Game core's interface on fixtures (`keyAt`, `doorAt`, `gateAt`, `leverAt` and `signAt` in `tests/fixtures.ts`). `device-blocking.test.ts` pins what a shut device does to the hero's arrow, a walking monster, a charger's dash and a projectile; `device-content.test.ts` and `device-routes.test.ts` the refusals, the second on small halls drawn in the file; `device-persistence.test.ts` a defeat, leaving an area and a saved game. The saved adventure in `tests/saved-adventure.ts` takes the devices through the round trip and the sweeps. `tests/shipped-puzzles.test.ts` plays the shipped room, the cabin, with the core's own walking and Interact, keeps the way out free of it, and checks the two tickets together: a New Game after the puzzles were played starts clean with the opening, and a Continue brings them back with none. A door and a gate count as solid in `tests/routes.ts`, as the hero finds them, and as open in the check of `tests/shipped-areas.test.ts` that every tile that is not solid can be reached, so that the rooms behind them count; no route that `shipped-enemies.test.ts` or `shipped-content.test.ts` walks goes through one. `tests/routes.test.ts` pins both. Not tested automatically: how the devices, the notices and the key rows of the inventory look. Look at them in a browser with `npm run dev`: press Enter on the title and again on the card of the opening, walk east along the coast and through its exit into the woods, and follow the sand trail east and then north-east to the brass key, which lies off it in the north. Take the key, go back to the cabin in the south-west, read the sign, and press E at the door and at the chest. No shipped area has a lever or a gate on the way to the cabin, so pulling a lever is for the play check of the cave (see the tests of the cave below). Walk onto the Checkpoint at the way in of the woods to save, reload and choose Continue: the door and the key are as they were left, and a defeat leaves them alone too.

## Checkpoints and defeat recovery

- **Checkpoints are data.** An area in `src/content/areas/` lists its `checkpoints`, `{ id, tile }`: one tile each, which is not solid. Every area needs at least one, so that a defeat in it can send the hero somewhere safe. The coast has `coast-checkpoint` on the tile where the hero starts, the woods `woods-checkpoint` at the way in from the coast, the mountain `mountain-checkpoint` at the way in from the woods, the cave `cave-checkpoint` at the way in from the mountain, and the castle `castle-checkpoint` at the way in from the cave. Loading (`loadCheckpoints` in `src/core/checkpoint-content.ts`) refuses an area with none, an id used twice anywhere in the content, and a tile that is solid, inside an exit of its own area, or where an interactable or a monster starts, because after a defeat the hero stands at the centre of the tile. To add one, add it to the area's list: no rule changes.
- **Touching one activates it.** In every fixed step `activateCheckpoints` (`src/core/checkpoints.ts`) activates each Checkpoint of the hero's area that its body overlaps now and did not at the start of the step: the hero comes onto it. Standing on it, or being hit on it, does nothing more; a hero who leaves it and comes back activates it again. Activating emits `checkpoint-activated`, restores the hero's Health to full and records what defeat will give back (below). It refills no Ammunition. It comes after the hero has walked and taken the pickups it touched, so a pickup on the way onto a Checkpoint is recorded with it, and before the arrows fly and the monsters act. A Checkpoint at an entrance is activated as the hero comes in: its event follows `area-changed` and `area-text`. The start of the adventure counts as the first Checkpoint without being touched, so a new game, or a game continued from a snapshot, emits no `checkpoint-activated`.
- **Defeat goes back to the last one.** `recoverHero` puts the hero at the centre of the tile of the Checkpoint it activated last, at full Health, and the monsters of that Checkpoint's area are back at full Health at their starting places, defeated ones included. The Checkpoint can be in another area than the one where the hero fell: then `hero-defeated` is followed by `area-changed`, the living monsters of the area where the hero fell are calmed (idle, with their Health kept) as when it leaves by an exit, and the monsters of every other area keep what happened to them, so a monster defeated there stays defeated.
- **What is given back and what is kept.** The Ammunition and the Healing Potions are as many as the hero had at the Checkpoint: what it spent is back, what it found since is gone. Every pickup, cache and chest of potions, in every area, is taken or not as it was then (`src/core/consumable-rollback.ts`), so a cache opened after the Checkpoint can be opened again, its arrows included. What stays is everything permanent: the Level and Experience, the Stat Points already assigned, all the Gear and what is equipped, the weapon in hand, the opened chests of Gear, the milestones reached and the world of the light puzzles: the keys taken and held, the doors opened, the levers pulled and the gates they opened (see Light puzzles and clues).
- **One known edge.** A consumable that a monster dropped is not given back when that monster is in another area than the Checkpoint's: it stays defeated and drops nothing more, so the drop is lost. The monsters of the Checkpoint's own area come back, so their drops can be earned again. This is left as it is on purpose, and `tests/checkpoints.test.ts` pins it.
- **In the adapter.** `src/adapter/prop-sprites.ts` draws a Checkpoint as a pole with a flag (`prop-checkpoint`, 16 by 26 pixels, standing on the bottom of its tile). The pole stands 10 pixels above its tile, so that the flag of the one defeat returns to now (`active` in the view: red, waving at the top of the pole) shows over the hero, who stands on it at the start and after a defeat; the others hang a grey flag half way down, still. The notice says CHECKPOINT and HEALTH FULL for a few seconds when one is touched, and a defeat ends the notice that is on the screen, whatever it is, because it told of what happened before the fall (what was found since the Checkpoint is back where it was).
- **The tests.** `tests/checkpoints.test.ts` builds two-area worlds with numbers worked out by hand: the content rules, touching, arriving on a Checkpoint, defeat in the same area and in another, the monsters, each kind of consumable that is given back, what stays, and a snapshot taken before a defeat. `tests/shipped-areas.test.ts` checks the Checkpoints of the real areas. `tests/checkpoint-enemies.test.ts` takes a charger and a ranged attacker through the same defeat (see Chargers and ranged attackers).

## The Automap

- **What is recorded.** Each Adventure Area keeps `revealed` in the state: a grid of booleans, one per tile (`revealed[row][col]`), all false at the start of the adventure. A tile only ever goes from false to true, so what the hero has explored is never taken back: not by a defeat and the roll-back that comes with it, not by leaving the area. It is part of the plain-data state, so a snapshot carries it. `SNAPSHOT_VERSION` was not raised for it: nothing was saved to disk before the save store (see Saving, Continue and the title), so no save lacks it.
- **When tiles are revealed.** `revealAroundHero` (`src/core/automap.ts`) reveals every tile of the hero's area within `automapRevealDistance` tiles of the hero's tile: a disc, the tile `(c, r)` when `(c - hc)² + (r - hr)² <= d²` with `hc` and `hr` the hero's column and row. There is no line of sight, so a wall or water beside the hero is revealed like ground. It runs at a new game, after the hero has walked in each fixed step, as the hero comes in through an exit, and after a defeat once the hero is back at its Checkpoint, never while the game waits. It sends no event: the view is the truth. `automapRevealDistance` is a number on the content (tiles, 0 or more; 4 if left out, and the shipped content says 4); a value that is not a number of 0 or more is refused.
- **The page.** While the Automap is open, `view().page` is `{ id: 'automap', areas }`, built only then. `areas` has every Adventure Area of the content in the order of `areas` in `src/content/index.ts`, which is the order of the route, and each one has `id`, `name`, `width` and `height`, `current`, `discovered`, `connections` (the ids its exits lead to, shown from the start so the route is known), `hero` (where the hero is, in tiles, only in the current area), `exits` (only the ones found) and `terrain` (the kind of each revealed tile, `null` for a tile not revealed). An area the hero has not been in has no name, no terrain and no hero. A found exit is one with a revealed tile in its `zone`, worked out when the view is built, so a farther distance finds exits sooner. A reveal distance below 1 can let the hero cross an exit before it has found it. There are no quest markers.
- **Adding an area.** Write it and add it to `areas`: it comes on the page in that place with no rule changes. Content that links areas both ways is already required (see Connected areas).
- **In the adapter.** `src/adapter/automap-layout.ts` places the route with plain numbers and no Phaser (`layoutRoute`, `routeLinks`, `tileRects`, `exitRect`, `markerRect`, `fitLabel`), and `src/adapter/automap-page.ts` draws it from the view, over the dimmed game, with the bitmap font (area names must use letters, digits and the signs the font has). Its window is drawn with the same `UiLayer` frames as the other pages (see Art below), under the map and the hero's mark, which are shapes drawn on top of it (the window at depth 199, the map at 200, the mark at 201, the same place as the overlay). Each Adventure Area is a card: its name above its map, the revealed terrain in the terrain colours (`terrainColour` in `src/adapter/art.ts`), undiscovered tiles dark, found exits pale (as in the game), the current area ringed in the title colour of the window, and the hero a mark that blinks gold and white. The cards run along a row in route order and the next row runs back (a serpentine), at the largest scale from 8 pixels a tile down to 1/16 at which the whole route fits; a name too wide is cut and ends in `..`. A link joins two areas next to each other on the route when an exit of one leads to the other: a straight strip in a row, a C round the end of the rows between rows. Links between areas that are not neighbours on the route are not drawn. An area the hero has not been in is a dark box of its true size with the name UNKNOWN.
- **The tests.** `tests/automap.test.ts` is at the Game core's interface on fixtures: nothing revealed before the hero has explored, the disc and its edge, the reveal distance, the hero's position, the route in order, exits found only once, arriving in another area, the page and the pause, a snapshot, and a defeat that takes nothing back, with a three-area route (so a route of more than two areas is covered). `tests/shipped-content.test.ts` checks the real route. `tests/automap-layout.test.ts` pins the pure layout in numbers worked out by hand: the scale ladder, the rows, the pixels of a map, the links and the cut names. Not tested automatically: the colours and the size of the mark, and how it looks. Look at it in a browser with `npm run dev`: press Enter on the title and again on the card of the opening, then M, and walk.

## Saving, Continue and the title

- **The game opens on the title screen.** `TitleScene` (`src/adapter/title-scene.ts`) is the first scene. It offers New Game and Continue in a `UiLayer` window of its own (depth 300 in `depths.ts`). Up and Down (or W and S) move the cursor and Enter chooses. Continue is greyed, and the cursor cannot rest on it, when there is no saved game to continue from; when there is one the cursor starts on it, so that Enter goes on with it. New Game over a saved game asks first (REPLACE THE SAVED GAME?): Enter replaces it, Esc keeps it, and nothing is written until Enter. The rules of the menu are `openMenu`, `selectableEntries` and `pressMenu` in `src/adapter/title-menu.ts`, with no Phaser. New Game sends `new-game` and Continue sends `continue` with the saved snapshot, and then `PlayScene` starts; for a New Game it starts with the card of the opening (see The opening). `gameCore.view()` is `{ phase: 'title' }` until one of them is chosen, so press Enter before using `gameCore` in the console. When the core's view says `title` while the play scene is up, the play scene hands over to the title: that is the way back for the ending of ticket 20.
- **When it saves.** There is one slot and no manual saving. The rule is `callsForSave` (`src/adapter/autosave.ts`): a frame whose events hold `checkpoint-activated` or `area-changed` saves, once, as the game stands at the end of the frame. That includes a defeat that returns the hero to a Checkpoint in another area. A New Game saves at once as well: the start counts as the first Checkpoint without an event, and without that save a tab closed right after a confirmed New Game would bring the old save back. Continue and the title never save. The slot holds the game as it was at the last Checkpoint or area change, not as it is now: reload, choose Continue, and the hero is back there.
- **The slot.** It holds the JSON text of one `Snapshot` under the localStorage key `island-adventure-rpg:saved-game` (`SAVE_KEY` in `src/adapter/save-store.ts`). `createSaveStore(storage, content)` is a thin adapter and holds no rules: `read()` says `none`, `usable`, `unusable` (`damaged` or `incompatible`) or `unavailable` (the browser gives no storage, or refuses to read it), and `write(snapshot)` says whether the browser took the save. It never removes a save: one the game cannot continue from stays until the next autosave overwrites it. `main.ts` hands it `window.localStorage`, or null when the browser blocks it. Held keys are input, not state, so a Snapshot has none and `continue` clears them: a restored game stands still until a key goes down. Whatever the player is pressing right now is never saved, and the tickets that follow keep to that.
- **A save the game cannot take is never fatal.** `parseSave` (`src/adapter/saved-game.ts`) is the one gate between the text in the slot and the Game core. It is a pure function of the text and the content: it parses the JSON, checks the saved shape field by field (a snapshot must have exactly the fields the state has, with ids the content has and values that make sense, such as a position inside the area), and then tries the snapshot on a game of its own (`continue`, `view`, one step), so a save that passes the checks but cannot be played is refused too. A save that is not a snapshot is `damaged`; one made for other content or by another version of the game (the `version` marker, `SNAPSHOT_VERSION`) is `incompatible`. The title treats either as no save: Continue is greyed, a short message in the window says why and that a New Game will replace it (nothing is asked, because there is nothing to keep), and the console gets a warning with the detail. With no storage the title says SAVING IS NOT AVAILABLE and the game can still be played. A write that fails shows the notice COULD NOT SAVE THE GAME for a few seconds and the game goes on; the earlier save stays as it was.
- **Changing what is saved.** A ticket that adds to or changes the saved state bumps `SNAPSHOT_VERSION` (`src/core/state.ts`), with the literal of `Snapshot.version` in `src/core/interface.ts` (both are 2, since ticket 13 added the devices), so that older saves are named incompatible, and it extends two things in the same commit: the checks in `saved-game.ts` (they refuse a snapshot with fields the state does not have, so the tests go red until the checks are extended) and the fixture `tests/saved-adventure.ts` (a thing in its content and a chapter of its script that changes it). For a new kind of interactable, such as the devices of ticket 13, that means `FLAG_OF` and `checkInteractables` in `saved-game.ts`, as well as the fixture's content and a chapter. State that is only input stays out of the snapshot.
- **The tests.** The parser and the store are the first of the three exceptions of ADR 0002, tested directly because a save outlives the build that wrote it. `tests/saved-game.test.ts` pins the faults that matter, with saves written by hand. `tests/saved-game-sweeps.test.ts` damages a full saved adventure at every place of it in turn (the wrong kind of value, taken away, an extra field) and expects a refusal that names the place; the few places that would not be a fault are named in the file, and a ticket that adds state has its places swept without writing a line. `tests/saved-game-walks.test.ts` plays a hero that does anything at all, among every kind of monster and in the shipped content, and requires every state it saves to be usable and to come back as it was. `tests/save-store.test.ts` tests the store over a storage in memory that can fail. `tests/save-round-trip.test.ts` is at the Game core's interface: a game restored from its snapshot, after a trip through JSON text, is the same game after every chapter of `tests/saved-adventure.ts`, and a defeat after Continue goes as it would have. The saved adventure places no chaser, so the rows about one are judged in `saved-game.test.ts` with the content's rat made one.
- **Not tested automatically:** the title menu, the autosave rule and the scenes. Look at them in a browser with `npm run dev`: press Enter (a second time for the card of a New Game), walk to a Checkpoint or through an exit, reload the page and choose Continue. For a bad save, put text that is not a snapshot into the key in the console (`localStorage.setItem('island-adventure-rpg:saved-game', '{')`) and reload.

## The opening

- **What it is.** A New Game begins with a short card of text before the player takes control: a few lines that say what happened. It is content (`opening` in `ContentDefinition`, the lines are in `src/content/opening.ts`): one to four lines, none of them blank, and a content with none (leave `opening` out) has no card. `createGame` refuses an opening with no line, a blank line or more than four (`MAX_OPENING_LINES` in `src/core/content.ts`), naming the line. The pixel font draws letters (as capitals), digits and `. , ! ? ' - + / : ( ) % =`, and anything else is left blank, so write the lines with those: `tests/opening-card.test.ts` draws every character of the shipped opening to be sure.
- **Where the Game core stands.** The core sends the opening as an event and holds nothing for it. `new-game` returns `opening` (with the `lines`) first, then what entering the first area gives (its `area-changed`, `area-text` and so on); `continue` and a defeat never return it. The game is not paused and nothing is saved for it: if the caller steps, the hero walks. That is why the saved game needed no new field and `SNAPSHOT_VERSION` was not raised.
- **Where the adapter holds the game.** `startOfNewGame` (`src/adapter/scene-keys.ts`) turns the events of `new-game` into what `PlayScene` starts with: `saveAtOnce` as before, and the `opening` lines when the core gave them. While `PlayScene` has a card up (`OpeningCard` in `src/adapter/opening-card.ts`, above everything at depth 250) it does not step the core, forwards no key and discards what the menu and action keys pressed; Enter takes the card away and the screen fades in from black. The keys that are held are read again from the next frame. The area text counts its time from there, because no step has run. A New Game is still saved at once while the card shows, so a tab closed on the card brings back the new game on Continue, which skips the card.
- **The layout** is `layoutCard` in `src/adapter/opening-card.ts`, with no Phaser: each line is wrapped to fit the screen with the bitmap font (the same `wrapText` as the area text), lines are set apart more than the rows of one broken line, the rows are centred, the hint ENTER TO BEGIN sits under them, and the window is sized round them and centred on the screen.
- **The tests.** `tests/opening.test.ts` is at the Game core's interface on fixtures (`opening` in the arena options of `tests/fixtures.ts`): the event, its place before the area text, every new game, none for Continue, no pause and nothing saved, and the refusals. `tests/play-start.test.ts` pins what `PlayScene` starts with. `tests/opening-card.test.ts` pins the layout in numbers and the glyphs of the shipped lines. Not tested automatically: the drawing of the card, that it holds the game, and the fade.

## Art

The art is the Ninja Adventure pack (CC0), and the one record of every file copied from it is `docs/assets/licences.md`. Art is presentation only: no rule, number, map or collision depends on it, and the Game core knows nothing of it.

- **The asset manifest** (`src/adapter/asset-manifest.ts`) registers every picture by name, as one of three kinds: `image(file)`, `sheet(file, frameWidth)` for equal frames in one file, and `drawn(rows, palette)` for a small picture drawn in code where the pack has nothing (the armor icons, `src/adapter/drawn-icons.ts`). `ARTWORK` in `src/adapter/artwork.ts` is the one list, a line per picture, and the files are under `public/art/`. **To add a picture,** copy the file into `public/art/` unchanged, add its line to `ARTWORK`, and list the file in `docs/assets/licences.md` in the same commit.
- **Content asks for art by name, never by file.** For Gear and consumables the name follows one rule: `gear-<id>` and `consumable-<id>` (`gearIcon`, `consumableIcon` and `neededArt` in `artwork.ts`). A new piece of Gear or a new consumable needs its line in `ARTWORK` under that name. The flat colours, which every area without final art is still drawn in (see below), are named the same way: a terrain kind needs its colour in `TERRAIN_COLOURS` and a monster type its colour in `MONSTER_COLOURS` (`src/adapter/art.ts`), and one that has none is drawn in magenta. `tests/shipped-art.test.ts` fails for any picture or colour that the shipped content asks for and the adapter lacks.
- **A missing picture fails loudly, and says which.** `requireArt` throws an Error that names every picture that is missing. It runs when the game starts, on the names the content needs against the manifest, and again once the scene has loaded, on every picture of the manifest against Phaser's textures, so a file that is not there (a 404) is named too, and nothing is drawn as a blank. The check is a pure function of an `ArtLookup`, and `tests/asset-manifest.test.ts` tests it through its public functions with in-memory fakes. The loading itself is `src/adapter/asset-loader.ts`: `queueArt` in `preload`, then `buildDrawnArt` and `requireLoadedArt` in `create`. Files are fetched from `art/` under the site's base, so the game works from any path. `vite.config.ts` sets `appType: 'mpa'`: with the default single-page fallback the dev server answers a missing picture with `index.html` and a 200, which hides the missing file, and with `mpa` it is a real 404.
- **Final art, area by area.** `FINAL_ART_AREAS` in `artwork.ts` lists the Adventure Areas that are drawn from pictures: the shipwreck coast, the woods, the mountain and the cave. `hasFinalArt` is the one question the scene asks, and every other area keeps its flat colours (`TERRAIN_COLOURS` and `MONSTER_COLOURS`) until its own art pass, so an area can be playable before it is drawn. For a listed area `neededArt` asks for `terrain-<kind>` for every kind of terrain on its map and `monster-<type>` for every type placed in it, and the game refuses to start without them; for any other area it asks for nothing. **To give another area its art,** compose the pictures its kinds and types need, add their lines to `ARTWORK`, and then add the area to the list. `tests/final-art.test.ts` pins all of it, and `tests/mountain-cave-final-art.test.ts` that the mountain and the cave are on the list and that every picture they ask for is in the manifest.
- **Composed pictures.** Most of the pictures of the coast, the woods, the mountain and the cave are not copies of one pack file. `docs/assets/compose-art.py` cuts named pieces out of the pack, puts them together, and writes the PNGs of `public/art/`: it needs Python 3 with Pillow and the pack (not in the repository), and `python docs/assets/compose-art.py --pack "<the folder Ninja Adventure - Asset Pack>"` makes every picture again, or only the ones named after it; `--out <folder>` writes somewhere else. A few small touches are drawn by the script and say so in its comments; `docs/assets/licences.md` names, for each picture, the pack files and the pieces it was made from, and the same commit keeps it in step. The icons of the two bows are the pack's bows turned upright (the bow that the hero holds, `bow-held.png`, is the pack's own, lying down, which read as a bowl in the HUD and the inventory).
- **The ground.** `planTerrain` (`src/adapter/terrain-plan.ts`) is pure planning, with no Phaser: it turns the kinds of terrain of a map into a list of stamps, each a frame of a terrain sheet on a tile or on a quarter of one, so that a shore, the edge of the sand and the face of a cliff join up at bends, corners and inlets with thirteen pieces each. `bakeGround` (`src/adapter/terrain-baker.ts`) paints the stamps once onto one canvas texture for the area (`ground-<area id>`), in whole pixels with nearest-neighbour sampling, and the scene shows it as one image that scrolls with the camera, because terrain never changes. The wreck is a picture of its own (`terrain-wreckage`). Sand, grass and rock are dressed in the look of the area (`TerrainLook`, chosen by `lookOf`): the coast and the woods have the standard sheets, the mountain has cliffs of slate, and boulders where a rock stands alone, and the cave has a darker stone and a floor of sand and grass that is darkened in the sheets themselves, so that its dim look is in the ground and nothing is laid over what stands on it. A look changes the picture of a frame and never which frame goes where, so the maps and their collision are as authored (`tests/mountain-cave-ground.test.ts` pins both looks). `tests/terrain-plan.test.ts` pins the plan on small maps worked out by hand, and `tests/final-art.test.ts` that the pictures on disk hold the frames the plan asks for.
- **The monsters.** In an area of final art each monster is a sprite (`MonsterSprites`, `src/adapter/monster-sprites.ts`): four ways of facing, a walk, a white frame when it is hit, a red one with a shake while it winds up, faded copies of a dash, a puff of smoke where it fell, and its Health bar. `MonsterView` has no facing, so it is worked out from the last step, from the direction of a dash and, while it winds up, towards the hero. What a monster shoots (the spitter, the raider archer and the cave eye) is an orb (`src/adapter/projectile-sprites.ts`). The pack has no crab and no wolf, so the crab is its red mollusc and the wolf its black dog, and the spitter's mushroom has a purple cap, so that the red of a wind-up shows on it (all in `licences.md`). It has no raiders either: the dark ninja is the raider, the yellow one the charger, the blue one the archer and the knight, in navy, the veteran; the bat, the lizard, the eye and the bear of the cave are the pack's own, the bear in brown for the same reason as the mushroom's cap (`tests/mountain-cave-monsters.test.ts` pins their sheets). The telegraph and the strike of an attack stay shapes drawn in `src/adapter/art.ts`: they say where a blow will land and must read on every ground.
- **The props** every area shares (`PropSprites`, `src/adapter/prop-sprites.ts`): chests and caches shut and open (a Gear chest, a cache of Ammunition and a cache of Healing Potions look different from one another), what lies on the ground (a potion, arrows, a key, each with a glint now and then), Checkpoints (a grey flag hung low while untouched, a red one waving once it is the one the hero returns to), the chevrons that mark an exit, doors shut (with a padlock) and open, gates shut (iron bars under an arch that stands over the way and on the rock beside it) and open (the arch alone), levers at rest and pulled, and signs. Each stands with its foot on the bottom of the tile the core says it is on, and none of it knows which area it is in. A new kind of interactable gets its picture here, and a new area needs nothing.
- **What draws above what** is in `src/adapter/depths.ts`: the ground, the marks of an exit, the props, the telegraphs, the flat shapes of what has no picture yet, the monsters, their shots, the hero, the strikes. The telegraphs are above the props on purpose: a wind-up must never be hidden by a chest or a flag.
- **The hero** is `HeroSprite` in `src/adapter/hero-sprite.ts`: standing, walking in four directions, the sword, the bow, a red flash when hit and lying defeated, and the hero's arrows, which point along their flight. The Hunter's sheet has one attack pose per direction and nothing for being hit, so the sword in the hand, the slash and the flash are added there. It runs on frame time from the view and the events, and the weapon in hand is shown by its slot, because the view does not say which piece of Gear is equipped. Only the arrows the view says the hero shot are the hero's (`byShooter` in `src/adapter/projectiles.ts`); a monster's projectile is an orb and no arrow sprite is ever drawn on it.
- **The fall.** The Game core puts a defeated hero back at its Checkpoint, in another Adventure Area if that is where it is, in the very step that defeats it, so the view of that step already shows the place it returned to. `Fall` (`src/adapter/fall.ts`) keeps the last frame the player saw, with the hero lying in it at 0 Health (the HUD too: the counts it had), for `FALL_LIE_MS`, then the camera fades to black for `FALL_FADE_OUT_MS`, and only then does the scene show the place the hero returned to, fading in, with the Health, the Ammunition and the potions that the roll-back gave it. No step of the Game core runs during the fall, and its timeline always ends, so it can never hold the game.
- **The interface** is built from `UiLayer` in `src/adapter/ui-layer.ts`: nine-patch frames (`panel`, `window` and `button`, from the pack's wooden theme), pictures at whole pixels, text and bars, all in the `INK` colours. The HUD, the overlay, the Automap's window, the notice and the area text all use it, so the look is in one place. Text is the project's own 5 by 7 bitmap font, `src/adapter/pixel-font.ts`, whose letters are rectangles: Phaser's `Text` blurs at this size, and no font file is shipped (see A2 in the licence record).
- **Looking at it.** The drawing is not tested automatically. Open the dev server with `?debug`, press Enter on the title to start a game (and Enter again on the card of the opening), and use `gameCore` in the console to set a scene up (a `snapshot()` with more Gear or Health, then `send({ type: 'continue', snapshot })`), then look at the page: the HUD, both pages, the level-up choice, a pickup and the out-of-ammunition notice.

## How the tests work
The Game core's interface is the only automated test seam (see `docs/adr/0002-game-core-interface-is-the-test-seam.md`). Commands go in with `send`, time goes in with `step` (one fixed step is 1/60 s), and everything comes out as the return values of those calls, `view()` and `snapshot()`. Tests never look inside the core, never need Phaser, and are deterministic: time moves only when a test steps the game, and the random source is passed in.

- `tests/fixtures.ts` builds a small arena whose numbers can be worked out by hand. Expected values in tests are such hand-worked examples, never the rule run again, and test names use the glossary's words. For the bow it has `WITH_BOW` (starting Gear with a bow) and `cacheAt`; for pickups `pickupAt`; for drops `newGame` takes the random source, and `scriptedRandom` (fails if the game asks for a value nobody scripted) and `seededRandom` make one, while the default `fixedRandom` always says 0.5.
- A new rule starts as a failing test that creates a game with `createGame`, sends commands, steps, and asserts on the view, the events or the snapshot. Rules are tested against fixtures, so retuning the real content does not break them.

## Keeping the core independent

`tsconfig.core.json` type-checks only `src/core` and `src/content`, with no DOM or Node typings and no way to resolve other modules. A file there that imports Phaser or the adapter, or touches `window`, `document`, `localStorage`, timers, `performance`, `console` or `AudioContext`, fails `npm run typecheck`. Two things the compiler cannot see stay review rules: `Date` and `Math.random` are part of the language, so the core must read no clock and take randomness only from the `random` option; and the content may import only types from the core.

## Conventions

- **Content is data.** Maps, hero numbers, monsters and Gear live in `src/content` and are handed to `createGame`, which checks them and refuses anything invalid. The core holds no numbers of its own.
- **Units.** Positions and sizes are in tiles; a body's position is its centre. The adapter's tile size is one constant, `TILE_SIZE` in `src/adapter/config.ts`.
- **State is plain data** that survives `JSON.stringify` and `JSON.parse`. World state is kept per Adventure Area. `snapshot()` and the `continue` command save and restore a game, and the adapter keeps the snapshot in the browser (see Saving, Continue and the title).
- **Events are for presentation** (a swing, a hit, a defeat). The view is the truth; no rule depends on an event being seen.
- **Part of the world is still drawn as shapes**: the ground and the monsters of the areas without final art (`src/adapter/art.ts`), and the telegraphs and strikes of the monsters' attacks; later art tickets replace them with the pack's art through the asset manifest (see Art). The hero, its weapons and arrows, the HUD, the pages and the notices, the coast, the woods, the mountain and the cave with their monsters, and the chests, pickups, Checkpoints, exits, doors, gates, levers and signs of every area already use pictures.
- **Looking at the running game.** Open the page with `?debug` in the URL to expose the Game core as `window.gameCore`, for example `gameCore.view()` in the browser console. Nothing in the game uses it. The game opens on the title: `gameCore.view()` is `{ phase: 'title' }` until a game is started with Enter; a New Game then holds on the card of the opening until Enter again (the core is already in play by then, and nothing steps).
